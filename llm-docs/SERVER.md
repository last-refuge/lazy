# Lazy server

How `crates/lazy-server` works and how to run it. The contracts it implements are in [DECISIONS.md](DECISIONS.md) (D2 sign-in, D3 ordering, D4 submission, D11 conversations and read state, D12 message lifecycle, D13 reactions, D14 mentions and user groups, D15 threads, D16 incoming webhooks and bot identity, D17 attachments, D18 custom emoji, D19 search, D20 notifications and attention, D21 discovery, D22 workspace administration, D23 several workspaces, profiles and avatars, D24 logging) and the rustdoc of `lazy-protocol` (protocol version 14).

## Running it

```sh
scripts/dev-db.sh start                 # project-local Postgres on 127.0.0.1:54329
export DATABASE_URL=postgres://lazy@127.0.0.1:54329/lazy
cargo run -p lazy-server -- serve       # listens on 127.0.0.1:8080
```

`serve` applies the embedded migrations, starts the event-log pruner (see [Retention](#retention)), and, if no workspace exists, creates the workspace **Lazy** with a public `#general` channel. Both are safe to repeat and safe to run from several servers at once (an advisory lock guards the seed). Registering adds a person to that workspace and to its **default channel** (`#general`) only; other public channels are found by browsing and joined explicitly. The first person to register becomes the workspace's owner.

`lazy-server migrate` applies migrations and exits. `LAZY_LOG` (or `RUST_LOG`) controls logging (default `info,sqlx=warn`; [Logging](#logging)). Passwords, tokens, invitation codes, webhook secrets, database URLs, and message text, names and file names are never logged. `SIGINT` or `SIGTERM` starts a graceful shutdown: the listener stops, every WebSocket gets a close frame (code 1001), connections are given up to 10 seconds to finish, and the dispatcher and pruner stop.

```sh
curl -s localhost:8080/healthz
curl -s -X POST localhost:8080/v1/auth/register -H 'content-type: application/json' \
  -d '{"username":"ada","display_name":"Ada","password":"correct horse battery"}'
```

### Deploying

For a server on a public address (a container, Coolify, a VPS):

**First run.** `lazy-server serve` against an empty Postgres applies the migrations and creates the workspace **Lazy** with `#general`. Until someone registers, the log says so (`waiting for the first account: registration needs the setup code`, or, without a setup code, a warning that the first person to register will own the workspace).

**Set a setup code.** Without one, *the first person to register owns the workspace*, and on a public address that can be a stranger who found the page before you did. Set `LAZY_SETUP_CODE` to a random string of at least 16 characters (`openssl rand -base64 24`); the server refuses to start with a shorter one, saying so (and not repeating it). While the default workspace (the one registration targets) has **no members**, registration must carry the code in the field the registration form already has for an invitation code; a missing code and a wrong one get the same answer (`forbidden`, "this server needs its setup code to create the first account"), and nothing is created. The first account is the owner. From the moment the workspace has any member, however it got one, the code does nothing at all: it is not an invitation (presenting it is `invitation_invalid`, like any wrong code), and removing it from the environment later changes nothing. Of two first registrations with the right code at the same time, one is the owner and the other is handled as an ordinary registration. The code is compared in constant time, is never logged (the `starting` line says only `setup_code_set=true`), and `Config`'s `Debug` shows it as `<redacted>`. Prefer the environment variable to `--setup-code`: a command line is visible to other users of the machine. A server without the variable behaves exactly as before.

**Seed policy.** `LAZY_SEED_REGISTRATION=invite_only` creates the workspace with registration by invitation only, so that after the first account (the owner, let in by the setup code, or, with no setup code, whoever registers first) nobody else can register without an invitation from the owner. It applies only when the server creates the workspace; an existing workspace keeps its settings (change them in the workspace's settings). An invite-only workspace with no members lets its first registrant in, since nobody could have invited them; a public server should therefore always set a setup code.

**Health check.** `lazy-server healthcheck` exits 0 only if `GET /healthz` answers 200 within 3 seconds, so `HEALTHCHECK CMD lazy-server healthcheck` works in an image with no `curl`. With no flags it reads `LAZY_LISTEN` (the same variable the server reads) and asks that address, with an unspecified host (`0.0.0.0`, `[::]`) read as `127.0.0.1`; `--url http://host:port[/path]` asks elsewhere (the path defaults to `/healthz`; `https` is not supported: ask the plain listening address). It needs no database, speaks HTTP/1.0 over a plain TCP connection, prints one line (`healthy`, or `unhealthy: ` and a kind of failure such as `cannot connect (ConnectionRefused)`, `status 503` or `timed out`; never anything the server sent) and logs nothing.

**What to back up.** The database and `LAZY_ATTACHMENTS_DIR` together: the database says which files exist and the directory holds their bytes (restoring one without the other leaves messages without their files or files nothing refers to). Nothing else holds state: sessions are in the database, and the setup code and every other setting are the environment.

**Also for a public server.** Terminate TLS in front of the server (it has none), set `LAZY_PUBLIC_URL` to the address clients use (webhook addresses are shown under it), bind with `LAZY_LISTEN=0.0.0.0:8080` inside a container, and consider `LAZY_LOG_FORMAT=json` for a log collector.

## Ordering: how it is implemented

Every event-producing write runs in one transaction that calls `events::next_position`:

```sql
UPDATE workspaces SET event_head = event_head + 1 WHERE id = $1 RETURNING event_head, clock_timestamp()
```

The row lock is held until the transaction ends. A second writer's `UPDATE` waits, so position `n + 1` cannot be assigned until the transaction holding `n` has committed or rolled back. Hence positions are assigned in commit order, a rollback leaves no hole, and if event `n + 1` is visible to any reader, event `n` is too.

### The send transaction

1. Lock the conversation row `FOR SHARE`, then load the caller's facts and evaluate `ChannelAccess`. A conversation the caller cannot read is `not_found` (so private channels do not reveal themselves); readable but not postable is `forbidden`.
2. Claim the receipt: `INSERT ... ON CONFLICT (user_id, operation_id) DO NOTHING`. If it was not inserted, the existing receipt decides: same request fingerprint returns the original message (identical response), a different fingerprint is `conflict`. Two simultaneous duplicates serialize on this insert; the second waits for the first's outcome.
3. Resolve the [mentions](#mentions) in the document (a refusal here rolls the receipt back with everything else). Then `next_position`, and insert the message (`seq` = that position, `created_at` = the database clock read under the lock) together with its `mentions` and `message_mentions` rows. A [reply](#threads) also locks its root's message row before step 2, and appends `thread_changed` and the new followers' `thread_state_changed` events after step 5's event.
4. Move the author's `last_read` to the message's position, in this transaction and **without an event**: someone who has just written has read everything before it. (Not for a reply: see [Threads](#threads).)
5. Insert the event (audience `members`) and `pg_notify('lazy_events', workspace_id)`.
6. Commit. Only then is the acknowledgment returned.

Because a send holds the conversation row `FOR SHARE`, any number of sends run together, but never alongside an archive or a membership change (which take it exclusively). No message can therefore appear in the log after the event that archived its channel, or after its author's removal.

The fingerprint covers the conversation id and the document, so an operation id reused anywhere else is a conflict. Rejected sends (authorization failures) create no receipt.

Registration takes an advisory lock so registrations take turns (the first owns the workspace even when two arrive together), then the handle lock it shares with [user groups](#user-groups) and refuses a username that is reserved or that names a group, inserts the user and membership, joins the default channel, appends `member_joined` (audience `workspace`) and `member_added` for `#general` (audience `members`), creates the session, and commits.

### Bootstrap

One `REPEATABLE READ`, read-only transaction reads the workspace's `event_head` together with the caller's conversations (member conversations only, with participants for direct and group ones), their favorite and read state and unread counts, and the members. The same snapshot carries the workspace's user groups (ordered by handle, members by user id) and each conversation's `mention_count`, the caller's notification settings and conversation preferences, the ids of the newest 2,000 saved messages they can read, and each member's current (unexpired) status. Because an event and its `event_head` bump commit atomically, the snapshot contains exactly the effects of events up to `head`. A client that subscribes with `after = head` neither misses nor repeats anything. `bootstrap::joined_workspace` builds one workspace's part of it (the same code, in its own snapshot) for `PUT /v1/workspaces/{id}` and `POST /v1/invitations/accept`.

## Conversations and read state

`conversations.rs` implements every command in `lazy_protocol::api::paths` beyond messaging. They share one shape (the function docs have the detail):

1. **Lock the conversation row**: `FOR NO KEY UPDATE` to change it, `FOR SHARE` to act inside it.
2. **Load facts, then authorize** with the domain's `ConversationFacts`. A conversation the caller cannot see (a private channel they are not in, or one outside their workspace) is `not_found`, for everyone including the owner and admins. One they can see but may not do this to is `forbidden`.
3. **Write rows**: memberships, state rows, the conversation, `member_count`.
4. **Append events last** with `events::append_all`, which takes the workspace row lock for the position bump.

**Lock order is conversation row, then workspace row, always**, and nothing waits on anything else once it holds the workspace lock. Operations that wait on a unique index (creating a channel, opening a conversation) do so before that point. This is why the concurrent cases below cannot deadlock.

| Command | Allowed | Events appended |
| --- | --- | --- |
| Create channel | any workspace member | `conversation_created` (members) |
| Open direct/group | any workspace member, everyone named in the workspace, 2 to 9 people | `conversation_created` (members), only if it was created |
| Update name | the creator or an admin/owner; not archived | `conversation_updated` |
| Update topic/description | a member; not archived | `conversation_updated` |
| Join | anyone in the workspace, public and unarchived | `member_added` |
| Leave | a member of a channel, never the default channel | `member_removed` (members and the leaver), `conversation_updated` (new count) |
| Add members | a member; or an admin/owner for a *public* channel they are not in; not archived | one `member_added` per person newly added |
| Remove member | the creator or an admin/owner, never from the default channel | as leave |
| Archive / unarchive | the creator or an admin/owner; never the default channel | `conversation_updated` |
| List members (`GET .../members`) | anyone who can read the conversation (a member, or any workspace member for a public channel); otherwise `not_found` | none |
| Favorite | a member | `user_state_changed` (that person), if it changed |
| Mark read | a member | `user_state_changed` (that person), if it advanced |

Repeating a command that is already in effect (joining a channel you are in, archiving an archived channel, setting the same favorite) succeeds and appends nothing. A request that changes nothing (a topic equal to the current one, an empty update) appends nothing. A private channel is never reachable by an admin who is not in it, for any command.

**Idempotency.** Creating a channel and opening a conversation claim a receipt like a send does (`kind` distinguishes the commands, so an operation id reused across commands is a `conflict`), and `GET /v1/operations/{id}` answers `conversation_committed` for them. Channel names are arbitrated by the unique `(workspace_id, name)`: of simultaneous creates exactly one wins and the others get `name_taken`. Opening is arbitrated by the unique `(workspace_id, participant_key)` with `ON CONFLICT DO NOTHING`: the loser waits for the winner, finds its row, and returns it; only the winner appends `conversation_created`. Different operation ids for the same set, from either participant, all return the one conversation.

**Read state.** `last_read` is a message position. The unread count is messages from *other* people after it. A person's own send moves it (step 4 above). `MarkRead` takes the maximum of the current position and `min(up_to, newest message)`, so it only moves forward and cannot point past the end; it returns the resulting state. Someone who joins (or is added) starts with `last_read` at the conversation's newest message, so history from before they arrived is not "unread" (the protocol leaves this open; the alternative would show a new member every old message as unread). State rows are deleted on removal, so rejoining starts fresh, favorite included.

**`member_count`** is maintained by the same transactions that change membership, under the conversation row lock, and a test checks after concurrent churn that it equals `count(*)` of the members and that state rows exist exactly for the members. A removal appends a `conversation_updated` carrying the new count (the `member_removed` event has none); an addition's `member_added` already carries the count as of that person.

### Unread query plans

The bootstrap unread count for one conversation is `SELECT count(*) FROM messages WHERE conversation_id = $1 AND seq > $2 AND author_id <> $3`, run once per member conversation inside the bootstrap snapshot, with the person's read position as a concrete value. Measured on a seeded database with one 100,000-message conversation (80% from others) and 200 other conversations of 500 messages:

| Case | Plan | Buffers | Time |
| --- | --- | --- | --- |
| 10 unread in the 100k conversation | Index Only Scan on `messages_conversation_seq_idx`, 0 heap fetches | 4 | 0.04 ms |
| 100 unread among 200 other conversations | Index Only Scan, 0 heap fetches | 5 | 0.04 ms |
| 80,000 unread (nothing ever read) | Parallel Seq Scan (the right plan: 80% of the table matches) | 3637 | 11.7 ms |

Two things made this fast, both found by looking at the plan. The unread count was first written as a correlated subquery inside the member-conversations query; the planner cannot see the outer row's `last_read` and assumes a third of the table matches, so it scanned all 100,000 messages to find 8 (2128 buffers, 2.9 ms). Running one query per conversation with the actual position fixes that. And `messages_conversation_seq_idx` now carries `author_id` (`INCLUDE`), so the author filter needs no heap access.

Since threads (migration 0007) the count is `... AND listed AND NOT deleted` and runs on the partial `messages_history_idx` instead (thread-only replies and tombstones are not in it, and it carries the same `author_id` and `deleted`); the plans above are unchanged in kind. Re-measured on 1.48 million messages with 280,000 replies interleaved after the top-level messages: 10,000 behind is a parallel Index Only Scan with 0 heap fetches (4.7 ms), and never-read is the same parallel sequential scan as before (62 ms for about 1.01M matching messages, against 63 ms for the old query on the same data).

### Mention count query plans

`mention_count` is the number of *distinct* messages the conversation lists after the person's read position that name them or use `@channel` (`WHERE listed`, so a mention in a thread-only reply belongs to its thread): a `UNION` (not `UNION ALL`, so a message that does both counts once) of a range scan of `message_mentions_user_idx` and a range scan of the partial `messages_channel_mentions_idx` (channel messages not written by the person). It runs once per member conversation in the bootstrap snapshot and once per state response, with the read position as a concrete value for the same reason as the unread count. Measured on a seeded database of 1.2 million messages (one 1,000,000-message conversation with 5,000 members, 2% of its messages naming one person each, one "hot" person named by another 2% (20,000 rows), 0.2% using `@channel` (2,000 messages); and 100 channels of 2,000 messages; 49,600 `message_mentions` rows):

| Case | Plan | Buffers | Time |
| --- | --- | --- | --- |
| Caught up | Index Only Scan on each index, 0 rows | 8 | 0.08 ms |
| 10,000 messages behind (20 `@channel` messages) | the same two scans, 20 rows | 6 | 0.09 ms |
| Never read: 2,000 `@channel` messages | the same, 2,000 rows, HashAggregate | 25 | 0.75 ms |
| Never read, the hot person: 20,000 named + 2,000 `@channel` | the same, 22,000 rows | 358 | 6.7 ms |
| Every conversation of one person who has read nothing (101, including that one), one statement | | | 4.7 to 5.1 ms (their unread counts for the same 101: 82 ms) |

All of them are index-only with 0 heap fetches and no sequential scan, so the cost follows the number of mentions after the read position, never the length of the conversation. The first version of the partial index carried only `author_id`, so the channel branch had to visit the table for `id`: 2,016 buffers and 2.8 ms for the 2,000-message case (20 ms on a cold cache). Adding `id` to `INCLUDE` made it index-only (25 buffers, 0.75 ms), which matters because `@channel` counts for everyone in the conversation. Sizes: `message_mentions_user_idx` 5.9 MB for 49,600 rows, the partial index 240 KB. The mention count adds a few percent to a bootstrap that is dominated, as before, by the unread count of the 1,000,000-message conversation and by the 5,000-member list (`/v1/bootstrap` for that person, debug build, other work running on the machine: 150 to 210 ms, 509 KB). History paging is unaffected: the newest 50 of the 1,000,000 messages came back in 4 to 5 ms using the index it already used.

## Editing and deleting messages

`GET`, `PATCH` and `DELETE` on `/v1/messages/{id}` (`messages.rs`).

| | Who | Result | Event |
| --- | --- | --- | --- |
| `GET` | anyone who can read the conversation; otherwise `not_found` | the message, **tombstones included** | none |
| `PATCH` | the author, and only where they could post (not archived, not left) | the new revision | `message_edited` (members), carrying the editor's operation id |
| `DELETE` | the author where they could post, or an admin/owner in any conversation they can read (archived included), never a private channel they are not in | the tombstone | `message_deleted` (members) |

Authorization is `lazy_domain::message::MessageFacts` over facts loaded from the database for each request: the caller's `ChannelAccess` for the conversation, whether they are the author, whether the message is deleted. A message in a private channel the caller is not in, or one that does not exist, is `not_found` for every method; so is editing a deleted message.

**An edit is an operation like a send.** It claims a receipt keyed `(user, operation id)` whose fingerprint covers the message id, `base_revision` and document, so:

- the same id with the same request returns the **original result** even after the message has moved on: the receipt remembers the revision the edit produced, and that revision is read back from `message_revisions` if the message is past it. If the message has been deleted since, those revisions are gone and the tombstone is the only honest answer, so that is what is returned;
- the same id with anything different (the words, the base revision, another message, or a send's id) is `conflict`;
- `GET /v1/operations/{id}` answers `edit_committed` with that same result.

A new edit is then checked in a fixed order, and each failure leaves nothing behind, receipt included: deleted or invisible is `not_found`; not the author (or no longer able to post) is `forbidden`; a `base_revision` that is not the current revision, higher or lower, is `stale_revision` (409). An edit whose document equals the current one **commits only its receipt** (recording the revision it found), returns the current message, and appends no event.

A committed edit inserts the prior revision into `message_revisions`, updates the message (`revision + 1`, `edited_at` = the event time, a fresh `plain_text`), and appends `message_edited`. The message keeps its `seq`: editing never reorders a conversation.

**A delete is idempotent** and carries no operation id. The first one turns the row into a tombstone (the fixed placeholder document, an empty `plain_text`, `deleted`, `revision + 1`, `edited_at` cleared) and appends `message_deleted`. A second returns the same tombstone and appends nothing, to anyone who *could* have deleted it (someone who could not is still `forbidden`).

**What deletion erases.** The brief for deletion is that the earlier content is gone from the server, so one transaction clears every place it lived:

- the rows in `message_revisions` are deleted, and so are the message's `message_mentions` rows (see [Mentions](#mentions));
- the message's earlier `message_created` and `message_edited` events have their `message` replaced by the tombstone (`jsonb_set`, found through `events.message_id`). **This is the one place the event log is rewritten.** Without it the log would keep the text, and a device replaying from an old cursor would be handed it before the deletion. After the rewrite a replay shows those events as tombstones, and because a client keeps the highest revision it has seen, the end state is the same either way. **Only the `message` inside those events changes** (placeholder document, `deleted`, empty mentions). Everything else in the event stays as it was written, `operation_id` and a `message_edited`'s `previous_mentions` included: `previous_mentions` holds user ids and no content, and a client that counted that edit needs it to undo its count (see [Mentions](#mentions));
- `messages.document` and `plain_text` hold the placeholder and nothing.

A test counts occurrences of three distinct words across `messages`, `message_revisions` and `events` before and after.

**Lock order.** Every edit and delete locks, in this order: the conversation row (`FOR SHARE`, like a send, so neither can interleave with an archive or a removal), the message row (`FOR NO KEY UPDATE`, the lock an `UPDATE` takes, so concurrent edits of one message exclude each other), and only then the workspace row for the event position. This extends the order every other command uses (conversation, then workspace) and nothing ever takes a message row after the workspace row, so edits, deletes, sends, and conversation commands cannot deadlock with each other.

The position is deliberately the last thing reserved, not the first, because two outcomes must commit *without* an event. An edit that changes nothing still records its receipt, and a second delete returns the tombstone. A position cannot be reserved without an event, since that would leave a hole in the log (D3), so the bump has to wait until the transaction knows it will append one.

**History, unread and read position.** History lists what `listed` says (see [Threads](#threads)): deleted messages are left out, filtering before the page is cut, so a page holds `limit` messages that belong and `has_more` is true only if older ones that do remain (tested with deleted messages at the edge of pages); the one exception is a deleted root that still has replies. Unread counts exclude deleted messages, thread-only replies and tombstones, in bootstrap and in `UserStateChanged`. `MarkRead` clamps to the conversation's newest message **including tombstones**: a deleted message still occupies a position, a position that was reached stays valid, and the unread count is the same either way. A read position never moves backwards, so deleting a message the person had read (their own send moved their position to it) changes nothing.

**A repeated send returns the message as it now stands.** The receipt of a send points at the message, so retrying it after an edit returns the edited message, and after a deletion the tombstone. (An edit's receipt is what remembers its own revision.)

**Documents.** Stored messages are version 1 or 2 JSON; both read. Responses serialize the current version. A send's receipt fingerprint covers the serialized document, and documents moved from version 1 to 2, so `request_fingerprints` returns both forms and a repeated send is accepted if either matches: a person whose acknowledgment was lost across the upgrade is not told they conflict with themselves. The legacy form is byte-identical to what a version 1 server stored (a unit test pins this).

## Reactions

`PUT /v1/messages/{id}/reactions` with `{ "emoji": "...", "present": true|false }` (`messages::set_reaction`). It **sets a state**: whether the caller has reacted with that emoji. Like favorites it has no operation id and is not journaled.

**The emoji** is a `lazy_domain::ReactionEmoji`, which exists only if the text is one glyph from the dataset, in its canonical spelling. Parsing therefore happens while the body is deserialized, and anything else is `invalid_request` (400), never a server error. `❤` and `❤️` are one reaction, stored and returned as the canonical form; a skin tone is a different reaction. (Body parsing runs before authorization, as for edits, so a malformed body is `invalid_request` whatever message it targets; it reveals nothing about the message.)

**A custom emoji** is a reaction too: `custom:` and its id on the wire and in `message_reactions.emoji`. Adding one requires it to be live in the message's workspace (`invalid_request` for an unknown, deleted, or another workspace's), checked under a `FOR SHARE` lock on its row so a deletion and the reaction take turns ([Custom emoji](#custom-emoji)); withdrawing is never checked, so a deleted emoji's reactions can still be removed; it counts as a kind toward the 50, and a summary keeps naming a deleted emoji by id.

**Checks, in order**, each failure leaving nothing behind: a message that is deleted or that the caller cannot read is `not_found`; one they can read but could not post in (a public channel they have not joined, or an archived one) is `forbidden` (`MessageFacts::can_react`); adding an emoji that the message does not yet have when it already has 50 different ones is `limit_reached` (422). Adding to a kind that exists is never a new kind, and withdrawing the last reaction of a kind frees its place, so withdrawing and re-adding always fits. Someone who left a channel keeps their past reactions but cannot add or withdraw any.

**Idempotent.** If the caller's state already is what was asked for, the transaction commits nothing: no event, no position, no row change. The message is returned as it stands. A test asserts `event_head` is unchanged.

**Lock order is the edit's**: the conversation row `FOR SHARE`, the message row `FOR NO KEY UPDATE`, and the position last, only when something changes. Reactions, edits and deletions of one message therefore take turns, which also makes the limit exact (nothing can add a kind between the count and the insert) and means an edit reads, under its own lock, exactly the reactions it commits against.

**A change** inserts or deletes the one `message_reactions` row (stamped with the new position), sets `messages.reactions_as_of` to that position, and appends `reactions_changed` carrying the **complete new list**. Its audience is the conversation's members, with the D11 rules on replay and live delivery.

**Order.** A message's reactions are listed with each emoji at the place of its *earliest surviving* reaction (the smallest `seq` among its rows) and the people under it in `seq` order. So when the first person to use an emoji withdraws, that emoji moves to where the next person reacted; an emoji nobody uses is dropped; reacting again after withdrawing goes to the end.

**Versions.** `reactions_as_of` is the position of the latest change to the list (0 if never changed), independent of the content's `revision`. Every `Message` the server returns or announces carries its reactions and this version, so a client that keeps the highest `reactions_as_of` per message cannot be undone by a history page that was in flight while a reaction changed. That covers history pages, `GET`, the send, edit and reaction responses, `message_created` (empty), `message_edited` (the reactions at the moment of the edit), and the messages inside receipts' results.

**Loading.** One query reads the reactions of a whole page (`WHERE message_id = ANY(...) ORDER BY message_id, seq`), so a page costs one query for its reactions however many messages it holds, and grouping the rows in order gives the protocol's ordering with no sorting. Deleted messages are not queried.

**Deleting a message** deletes its reaction rows in the same transaction and gives the tombstone no reactions. Clearing them is a change to the list, so the tombstone's `reactions_as_of` is the deletion's own position and a client that keeps the highest version ends with none. Earlier `reactions_changed` events are not rewritten: they hold only emoji and people, no content.

**Measured.** On a seeded database with 300,000 messages in one conversation and 90,000 reactions (on 30,000 of them), the reactions of the newest 100 messages come back in **one query: 0.09 ms, 12 buffers**, a bitmap scan on `message_reactions_by_message_idx` and a sort of the 30 rows returned; the same page from the middle of the history (`seq < 150000`) is 0.08 ms and 16 buffers. The messages query that precedes it is unchanged (0.04 ms, 6 buffers).

## Mentions

A message's document may contain mention inlines (document version 3 appears only when one does; a message without mentions is byte-for-byte what it was). The server never parses text for `@names`: the client resolves them while composing, and the server reads `document.mentions()` (`MentionTarget::User`, `Group`, `Channel`) and **decides who is notified**. That decision is made when the message is sent or edited, in the same transaction, and stored with it (`messages.mentions`, the exact `Mentions { users, channel }` value, returned on every `Message`). History, `GET`, events and receipts therefore report what was decided then, without recomputing anything.

**Resolution** (`messages::compute_mentions`, under the conversation row lock), each failure leaving nothing behind:

1. `@channel` needs `lazy_domain::mention::can_mention_channel`: anyone who can post may use it, **except in the workspace's default channel, where only admins and owners may** (`forbidden`). It is allowed in direct and group conversations.
2. A named person must be in the workspace, and a named group must exist in it: otherwise `invalid_request`. A client cannot make the server notify anyone by naming an id it invented.
3. The notified people are the named people **plus the current members of the named groups**, **restricted to the current members of this conversation**, minus the author, deduplicated and sorted by user id. Naming someone who is not in the conversation is not an error; they are simply not notified (`Mentions.users` lists only people who were). Naming yourself notifies nobody. People named directly are still listed when `@channel` is also used (`channel: true` is separate from `users`).
4. Group membership is read **as of this moment**: a group that changes or is deleted later never changes the message (it keeps naming the group by identity and keeps the people it notified).

**Storage.** `messages.mentions` and `mentions_channel` (denormalized for the partial index), and one `message_mentions` row per notified person with the message's *own* `seq`. Unread is measured by message position, so a mention that an edit adds to a message the person has already read does not make it unread again, and one an edit removes stops counting. `@channel` has no per-person rows: it counts for everyone currently in the conversation, which is why the partial index exists. Someone who joins later starts with `last_read` at the newest message, so older `@channel`s do not count for them.

**The count** (`conversations::mention_count`, [plans above](#mention-count-query-plans)) is in bootstrap's `user_state`, in `UserStateChanged`, and in the responses to mark-read and favorite. A message that names the person *and* uses `@channel` counts once (`UNION`); the author's own `@channel` never counts for them, even if their read position were behind their own message (tested by rewinding it).

**Edits.** An edit that changes the document recomputes the mentions as of now and replaces the person's rows; one that changes nothing (the document equals the current one) commits only its receipt and **does not revalidate or recompute mentions**. The `message_edited` event carries `previous_mentions`, the set the edit replaced, so a client can correct its counts without holding the earlier version. The prior revision stored in `message_revisions` keeps its mentions, so a repeated edit (same operation id) returns the original words *and* the people they notified, not the current mentions.

**Deletion.** A delete clears `mentions`, `mentions_channel` and the `message_mentions` rows, and the tombstone notifies nobody. The `message_deleted` event carries **`had_mentions`: the mentions of the message's last version, the set stored when it was deleted (after any edits)**, so a client that counted the message for someone stops counting it. The rewrite of the message's earlier events (see [Editing and deleting](#editing-and-deleting-messages)) replaces **only the `message` inside** `message_created` and `message_edited`; `previous_mentions` on a rewritten `message_edited` stays exactly as written, because it holds user ids and no content and a client that counted that edit needs it. Replaying from before the message therefore shows: a tombstone `message_created`; a tombstone `message_edited` that still says which set it replaced; and a `message_deleted` whose `had_mentions` is the last version's set. Two tests pin this: a message that mentioned X, was edited to mention nobody and then deleted replays with the edit's `previous_mentions` = {X} and the deletion's `had_mentions` = {}; and one that mentioned X, was edited to add Y and then deleted replays with the edit's `previous_mentions` = {X} and the deletion's `had_mentions` = {X, Y}.

**Upgrading.** Every existing message mentions nobody (`DEFAULT '{}'`), old events replay unchanged (`previous_mentions` and `had_mentions` are optional on the wire), and old receipts, which the new constraint re-checks, keep working. `tests/upgrade.rs` migrates a database populated in the 0005 shapes (edited, deleted and reacted-to messages, an operation receipt, sessions, and an event log with rewritten tombstones), replays its whole log, and then edits, deletes, mentions and creates groups on top of it.

## User groups

`POST` and `GET /v1/workspaces/{id}/groups`, `PATCH` and `DELETE /v1/groups/{id}` (`groups.rs`). A group is a named set of workspace people that one mention reaches (`@design-team`).

| | Who | Result | Event |
| --- | --- | --- | --- |
| Create | admin or owner (`WorkspaceRole::can_manage_groups`); an ordinary member is `forbidden`, a non-member `not_found` | the group | `group_changed` (workspace) |
| Change handle, name, or membership | the same; a group of another workspace is `not_found` for everyone | the group | `group_changed`, only if something changed |
| Delete | the same; **deleting a group that is not there is `204` for any signed-in caller**, and a group of another workspace is `not_found` | none | `group_deleted` (workspace), only if it existed |
| List | any workspace member | the groups, by handle | none |

**Limits** (`limit_reached`, 422): at most 100 groups per workspace (exact, because creations take turns on a per-workspace lock) and at most 200 people per group, all of whom must be in the workspace (`invalid_request` otherwise). A request that repeats a person counts them once. Handles are lowercase whatever case was sent; `channel`, `here` and `everyone` are refused when the body is parsed (`invalid_request`, before any authorization, as for the other bodies).

**An update replaces what it names**: `members`, when given, is the complete new membership; absent fields are unchanged; a request that changes nothing (including an empty one) succeeds, appends nothing, and consumes no position. `group_changed` carries the **complete group**, members sorted by user id, to every workspace member, so autocomplete stays current without a fetch; `group_deleted` carries the id.

**One namespace for handles.** What follows `@` is looked up as a username or a group handle, so they must not collide. A group handle is unique per workspace (a constraint) and must not equal **any** username; a username must not equal a group handle in **any** workspace (people are global, workspaces are not); reserved words are refused for both (registration included: `invalid_request`). The claim and the check race, so they are serialized: creating, renaming and registering each take `pg_advisory_xact_lock(hashtextextended('handle:<handle>', 0))` *before* checking, and hold it to commit, so whichever comes second sees the first one's row and gets `name_taken` (a group) or `username_taken` (a person). **Lock order**: registration's own turn-taking lock, then the handle lock; group creation: the per-workspace `groups:<workspace>` lock, then the handle lock, then (after the checks) the workspace row for the event position; a rename: the handle lock, then the group row `FOR NO KEY UPDATE`, then the workspace row. Only other registrations wait on registration's first lock, and nothing takes a handle lock while holding the workspace row, so none of it can deadlock with the rest of the server. Tests hold the handle lock themselves, start a registration, a creation or a rename, assert it stays blocked, then commit the conflicting row and expect the refusal (so the outcome never depends on timing), and also race the pairs 15 times each.

**Idempotent creation.** Create claims a receipt (`kind = create_group`, fingerprinting handle, name and the *set* of members, so order is irrelevant) like channel creation, and `GET /v1/operations/{id}` answers `group_committed`. The receipt records the group id with **no foreign key**: deleting a group leaves it, so a retried create after the group is deleted is a `conflict` (not a second group) and the status becomes `not_found`. The operation id is checked against the caller, so another person's id is `not_found`.

**`GET /v1/conversations/{id}/members`** lists a conversation's member ids in the order they joined (ties by user id) for anyone who can read the conversation: its members, plus any workspace member for a public channel; everyone else, including the owner for a private channel they are not in, gets `not_found`. It is what lets a client offer only people who would actually be notified; a client adds the rest of the workspace itself when it wants to show who would *not* be.

## Threads

`GET /v1/messages/{root}/replies`, `PUT /v1/messages/{root}/thread/follow`, `POST /v1/messages/{root}/thread/read`, and `thread_root` / `also_in_channel` on the ordinary send (`messages.rs` for replies, `threads.rs` for the rest). A thread is a top-level message (the *root*) and its replies, in one conversation. A reply is a message row with `thread_root_id` set; it can be edited, deleted, reacted to and can mention people like any other message, and it inherits the conversation's access.

**What lists where.** `messages.listed` says whether the conversation's history lists a message, and everything that pages or counts a conversation reads it: a top-level message that exists; a reply sent also to the channel (`in_channel`), which is the same row and the same identity as in its thread, not a copy; and a **deleted root that still has replies**, as a tombstone. A thread-only reply is not listed; a deleted reply, a deleted root without replies, and a tombstone whose last reply went are not. The column is set when a message is created and changed only by the delete transactions below (so it never needs a join), and `CHECK`s keep it consistent with `deleted`, `thread_root_id` and `in_channel`.

**Sending a reply.** Everything is the ordinary send plus a root. `also_in_channel` without `thread_root` is `invalid_request`. After the conversation row (`FOR SHARE`) and the post check, the root's **message row is locked `FOR NO KEY UPDATE`** (only if it is a message of *this* conversation, so another conversation's message is neither locked nor revealed), then the receipt is claimed (so a retry waits for the original and, if the original committed, gets it back even after the root was deleted), then: a missing or other-conversation root is `not_found`; a deleted root is `not_found`; a root that is itself a reply is `invalid_request` (threads are flat; the client names the root); mentions are resolved as for any message. The lock order is **conversation row, root message row, the new reply (and the people's state rows), the workspace row for the event position last**: replies, edits, reactions and deletions of one thread take turns, and the same order serves the deletion of a reply. The receipt fingerprint of a reply also covers the root and the flag, so the same operation id for the same words in another thread, or without the flag, is a `conflict`; a send that is not a reply keeps the fingerprint it always had.

**Events, in order**, at consecutive positions: `message_created` (the reply, with `thread_root`), `thread_changed` (the root's new complete summary, whose `as_of` is the event's own position), then one `thread_state_changed` per person whose following **started** (replier first, the others by user id; owner-only). A reply that changes nobody's following appends two events.

**The summary** (`threads` row, kept in the reply's transaction under the root lock, so concurrent repliers are exact): `reply_count` counts replies that exist, `last_reply_seq`/`last_reply_at` are the newest reply's, `recent_repliers` is the last five *different* people, most recent first (a returning replier moves to the front), and `as_of` is the position of the latest change. Adding a reply is one upsert. Deleting one recomputes the newest remaining reply (an index lookup) and the repliers (an index scan back from the newest reply that stops at the fifth person); measured below. The summary reaches clients in `ThreadChanged`, and **every place a root `Message` is built carries its current summary**: history pages, `GET`, the send/edit/reaction/delete responses, and the events about the root (`message_edited`, `message_deleted`). `reactions_changed` carries no message.

**Deleting.** A **reply** becomes a tombstone (`thread_root` kept) and leaves its thread, its summary, and the channel; the transaction appends `message_deleted` then `thread_changed` (the new summary, or `None` when no replies remain, in which case a deleted root with nothing under it also leaves history and its followers' state rows are removed). A **root with replies** becomes a tombstone that stays listed and keeps its summary (the `message_deleted` carries it) and its replies, which stay readable; a **root without replies** is removed as in D12. The rewrite of earlier events applies to replies and roots exactly as for other messages: only the `message` inside `message_created`/`message_edited` becomes the tombstone (without a `thread` summary: `thread_changed` is what describes the thread), `previous_mentions` is kept as written, and `had_mentions` is the last version's. Nobody can reply to, react to, or edit a deleted root (`not_found`); following and reading its thread stay possible while it has replies.

**Replies pages.** `GET /v1/messages/{root}/replies` takes the history query and returns the history page: the replies that exist, oldest first within the page, the newest `limit` before `before`, `has_more` only if older replies that exist remain. It needs read access to the conversation. A reply, a message that does not exist or is not visible, and a deleted message without replies are `not_found`; a deleted root that still has replies works; a top-level message nobody has replied to has an empty thread (so a client can open the pane before the first reply).

**Following** (`thread_user_state`; the counts are derived, below). A reply starts following for: its **author** (always, also after they unfollowed; and they have read the thread through their own reply, as an author's channel send does for the channel); the **root's author**, when someone else replies; and each person the reply **mentions by name** (`Mentions.users`: named directly or through a group, already limited to the conversation's members; `@channel` alone does not follow), both unless they chose to stop. A person new to the thread by one of the last two starts having read everything before this reply, so only it is unread for them. Choosing to stop (`PUT .../follow {"following": false}`) sticks against replies and mentions of others; only replying (or choosing to follow) undoes it. A reply by the author never moves the **channel's** read position (it may have been written from a thread pane; opening a thread never moves the channel's reading position), and its edits do not auto-follow anyone (following starts when a reply is created).

**The commands** are states, so they are idempotent: asking for what already holds appends nothing and reserves no position. `PUT .../follow` needs a member of the conversation (`forbidden` for someone who only reads a public channel; `not_found` where the conversation or message is not visible); a person with no state who follows starts at the thread's newest reply (nothing unread) and one who unfollows has that remembered silently (their visible state is unchanged, so no event). `POST .../read` moves forward only and is clamped to the thread's newest reply; a person with no state has nothing to move (the answer is the thread read to its newest reply and nothing is stored). Both answer with the resulting `ThreadUserState` and append an owner-only `thread_state_changed` when something changed. Both lock the conversation `FOR SHARE`, the root `FOR SHARE`, then the person's state row, so they take turns with replies and with each other.

**The counts** of a person's thread state: *unread* is the replies from others after `last_read` that have not been deleted; *mentions* are those of them that name the person (a `message_mentions` row) or use `@channel`. One query reads `messages_replies_idx` from `last_read` (index-only: the author and the `@channel` flag are in the index) and probes `message_mentions`' primary key only for replies that are actually unread. Nothing is adjusted when a reply is edited or deleted; the count simply follows the rows. Nothing about threads enters a conversation's counts, and the conversation counts use `listed` (`messages_history_idx` and the `WHERE listed` mention indexes), so thread-only replies are invisible to them and in-channel replies, once each, are not.

**The bootstrap's `threads`** lists, per workspace, the caller's states for threads they follow or that have unread replies, in conversations they are in, newest activity (`last_reply_seq`) first, at most 500. The candidates (following, or newest reply past `last_read`) are chosen from the summaries alone and cut to the limit *before* any counting, so the work is bounded by the limit however many threads the person has touched; a candidate that is not followed and has nothing unread after counting is dropped.

**Access and delivery.** `thread_changed` goes to the conversation's current members and `thread_state_changed` to its person while they are a member (audiences `members` and `user`, evaluated at delivery like every event). Someone removed from a private channel replays nothing further about its threads, gets `not_found` for replies and thread commands, and their `thread_user_state` rows for the conversation are deleted with their conversation state (re-adding starts fresh). In a public channel a person who left can still read its replies but cannot change their thread state (`forbidden`). Archived channels accept no replies (`forbidden`); following and reading still work for members.

**Measured.** On a seeded database of 1.48 million messages (1,000,000 top-level messages in a 5,000-member channel, 100 other channels, and 279,892 replies in 50,000 threads: most with 2 replies, one in five with 10, one in fifty with 100, five with 2,000; 5% of replies also in the channel, 1 in 33 naming one person, 1 in 101 using `@channel`), all with warm caches:

| Query | Plan | Time |
| --- | --- | --- |
| History, newest 50 of the channel; and the page before position 500,000 | `messages_history_idx`, 51 rows, no sort | 0.20 ms; 0.09 ms |
| Unread count, 10,000 behind | parallel Index Only Scan on `messages_history_idx`, 0 heap fetches | 4.7 ms |
| Unread count, never read (about 1.01M listed messages) | Parallel Seq Scan: most of the table matches, as before | 62 ms (the same plan and time as the previous query on the same data) |
| Mention count, a person with 2,558 mentions; the hot person with 22,107 | the two index-only range scans, 0 heap fetches | 1.1 ms; 7.4 ms |
| Replies page, newest 50 of a 2,000-reply thread; and from the middle | `messages_replies_idx` backward, 51 rows | 0.09 ms |
| Thread counts, 2,000 unread replies (1,981 probed); a 2-reply thread | Index Only Scan + primary-key probes | 1.4 ms; 0.10 ms |
| Bootstrap thread list, 800 followed threads (500 returned); 20,000 followed (13,600 following) | candidates cut to 500 then counted | 3.2 ms (8,828 buffers); about 21 ms |

Through the server (debug build, other work on the machine): a top-level send 5.5 ms median, a reply into a small thread 4.0 ms, into the 2,000-reply thread 3.6 ms, deleting a reply from that thread 4.6 ms median (9.3 ms worst), the replies page 3.5 ms, a follow 4.6 ms, history 3.6 ms, and the whole bootstrap of a person following 20,000 threads (500 returned) 95 to 116 ms. Sizes: `messages_history_idx` 140 MB (the older unique index is 171 MB and still serves every message), `messages_replies_idx` 23 MB for 280k replies, `threads` 7.8 MB, `thread_user_state` 1.8 MB for 20,000 rows.

## Incoming webhooks and bots

A prototype (D16): `POST /v1/conversations/{id}/webhooks`, `GET` the same, `DELETE /v1/webhooks/{id}`, and the public `POST /hooks/{id}/{secret}` (`webhooks.rs`). An admin or owner makes a webhook for a channel and is shown its address once; anything that can `POST {"text": "..."}` there posts into that one channel, as a **bot**.

| | Who | Result | Events |
| --- | --- | --- | --- |
| Create | an admin or owner who can read the channel: `forbidden` for a member, `not_found` where the caller cannot read it (an admin outside a private channel included), `invalid_request` for a direct or group conversation, `conflict` when archived, `limit_reached` (422) at 10 | `CreatedWebhook`: the webhook and its address | `member_joined` (the bot, to the workspace) and `member_added` (to the channel's members) |
| List | the same people; `forbidden`/`not_found` as above | the channel's webhooks in use, oldest first; **no secret and no address** | none |
| Revoke | the same; a webhook that is gone, already revoked, or never existed is `204` | none | `member_removed` (the bot) and `conversation_updated` (the new count) |
| Deliver | whoever has the address (no `Authorization`) | `IncomingWebhookResponse { message_id }` | the ordinary `message_created` |

**The bot.** A `users` row with `is_bot`, username `bot-` and eight hex digits, the webhook's name as its display name, role `member`, a member of the channel (it joins when the webhook is made, announced like any member, and its read position starts at the newest message). The eight digits are the **last** eight of the webhook's id, because the start of a v7 id is a timestamp that repeats for a minute; if the name is somehow taken, another id is tried. Names of that shape cannot be registered by a person (`invalid_request`), the handle lock and group check that registration uses are taken here too, and group handles cannot equal a bot's name (the namespace is the username table's). It cannot sign in: its password is the marker `'!'`, and **signing in as a bot is the same `invalid_credentials` as a wrong password** and does the same work (the stored hash is replaced by the stand-in one, as for a name that does not exist), so neither the answer nor its time tells them apart (tested at the real hashing cost). No session can reference it (a foreign key, not a check in code). Revoking a webhook removes the bot from the channel and **keeps the user**: past messages keep their author, and the bot stays in the workspace's member list with `is_bot` set for clients to display. `User.is_bot` is on every `User` the server sends (bootstrap's members and the caller, `member_joined`); it is omitted when false.

**Never a person.** The places that take a person by id refuse a bot (`invalid_request`): opening a direct or group conversation, adding someone to a channel, a user group's members, and a mention. It cannot be removed from its channel by hand either (`forbidden`; delete the webhook), because the webhook would then silently stop working.

**The secret.** 256 random bits as 64 hex digits; only its SHA-256 is stored; shown once, in the creation response (clients must not log or keep it). Delivery looks the id up, hashes whatever secret was sent, and compares the two hashes in constant time against the stored one (or against zeros if there is none). **A wrong secret, an unknown id, an id that is not an id, and a revoked webhook all answer the same `not_found`**, byte for byte, and all do the same lookup, hash and comparison. The path is the only credential, so it is kept out of logs and out of every error: the request span (`TraceLayer`) shows `/hooks/<id>/<redacted>` instead of the URI (tower-http's default span logs the full URI at debug, which is where it would have leaked), the hook handler reads its path as plain strings so a malformed one is never echoed back, and a test captures everything the server logs, at trace level, for good and failing deliveries, and asserts neither the secret nor a guess appears in a log line or an answer.

**Delivering**, in this order: check the address (404); take a token from the webhook's bucket (429, `Retry-After` in whole seconds rounded up; **only a right secret reaches the bucket**, so guessing neither uses anyone's allowance nor grows the map); validate `Idempotency-Key` (1 to 64 printable ASCII characters, else `invalid_request`); refuse a declared size over 64 KiB, then read at most 64 KiB (`payload_too_large`, whether or not the size was announced); parse `{"text": ...}` (`invalid_request`); empty or blank text is `invalid_request`; replace `:shortcode:` emoji and parse the text as markdown with **no mention directory**, so `@alice` and `@channel` stay plain text and notify nobody (a message holds at most 40,000 bytes of text, so a body within 64 KiB can still be `invalid_request`); then the **ordinary send** as the bot, which is a member, so `can_post`, the receipt, ordering, events, unread counts, replay and the read position are all the ordinary ones. Refusals of the send are translated to what they mean at the address: the bot no longer being a member (revoked a moment ago) is `not_found`, an archived channel is `conflict`.

**Idempotency.** With a key the operation id is the UUID v5 of the webhook id and the key, so a retry hits the bot's ordinary send receipt and returns the same message with 200 and appends nothing; the same key with other text is a `conflict`; without a key every delivery is new. A retry after the webhook was revoked is `not_found` like any delivery to it.

**The rate limit** is a token bucket per webhook in the server's memory: a burst of 30, one more per second (`IntegrationOptions::webhook_rate`; the tests use smaller ones). It resets on restart and is not shared between server processes.

**Locks.** Creating and revoking change the channel's membership, so both hold its row exclusively (like adding or removing any member), which makes the limit exact; a delivery holds it shared like any send. A delivery and a revocation therefore take turns: a delivery either commits before the bot leaves or finds it gone, and every acknowledged delivery is before the `member_removed` event (tested over 10 races of 20 deliveries each).

**Upgrading.** Every existing user is a person (`is_bot` defaults to false, and the placeholder `CHECK` is satisfied by every real hash), every existing session satisfies the new foreign key, and there are no webhooks; `tests/upgrade.rs` migrates a populated 0007 database and uses webhooks on top of it.

**What the prototype showed** (also in D16):

- *Identity.* A bot has to be a real user: authors, events, receipts, reactions and threads all refer to a user id. That made `is_bot` plus a database-enforced "cannot have a session" the safest shape, and it put the bot into every place that lists people, so those places had to be told (above). Its username has to be generated and reserved in the same namespace as people and groups, or a person (or a group handle) can take a bot's name first. Display names are the webhook's name and are not unique, so two bots can look the same in a member list. There is no rename. A revoked bot stays in the workspace's member list for good (its messages need an author), and nothing in the user says whether its webhook is still in use.
- *Membership.* The bot counts in the channel's `member_count` and appears in the channel's members list, so "N members" and "who would be notified" include an integration unless the client leaves it out. The bot's own read position moves with every delivery (one state row per bot per channel), harmlessly.
- *Authorization.* Creating is for the people who may manage integrations and can read the channel, so an admin cannot give a private channel a webhook unless they are in it. The address in the path is a bearer credential that proxies, load balancers and browsers' histories all see; this server redacts its own logs, nothing else can be redacted for it, and a header credential would be better when integrations are built properly. There is no recovery of a lost address and no operation id on creation: a lost response leaves a working webhook (and a visible bot) nobody has the address of, until an admin finds it in the list and deletes it. Scope is exactly the channel: the bot's membership is the enforcement, so archiving or removing it stops delivery at once, and unarchiving resumes it.
- *Behavior in the ordinary path.* Almost everything worked because a delivery *is* a send: ordering, unread counts, replay, receipts, threads under a bot's message, reactions, and moderator deletion (the tombstone is attributed to the bot). What needed care was (1) **edits**: nobody can edit a bot's message, since its author cannot sign in, so an integration cannot correct a message, only post another (a later version of this would need an edit through the address); (2) **mentions**: ignored by construction, but also refused as a mention *target*; (3) a revoked bot is not a member, and a public channel's non-member can read but not post, so the send's refusal was `forbidden`, not `not_found`, which had to be translated for the caller of the address; (4) **a flood** costs the same as a person's flood: each delivery holds the conversation row and the workspace position lock, so a webhook allowed 30 deliveries at once can crowd a busy workspace's log for that moment, and the limit is per webhook, so ten webhooks in a channel ten-fold it; (5) the **receipt per bot** that gives idempotency is kept forever like every receipt.

## Attachments

`PUT /v1/conversations/{c}/attachments/{id}`, `GET /v1/attachments/{id}` and `/thumbnail`, and `attachment_ids` on the ordinary send (`attachments/`, with `messages.rs` for attaching). Postgres holds the metadata and who may read each file; the bytes live behind the `AttachmentStore` trait (`attachments::store`), as files under `--attachments-dir`: `{dir}/{first two hex digits of the id}/{id}` for the file and `{id}.thumb` for its thumbnail (and `{id}.emoji` for a [custom emoji](#custom-emoji)'s image: ids are chosen by clients, so an emoji and a file that share one must be different objects), and `{dir}/tmp/{id}.{nonce}.part` for an upload in progress (the nonce keeps two uploads of one id from writing the same file; D17 names the file `{id}.part`). The in-memory store is for tests that do not look at the disk; test servers get a temporary directory of their own.

**An upload, in order.**

1. The caller must be able to post in the conversation (`not_found` where it is invisible, `forbidden` where it is read-only or archived).
2. `Content-Length` is required (a chunked body, or none, is `invalid_request`) and checked against the limit **before any byte of the body is read** (`payload_too_large`, 413).
3. The id: if a row exists it is the same upload again only if it is the caller's, for this conversation, not deleted, and the same size; otherwise `conflict`, with the same answer whether it is someone else's or merely different. Otherwise the caller's pending limits are checked from the declared size (50 files, 200 MiB: `limit_reached`).
4. The body is **streamed to a staging file** while its SHA-256 is computed and its first 512 bytes kept, the limit enforced again as it streams, and the file flushed to disk. It is never held whole.
5. The media type is decided from those bytes (`resolve_media_type`: a recognised signature wins over what the client said; otherwise the declared type survives only if it is well formed and not active content, else `application/octet-stream`). A file that is one of the four raster types is decoded on the **blocking pool, behind a semaphore of four** (`images.rs`): the header is read first and the pixel count checked against 64 million before anything is decoded, then the image is decoded (a GIF or WebP as its first frame, a photo turned upright by its EXIF orientation, so the stored `width` and `height` are the upright ones) and its thumbnail made (long side at most 640, JPEG at quality 80, or PNG when any pixel is transparent). An image that does not decode, or has too many pixels, is `unsupported_media` (415). The name from `x-attachment-name` is percent-decoded (a bad escape or invalid UTF-8 is `invalid_request`; no header is `file`) and sanitised.
6. Then, in a transaction holding two advisory locks (`attachment-user:{uploader}`, then `attachment:{id}`, always in that order): the id is looked up again (a racing identical upload is the same attachment, and the staged file is dropped; the same id with other bytes is a `conflict`), the pending limits are checked again (**exact**, because they are checked under the person's lock: sixty simultaneous uploads get exactly fifty places), the staged file is moved to its name and the thumbnail stored (each written, flushed, renamed and the directory flushed), and the row inserted.

**Crash safety is in that order.** The row is written last, so a crash can leave a file with no row but never a row with no file; the file is found by the daily sweep once it is old enough that no upload could still be about to write its row. A crash while streaming leaves only a staging file, which the same sweep removes. When the row cannot be written the files are taken back out at once. (`AttachmentOptions::fail_between_file_and_row` makes an upload fail at exactly that point, for tests.)

**Attaching.** A message names its files in `attachment_ids`, in order, at most 10, each once. In the message's own transaction, after the conversation row (and the thread's root) and before the workspace row, the files are locked in id order (so two messages naming the same files take turns) and checked: each must exist, be the sender's, belong to this conversation, and not be deleted (`not_found`, the same answer for all four so ownership is not revealed), and be unattached (`invalid_request`). Any failure sends nothing. Then they are attached in order. A message with files may have an empty document (`MessageDocument::empty`; its `plain_text` is empty, it is listed, counts as unread for others, can be reacted to, replied under and deleted like any other); a message with neither words nor files is `invalid_request`, replies and also-in-channel replies included. The retry fingerprint of a send includes its files, so the same operation id with other files is a `conflict` and the same with the same files returns the same message with its attachments. **An edit** changes the words only: it may empty them only if the message has files (`invalid_request` otherwise), and an edit that changes nothing is still a no-op. Webhook deliveries have no files.

**Everything that builds a `Message` carries its files** (history, `GET`, replies pages, the send, edit, reaction and delete responses, receipts, events), with **one query for a whole page** (`message_id = ANY(...)` on `(message_id, ordinal)`, deleted messages left out), like reactions and thread summaries.

**Downloading.** `GET /v1/attachments/{id}` (and `/thumbnail`, for images the server decoded): the uploader alone while the file is pending; whoever can read the conversation once it is on a message (a public channel's files are readable by people who have not joined it); never a deleted message's or a deleted file; and a file that does not exist, is not yours to read, or has gone all answer the same `not_found`. The response is streamed from the store (never buffered), with `Content-Type` the stored type, `Content-Disposition: inline` **only** for PNG, JPEG, GIF and WebP and `attachment` for everything else (with the name as an ASCII fallback and as `filename*=UTF-8''...`), `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, `ETag` (the SHA-256 in quotes, `-thumb` appended for a thumbnail), `Content-Length`, and `Cache-Control: private, max-age=31536000, immutable`. A matching `If-None-Match` (a list, weak validators and `*` included) is a `304` with the same headers and no body, after the access check. `HEAD` is served. `Range` is ignored (the whole file, `200`). Uploads and downloads have a 15-minute timeout; every other request keeps 30 seconds.

**Deleting and cleaning up.** Deleting a message marks its files deleted **in the same transaction** (access ends at once, for everyone), and the tombstone and the rewritten events carry no files. The hourly `cleanup` pass (a) marks pending uploads older than 24 hours deleted, claiming them `FOR UPDATE SKIP LOCKED` so it never waits on, or deadlocks with, a send that is attaching them, then (b) removes the files of every row marked deleted and only then the rows, so a crash in between leaves rows for the next pass, then (c) removes the images of deleted custom emoji and marks them removed ([Custom emoji](#custom-emoji)). `CleanupReport` counts each. The daily `sweep_orphans` removes files that have no row of their own kind (an attachment's file is accounted for by an `attachments` row, a custom emoji's image by a `custom_emoji` row whose image is not yet removed), and staging files that were never finished, once older than a grace period (an hour by default), by modification time. Both run once at start-up and log counts, never names. Their intervals, the 24 hours and the grace period are `AttachmentOptions` fields; the tests call the functions directly with the values they want.

**Measured** (release build, loopback, files on the machine's NVMe disk, the page cache warm, so these are the server's costs rather than a network's): a 25 MiB upload takes **22 ms** alone (about 1.1 GB/s, including the SHA-256 and the flush to disk) and 70 ms each when eight people upload at once; a 25 MiB download takes **10 to 15 ms** alone and 15 ms each with eight at once. **Memory is flat, which is the check that the body is streamed**: the server's resident size was 31 MB idle, 34 MB after five sequential 25 MiB uploads, and **71 MB at its peak after eight simultaneous 25 MiB uploads and eight simultaneous downloads** (a buffering server would have passed 400 MB). Images are where the memory goes: uploading a 12-megapixel image (4000 by 3000, a 4.5 MB JPEG or a smooth PNG) takes **100 to 130 ms** with its decode and thumbnail, and eight at once 108 to 258 ms, with the resident size peaking at **230 MB after a sequence of them and 462 MB with eight at once** (four decodes at a time, each holding the decoded pixels and the scaled copy). The worst case the cap allows is a 64-megapixel image, which decodes to 256 MB, so four at once could reach about 1 GB; lower `AttachmentOptions::thumbnail_slots` (it is 4) if that is too much. The files for a history page are **one index lookup**: for the newest 51 messages of a 300,000-message conversation in which 40% of messages have 1 to 3 files (240,008 files), `message_id = ANY(...)` is an Index Scan on `attachments_message_idx`, 42 rows, **5 buffers, 0.06 ms**, beside the messages query (6 buffers); the whole history request is about 2 ms.

## Custom emoji

`PUT /v1/workspaces/{w}/emoji/{id}`, `GET /v1/emoji/{id}`, `PATCH /v1/emoji/{id}`, `DELETE /v1/emoji/{id}`, the `custom_emoji` list in the bootstrap, and the checks that messages and reactions make (`emoji.rs`, with `messages.rs` calling it; D18, protocol 9). The row (`custom_emoji`) says what an emoji is and whether it is live; the image is a small PNG in the attachment store.

**Who.** Admins and owners add, rename and delete (`WorkspaceRole::can_manage_emoji`); every member of the workspace reads the image and uses the emoji. Someone outside the workspace, and any emoji that is unknown or deleted, get the same `not_found`; a member who may not manage gets `forbidden`.

**An upload, in order.**

1. The caller's role (`not_found` outside the workspace, `forbidden` for a member).
2. `x-emoji-name` parsed with `EmojiName::parse`: 2 to 32 lowercase letters, digits and underscores, starting and ending with a letter or digit, lowercased on the way in, and never a standard shortcode (`tada`, which would make `:tada:` ambiguous): `invalid_request`.
3. `Content-Length` is required and at most 512 KiB, checked **before any byte of the body is read** (`payload_too_large`; none or a chunked body is `invalid_request`). This is the attachments' helper with a smaller limit.
4. Cheap early checks from a connection: if the id exists it is a repeat only when it is this workspace's, live, and has this name (anything else is `conflict`, with one answer for all of them); otherwise the name must be free among live emoji (`name_taken`, 409) and fewer than 500 live (`limit_reached`, 422).
5. The body is streamed to a staging file with the attachments' code (hash computed, size limit enforced again while streaming). It must be a PNG, JPEG, GIF or WebP by its bytes (`unsupported_media`, 415). It is decoded on the **same blocking pool and semaphore as attachment thumbnails**: the header is read first and refused above 4,194,304 pixels (`unsupported_media`, as for attachments; nothing is decoded), then the image is decoded (a GIF or WebP as its first frame), turned upright by its EXIF orientation, scaled down with Lanczos3 until its long side is at most 128 pixels (aspect kept, **never enlarged**), and written as an RGBA PNG. **The original is not kept**: the staged file is discarded whatever happens.
6. In a transaction holding two advisory locks (`emoji:{workspace}`, then `emoji-id:{id}`): the id is looked up again (a racing identical upload, with the same name and the same bytes, is the same emoji and answers 200; the same id with anything else is `conflict`), then the name and the limit are checked again (**exact**, because they are checked under the workspace's lock: ten uploads racing for three places get exactly three), the PNG is stored, the row inserted **last**, `emoji_changed` appended, and the transaction committed. When it fails the PNG is taken back out at once (`AttachmentOptions::fail_between_file_and_row` makes an upload fail at exactly that point, for tests; the file is then left for the sweep).

**Crash safety is the attachments'.** The row is written last, so a crash can leave a file with no row, never a row with no file, and the daily `sweep_orphans` removes it once it is old enough. The sweep accounts for a file by a row **of its own kind**: an attachment's original or thumbnail by an attachment, an emoji's PNG by a `custom_emoji` row with `NOT image_removed`. **The image's name is `{dir}/{xx}/{id}.emoji`**, not the bare id attachments use. D18 says the image is stored under the emoji's id; the suffix keeps that and fixes a hole it would have left: ids are chosen by clients, an emoji's is visible to the whole workspace and a file's to everyone who can read its message, so a shared namespace would let someone give a file the id of an emoji (or the reverse) and replace the other's bytes. As separate objects neither can read, replace, list as, or delete the other, and a test uploads each with the other's id.

**Serving.** `GET /v1/emoji/{id}` streams the PNG from the store with `Content-Type: image/png`, `Cache-Control: private, max-age=31536000, immutable` (an id's image never changes), `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, `Content-Length`, and an `ETag` that is the SHA-256 **of the uploaded bytes** in quotes (not of the stored PNG; D18 does not say, and it is as good a validator because the stored PNG is a pure function of it). A matching `If-None-Match` is a `304` with the same headers and no body, after the access check. `HEAD` is served. Uploads share the 15-minute timeout of the attachment routes; the other three keep 30 seconds.

**Renaming** takes the workspace lock and the row `FOR UPDATE`; the new name goes through the same rules as an upload's and must not be a live emoji's (`name_taken`). Renaming to the emoji's own name changes nothing and appends nothing. A rename is one `emoji_changed`; messages and reactions name the emoji by id, so they read with the new name at once.

**Deleting** is soft and idempotent: it sets `deleted_at` and appends `emoji_changed` with `deleted: true` in one transaction; a second delete, and a delete of an id that never existed, are a quiet `204` (as for webhooks). The name is free at once (the unique index covers live rows only). Nothing that used the emoji changes: its messages keep it by id and show `:name:`, reactions keep it. The image is removed by the hourly cleanup job (`CleanupReport::emoji_images`): the file first, then `image_removed` set, so a crash between is simply retried, and removing a file that is already gone is not an error.

**Using one.** Every id in a message document (`MessageDocument::custom_emoji`) must be a **live** emoji of the conversation's workspace, else `invalid_request` and nothing is sent. The check runs in the send's or edit's own transaction, after the attachments are claimed and before the workspace row. **An edit checks only the emoji it adds**: those the message's current document already has are not checked again, so an edit is not refused merely because an old emoji has since been deleted, but it cannot add a dead one. A retry of a send returns the stored message through its receipt without checking again. Replies and also-in-channel replies are held to the same rule. A webhook delivery never contains emoji (a `:name:` in its text stays text, and a shortcode that is a standard emoji becomes that glyph, as before). Reactions: see [Reactions](#reactions).

**Using an emoji and deleting it take turns.** The check selects the emoji rows `FOR SHARE` (ordered by id) in the same transaction that commits the message or reaction. A deletion and a rename update the row, so they take the lock exclusively: a use either commits before the deletion or waits for it, finds the emoji deleted and is refused. **Nothing is ever committed that uses an emoji deleted before it**, and the log's positions show it (every message and reaction that used an emoji has a position before the deletion's). Uses share the lock with each other and never wait on one another. The full lock order of a message is the conversation row, the thread root's row, the attachment rows (id order), the emoji rows (share), and the workspace row (the event position) last; a deletion takes the workspace advisory lock, the emoji row and then the workspace row, so there is no cycle.

**The bootstrap** carries every emoji of the workspace, **deleted ones included and marked**, ordered by name and then id (a deleted `party` and a live one made later both appear), so a client can show `:name:` for old messages. `emoji_changed` is a workspace-audience event carrying the complete emoji, appended in the same transaction as the change, so a returning subscriber replays the whole story.

**Measured** (release build, loopback, page cache warm; each figure is the whole request as the client sees it: the hash, the decode, the resize, the PNG encode, the file write and the transaction). A **512 KiB PNG** (415 by 415 pixels of random noise, 506 KiB: the largest upload allowed, and a hard one for its size) takes **5 to 11 ms** (median 6.6 ms over 20, one after another) and 12 to 23 ms each with eight at once. A **4-megapixel JPEG** (2048 by 2048, exactly the pixel limit; 97 KB of detailed plasma, and 30 KB of smooth gradient) takes **35 to 39 ms** (median 37 ms) alone, 39 to 65 ms each with four at once (66 ms for all four), and 38 to 125 ms each with eight at once (128 ms for all eight: four are decoded at a time, the slots being shared with attachment thumbnails). It is the pixels, not the bytes, that cost. The server's resident size was 30 MB idle and **134 MB at its peak** after all of that, including the eight simultaneous 4 MP decodes; the 4 MP limit keeps one decode to about 16 MB of pixels, where the attachments' 64 MP limit allows 256 MB. A stored image is at most 128 pixels on a side (the noise PNG's 128 by 128 result is 55 KB, the largest seen; the average was 42 KB), and `GET` of one takes **0.4 to 1.7 ms**.

## Search

`GET /v1/workspaces/{id}/search?q=…&limit=…&offset=…&sort=relevance|recent` (`search.rs`; D19, protocol 10). The caller must be a member of the workspace (`not_found` otherwise, the same answer as for a workspace that does not exist). `q` is parsed by `lazy_domain::search::SearchQuery::parse` (a NUL is first replaced by a space); an unusable query is `invalid_request` with the `SearchError` text, a missing `q`, a non-numeric `limit` or `offset`, and an unknown `sort` are `invalid_request` too.

**Everything happens in one `REPEATABLE READ`, read-only transaction** with `statement_timeout` set from `SearchOptions` (3 s) and `jit` off, so a page is one consistent view and a slow search is cancelled, not left holding a connection. The search statement is not a prepared statement (`persistent(false)`), so it is always planned for its own values.

**Who can find what.** First `accessible` lists the workspace's conversations the caller is a member of, plus its public channels (archived ones too); an `in:` filter narrows that list to the channels of those names. The search statement then only looks at messages with `m.conversation_id = ANY(list)`; an empty list returns an empty page without running it. So a private channel or direct conversation the caller is not in is never a candidate, an `in:` naming one is indistinguishable from one that does not exist (a test compares the two responses), and a member removed from a conversation has lost it in the next search (`conversation_members` is read in the same snapshot). Nothing is filtered after the fact. The list is passed as a value rather than as a subquery on purpose: a first version joined a `WITH acc AS MATERIALIZED (…)` CTE, the planner estimated one row for it, and a person with access to one small conversation (or none) made it walk the whole `messages_seq_idx` (433 ms for an `in:` naming a private channel the caller was not in, with nothing to find). With the list as a parameter the planner sees its size, and the same search is 0.5 ms or does not run. Deleted messages never match (`NOT m.deleted`; a tombstone's text is empty anyway); a deleted root with replies is not a result, but its replies are, with `thread_root`; bot and webhook messages match like any other.

**The query becomes a `tsquery` string built with escaping and bound as one parameter.** Each word is a quoted lexeme with the prefix marker (`'deplo':*`; `'` is doubled and `\` doubled, and everything else inside quotes is literal, so `& | ! ( ) < > : *` have no meaning), a phrase is its words joined with `<->` in parentheses (**each word a prefix**, so a phrase typed live matches), an exclusion is `!(…)` (a prefix too), and all of them are joined with `&`. The text-search parser then splits each quoted word exactly as it split the indexed text, so `foo-bar` is `'foo-bar' <-> 'foo' <-> 'bar'` and `:party_parrot:` is `'party' <-> 'parrot'`. No user text is ever part of the SQL: filter values are bound arrays too. Tests send fifty hostile strings (quotes, backslashes, every operator, NUL, long words, a SQL injection) and require 200 or 400, and check that `apple | banana` is three plain words and not OR.

**Filters.** `from:` is `m.author_id IN (SELECT id FROM users WHERE username = ANY(…))` (an unknown name matches nothing, bots included); `after:` is `created_at >=` the UTC midnight of the day and `before:` is `created_at <` it; `has:file` is an `EXISTS` over the message's non-deleted attachments and `has:image` adds `media_type` in the four types the server decodes (PNG, JPEG, GIF, WebP; not SVG).

**Candidates, ranking and the cap.** A text query takes the newest `rank_candidates` (2,000) matches by position, plus one to know whether there were more, ranks them with `ts_rank_cd(vector, query, 1)` (normalised by length, so a short exact message beats the same word buried in a long one) and orders by rank, ties newest first. `truncated` is true when more than 2,000 matched. `sort=recent` and a query of only filters are newest first, take no more than the page can reach, and never say `truncated`. **Paging:** `limit` defaults to 20 and is clamped to 1 to 50; `offset` above 200 is `invalid_request` ("a search can page at most 200 results in; narrow it with in: or from:"); the page is cut at the 200th result, so `offset=150, limit=50` returns 50 with `has_more` false and `offset=200` returns an empty page with `has_more` false (a client that has 200 results tells the person to narrow the search). `has_more` is exact within the reach.

**One hit per message.** A message whose text matches the whole query is a `Message` hit. A message whose text does not match but one of its files' names does is an `Attachment` hit for the first such file (lowest position); the dedup is done in the query, with `NOT (search_vector @@ query)` on the file branch and `DISTINCT ON (message_id)` among a message's files, so a message is never listed twice and the cap counts messages. A query must be satisfied by the text, or by one file's name; terms are not combined across the two, and an exclusion applies to the thing being matched. File names are indexed with punctuation turned into spaces, so `report` finds `Quarterly_Report-v2.pdf` (the text-search parser would keep that whole as a file-name token); its snippet is the name with the words that start with a query word marked.

**Details for the page only.** The messages are loaded with `messages_by_ids` (the history machinery: reactions, files, thread summaries, in one query each for the whole page) and the conversations with `conversations_by_ids` (participants of direct and group conversations in one query), so a hit's message equals what `GET /v1/messages/{id}` returns (a test compares them), with no per-hit queries. The snippet of a text hit is `ts_headline` (one fragment of 8 to 24 words around the match) with the match marked by two control characters (any already in the text are replaced first), which the server turns into ranges **in characters** (Unicode scalar values of the snippet's own text, after the markers are removed, so it stays consistent however the headline trimmed and for emoji, combining marks and CJK; tests check offsets that would differ in bytes). A prefix of a longer word marks the whole word. A filters-only hit has the first 24 words of the text and no highlights.

**Scripts.** The `simple` configuration lowercases and splits on the parser's word boundaries and does nothing else: no stemming, **no accent folding** (`cafe` does not find `café`, and `caf` finds both), a run of CJK characters is one word (a prefix finds it, a substring in the middle does not), an emoji is not a word (a query that is only emoji is "nothing to search for"), right-to-left text is searched and highlighted in logical order.

**Failure.** The statement timeout (SQLSTATE `57014`) is mapped to `ErrorCode::Unavailable` (503) with "that search took too long; narrow it with in: or from:". `SearchOptions` (kept apart from `ServerOptions` like the attachment options) holds the limit, `rank_candidates`, and a test hook that sleeps in the database under the limit so a test can make a search slow.

**Migration 0011 on a large table.** Adding a stored generated column rewrites `messages` and holds an `ACCESS EXCLUSIVE` lock for the duration, which is acceptable now and noted for a very large deployment. Measured on a scratch database of 1,000,000 messages (471 MB of table, 83,333 files): the column and rewrite **6.8 s**, the GIN index **2.6 s**, the file-name column and the other four indexes **0.8 s** together, **about 11 s in all**; the table and its indexes went from 703 MB to 970 MB (heap 471 to 678 MB, the GIN index 53 MB on a deliberately small 5,000-word vocabulary, so a real corpus is larger, `messages_seq_idx` 21 MB, `messages_author_idx` 38 MB, `messages_created_idx` 21 MB, the file-name index 4.7 MB).

**Measured plans.** The database is `tests/fixtures/search_perf_seed.sql`: one workspace, 300 people, 200 channels (40 public, 160 private), 1,000,000 messages (skewed over the channels, 6 to 19 words from a 5,000-word vocabulary drawn Zipf-like, plus: "the" in 60% of messages, "deploy" in 5%, "deployment" 2%, "dependency" 1%, "plan" 1%, "rollback" in about 200, "rollback plan" in about 200, "kubernetes" in about 100), 2% of them deleted, and 83,333 files (every twelfth message; half PNG, a quarter JPEG, a quarter PDF; every file named `…_report.…`). The harness is `tests/search_plans.rs` (ignored; `LAZY_SEARCH_PERF_DB=… cargo test --release -p lazy-server --test search_plans -- --ignored --nocapture`); it runs `EXPLAIN (ANALYZE, BUFFERS)` of the candidate statement for three callers: a **typical** one (15 conversations), one in **10 public and 150 private** conversations, and a **new member** in a single public channel. Times are the database's execution time in ms, **first run / median of the next three**, with everything in the buffer cache or the operating system's (a disk-cold run was not possible without root: unverified); the work is in Postgres, so a debug and a release build of the server give the same figures here.

## Notifications, status and the thread inbox

`PUT /v1/workspaces/{w}/notification-settings`, `PUT /v1/conversations/{c}/notification-prefs`, `PUT /v1/workspaces/{w}/status`, `GET /v1/workspaces/{w}/inbox`, `POST /v1/workspaces/{w}/inbox/read` (`notifications.rs`; D20, protocol 11). **The server stores and syncs preferences and status and serves the inbox; it decides nothing about who a message notifies and stores nothing per recipient.** That is `lazy_domain::notification::decide`, evaluated by each client for what it receives live (and by a push worker later), so a message to a large channel writes nothing for its members.

**Settings.** The request body is the `NotificationSettings` value itself, replaced whole; the answer is `NotificationSettingsResponse`. A non-member is `not_found`. Quiet hours must satisfy `QuietHours::is_valid` and `dnd_until` may be at most 366 days ahead (`invalid_request`); a `dnd_until` already past is **accepted and stored as given**: it means no snooze (`is_paused` compares it with the time), and storing it unchanged keeps a repeated request identical whatever the time (normalising it to "none" would make a retry after the snooze ended look like a change). Under an advisory lock for (person, workspace) the value is compared with what is in force (the stored row, or the defaults when there is none): equal means nothing is committed and no event is appended; settings equal to the defaults delete the row; otherwise it is written and `NotificationSettingsChanged` goes to the person alone (`Audience::User`, no conversation) in the same transaction. The lock makes six devices sending the same settings at once one change and one event, and makes two devices sending different settings at once leave the last write with both events in the order they were written. The bootstrap carries the settings (the defaults if none are stored).

**Conversation preferences.** The caller must be able to read the conversation (a member, or any workspace member for a public channel, archived or not; anything else is the conversation's ordinary `not_found`), under the conversation's shared lock so that a removal (which holds it exclusively and deletes the row) cannot interleave. `level` and `muted` that both say nothing delete the row and still answer with the default preference; otherwise one `INSERT … ON CONFLICT DO UPDATE … WHERE (level, muted) IS DISTINCT FROM …` writes only if something differs, and returns a row only then, so a repeat commits nothing and appends no event, with no lock of its own. `ConversationNotificationPrefsChanged` goes to the person alone **with no conversation on the event** (the preference names its conversation): an event with a conversation would be filtered out for someone who is not in it, and a person who only reads a public channel must still hear of their own change on their other devices. A preference is deleted when its person leaves or is removed from the conversation (with their read and thread state, in `remove_member`); nothing is announced for that, since the removal itself is, and rejoining starts from the defaults. The bootstrap carries the preferences that exist for conversations the person can read (the ones they are in and public channels), so a stale row for a private conversation they are no longer in is never served.

**Status.** `StatusResponse { user }` is the caller as others see them. A non-member is `not_found`, a bot `forbidden`; a text, emoji or end that `UserStatus` refuses fails in the request's own deserialization, which the existing mapping answers as `invalid_request` (400, a test asserts the code, not 500). An end already past is `invalid_request`; a custom emoji must be live in this workspace (`emoji::check_reaction`, under a share lock on its row so a deletion and a use take turns). The end is truncated to the microsecond the database stores, so a repeat of the same request is the same status and the answer and the event carry what is stored. Under an advisory lock, what is in force (an expired row counts as none) is compared with the request: equal commits nothing; clearing an expired row removes it quietly; otherwise the row is written or deleted and `UserStatusChanged` goes to the whole workspace (a stored `workspace` audience, like groups and emoji), so it replays for a returning subscriber. **An expiry is never announced:** a status past `expires_at` is simply not served (the bootstrap's members join `user_status` with `expires_at IS NULL OR expires_at > now()`, the database clock at the snapshot's start), and clients also compare. A newly registered member's `MemberJoined` carries no status, and the top-level `user` of a bootstrap has none (status is per workspace: read it from `members`).

**Inbox.** `GET` lists the caller's followed threads (`thread_user_state.following`) in conversations of the workspace they are still in, most recent activity first (`threads.last_reply_seq`, then root id), paged by `before` (a last-reply position; two threads never share one in a workspace, so the cursor loses and repeats nothing), `limit` 20 by default and 1 to 50, and `unread=true` keeps threads with a reply from someone else, not deleted, past the person's read position. A deleted root that still has replies is in the list as a tombstone (`root.deleted`, with its summary); a root with no replies left has no `threads` row and is not; an unfollowed thread, and every thread of a conversation the person left or was removed from (their state rows went with them), are not. Each `InboxEntry` is built from the batch loaders history uses: the root and the newest reply that still exists (`messages_by_ids`: reactions, files, thread summary, one query each for the page), the conversation (`conversations_by_ids`, participants of direct and group conversations in one query), and the person's `ThreadUserState` with unread and mention counts from the same lateral count the bootstrap uses. A fixed number of queries serves a page, not some per entry. The statement chooses the page first, from the thread summaries and the person's state alone, **walking `threads_activity_idx` from the newest and probing the person's state for each**, and only then counts replies for the page's threads; the unread variant adds a cheap `EXISTS` for the filter. Two literal statements (never built from input), unprepared, so the plan is made for the cursor it gets. It runs in one `REPEATABLE READ` read-only transaction, like the bootstrap and search, so a page is one consistent view.

**Mark all read.** `POST` takes the caller's followed threads with unread replies (the same test, most recently active first), at most 500 (`FOR UPDATE OF` their state rows, so a removal in flight waits and then finds them gone), sets each one's read position to the newest reply it had when chosen (a reply that arrives meanwhile stays unread) in one `UPDATE … FROM unnest`, and appends a `ThreadStateChanged` for each to the caller alone, in the same transaction, answering how many. Ask again for more. It does not take the per-thread conversation and root locks that `mark_read` does (it does not need to: it only moves positions forward to values that existed, under row locks of its own).

**One transaction's events in one statement.** Announcing 500 threads one event at a time cost three round trips each (reserve, insert, notify): 120 to 160 ms. `events::append_all` now sends batches of more than three events through `append_batch`: one `UPDATE … event_head = event_head + n` reserves the positions, one `INSERT … SELECT FROM unnest(…)` writes the rows, one `NOTIFY` follows. The rows are the ones appending one by one would write, in the same order, with consecutive positions (a test asserts it); every other caller (one to three events) is unchanged.

**Measured.** On a database of 60,000 threads (a root and three replies each, 240,000 messages) in 40 channels where the person follows 20,000 of them, half read and half unread (`tests/fixtures/inbox_perf_seed.sql`, `tests/inbox_perf.rs`, ignored; whole calls from Rust, a debug test binary, so the figures include the database round trips and the batch loaders), milliseconds, first call / median of the next four:

| Request | First design (counts for every followed thread, then sort) | As built |
| --- | --- | --- |
| first page (20) | 179 / 71 | 10 / 4.3 |
| first page, 50 | 72 / 70 | 8 / 7.5 |
| unread only, first page | 59 / 58 | 5.5 / 5.0 |
| deep page, the middle of the history | 38 / 38 | 4.7 / 4.3 |
| deep page, unread only | 38 / 39 | 5.2 / 5.4 |
| deep page near the oldest | 15 / 15 | 4.9 / 3.9 |
| deep page near the oldest, unread only | 15 / 15 | 12 / 9.9 |
| mark all read, 500 threads | 130 / 137 / 166 | 31 / 31 / 30 |

The first design counted replies for all 20,000 followed threads and sorted before cutting the page, so every page cost the same as the first (and a shallower cursor cost more). The index walk reads about three threads per followed one (64 index entries for 22 followed threads, 0.8 ms in the database), so the cost no longer depends on how many threads the person follows. The 500-thread read is 31 ms with the events batched (it was 117 to 166 with them one at a time).

## Discovery

`GET /v1/workspaces/{w}/channels/browse`, `GET /v1/workspaces/{w}/people`, `GET /v1/workspaces/{w}/people/{user}`, `PUT /v1/messages/{m}/saved`, `GET /v1/workspaces/{w}/saved`, and the bootstrap's `saved` (`conversations::browse_channels` and `discovery.rs`; D21, protocol 12). All of them need the caller to be a member of the workspace (`not_found` otherwise, the same answer as for a workspace that does not exist).

**What the directories share.** `query` is a case-insensitive substring match done with `strpos(lower(x), lower($query))`, so `%`, `_` and `\` in it are ordinary characters (no `LIKE` pattern is ever built, so there is nothing to escape wrongly); surrounding blanks are trimmed and a blank query is no filter; a NUL, which text cannot hold, is replaced by a space; more than 100 characters, an `offset` above 100,000, or a non-numeric number is `invalid_request`. `limit` is clamped to `1..=100` (default 50), as the inbox does. A page fetches one row more than it returns to know `has_more`, and ties are broken by a final unique column, so paging neither repeats nor skips. The statements are literal (the two sorts of the channel directory are two literal strings), unprepared (`persistent(false)`), so a plan is made for the values it gets.

**Channel directory.** Only public channels of the workspace, as before: a private channel or a direct or group conversation is never listed, even to its members. `query` matches the name, the topic or the description; `joined` keeps only joined or only not joined channels; archived channels are left out unless `include_archived`; `sort` is `name` (the default) or `members`, most first, then name, then id. `joined` comes from a left join on the caller's membership row (a primary-key probe per channel).

**People.** A page is the workspace's members that are not integration bots, ordered by `lower(display_name)`, `username`, `id` (so "adam" and "Adam" sort together, then by username), each as a `Person`: the `User` with its status as it stands now (an ended one is not served), the workspace role and when they joined. `query` matches the display name or the username. `GET .../people/{user}` returns one `Person`, a bot included (its `user.is_bot` is set); a user who is not in the workspace is `not_found`, and so is a caller who is not.

**Saved messages.** `PUT` saves or removes one for the caller. The message's conversation is loaded for the caller as reading the message loads it (a workspace member who is in the conversation, or it is a public channel); anything else, and no such message, is the message's own `not_found`, and a test compares save, `GET /v1/messages/{id}` and search for every person and message of an access matrix (member of a private channel, a non-member, a public channel not joined, a direct conversation's non-participant, a stranger to the workspace). It runs under the conversation's shared lock and the message row `FOR SHARE`, so a removal from the conversation or a deletion cannot interleave. A **deleted message cannot be saved** (`not_found`: D21 does not say which error; the message is gone for the purpose, and a client does not offer it) **but can be removed**. Saving is `INSERT … ON CONFLICT DO NOTHING RETURNING 1`: it commits and announces only if a row was added, so saving what is saved keeps its place and announces nothing, and a second device saving the same message waits for the first and adds nothing; removing is a `DELETE` that announces only if it removed a row. A real change appends `SavedChanged` to the caller alone in the same transaction, **with no conversation on the event** (it names the message; with one it would be filtered out for someone who only reads a public channel, as for notification preferences). Six saves at once are one event; saves and removals racing leave one state with events that alternate and end in it.

**The list** (`GET .../saved?before=&limit=`) walks `saved_messages_list_idx` from the newest and joins the message (not deleted), its conversation (in this workspace) and the readable test (public channel, or a membership row), so an item that is deleted or unreadable is skipped inside the limit and a page holds `limit` eligible items; it comes back, with the same cursor, when the caller can read it again. `before` is the `cursor` (the `saved_order`) of the last item seen; a cursor beyond a bigint is "everything". The messages and conversations of the page are loaded with `messages_by_ids` and `conversations_by_ids` (reactions, files, thread summary in one query each), so a page costs a fixed number of queries; it runs in one `REPEATABLE READ` transaction. The **bootstrap** carries the same statement with a limit of 2,000 (`SAVED_BOOTSTRAP_LIMIT`), as ids only, per workspace: deleted and unreadable messages take no place, so the cap is filled from older ones. A message saved before the newest 2,000 reads as not saved in its conversation until the list has been paged to it, which D21 accepts.

**Measured.** On a database of one workspace with 20,000 people, 5,050 channels (5,000 public, one in 25 archived; 50 private the person is not in), 100,000 messages and 50,000 saved messages for one person (a sixth of them in private channels they cannot read), by `tests/discovery_perf.rs` (ignored, `LAZY_DISCOVERY_PERF_DB`, seeded by `tests/fixtures/discovery_perf_seed.sql`), whole calls from a debug test binary, milliseconds, first call / median of the next four:

## Workspace administration

`PATCH /v1/workspaces/{w}`, `PUT /v1/workspaces/{w}/people/{u}/role`, `PUT /v1/workspaces/{w}/people/{u}/deactivated`, `POST` and `GET /v1/workspaces/{w}/invitations`, `DELETE /v1/invitations/{i}`, and registration with an invitation code (`admin.rs`, `access.rs`, `accounts::register`; D22, protocol 13). The role and deactivation endpoints answer `PersonResponse` (the person as the directory shows them), which the protocol does not name: it is the natural answer for a client that updates a loaded `Person`.

**Locking.** Every change that must hold under races takes the workspace row `FOR UPDATE`, the row the event log's positions also lock (D3), **and reads the roles it decides on afterwards**: a role change, a deactivation, a settings change, and creating an invitation (so the limit of 100 is exact). So two owners demoting each other at once leave one (the second finds themself a member and is `forbidden`), two owners demoting themselves leave one (`conflict`), and an owner and an admin cannot both lock each other out. Changes are announced only when something changed, in the transaction that made them.

**Settings.** `PATCH` changes the name (`WorkspaceName`, validated by the request's own deserialization: `invalid_request`) and/or the settings (`registration`, `channel_creation`); admins and owners only (`forbidden` for a member, `not_found` for a stranger). Asking for what already is commits nothing and appends nothing; a change appends `WorkspaceUpdated` (the whole workspace). The channel policy is enforced when a channel is created (`forbidden`; direct and group conversations are unaffected), before the operation receipt is looked at, so a member who can no longer create channels is refused even on a retry. The bootstrap carries the settings per workspace.

**Roles.** `check_role_change` decides, with the active owners besides the target counted in the transaction (a deactivated owner does not count as one that remains): `forbidden` ("you cannot change this person's role") or `conflict` ("a workspace needs at least one owner"). Setting the role someone has commits nothing. A deactivated person's role can be set. An app (a webhook's bot) has no role (`invalid_request`). `MemberRoleChanged` goes to the whole workspace, the person included.

**Deactivation.** `check_member_action` decides (`forbidden`; nobody deactivates themself, so the last owner stays; reactivating is held to the same rule); an app cannot be deactivated (`invalid_request`). `deactivated_at` is set or cleared; their session, messages, role, profile and conversation memberships (and the member counts that include them) are untouched. `MemberDeactivated` goes to the workspace; the person's own subscription ends on the batch that carries it (their membership no longer counts), with an `error` frame (`forbidden`, "you are no longer a member of that workspace"), and a new subscription, from the start or from a cursor, is refused the same way. The WebSocket itself stays open for a person's other workspaces: "their live connections to it end" is the subscription to it. Reactivation is announced to the others; the person learns from their next bootstrap and subscribes again.

**One predicate.** `access::active_member!("alias")` is the SQL condition and `access::active_role` / `require_member` the code; every place that lets a request through because the person is in the workspace uses one of them: `accounts::workspace_role` (used by search, emoji, groups, browsing, creating channels, and the subscription), `conversations::load` (the left join that gives `workspace_role`, hence every message, thread, reaction, attachment, favorite, read, member and webhook-management request), `events::visibility` (replay and live delivery), the bootstrap (a workspace the person is deactivated in leaves it), discovery and notifications (`require_member`: people, profiles, saved, the inbox, settings, preferences, status), and the SQL that validates who may be added to a channel, opened a conversation with, or put in a group. Three places that look at memberships do not use it on purpose and say so: the directory and the bootstrap's `members` show deactivated people flagged; a mention of someone in the workspace is valid whatever their state (it simply reaches no one: the final recipient query joins the active memberships, for named people and for group members alike); and the invitation, role and deactivation code finds a membership in any state. Two places found by auditing every use of `workspace_members` and every `conversation_members` read that had been deciding by something else: `GET /v1/operations/{id}` reported what an operation produced to its maker without looking at the workspace at all (it now answers `not_found` for a deactivated person), and a pending upload could be downloaded by its uploader on their own say (it now needs an active membership). A test asks the same 45 questions as a deactivated person and as a stranger, in every family of endpoint, and requires the same status and error code for each; a mutation run removes the check from each family.

**What is left out for a deactivated person, and what stays.** They are left out of mention resolution (the mention stays plain text, notifies no one, and a group's expansion skips them), of adding to channels, opening direct conversations and putting in groups (`invalid_request`), and of the people directory unless an admin or owner asks (`include_deactivated`; anyone else is `forbidden`). A profile for them still resolves, flagged, for everyone, so old messages keep their author's name. Existing direct conversations with them remain and others can still write in them. Webhooks keep delivering: a webhook is not a person.

**Invitations.** `POST` (admins and owners) takes `expires_in_secs` (1 hour to 30 days, default 7 days) and `max_uses` (1 to 1,000 or unlimited), `invalid_request` otherwise; at most 100 are active (`limit_reached`). The code is 192 bits from the system RNG as 32 URL-safe characters; **only its SHA-256 is stored** and the response that creates the invitation is the only time it is shown; `InviteCode`'s `Debug` is redacted and no error message holds one. `GET` lists those created in the last 30 days or still active, newest first (at most 1,000), each with its state worked out by the database's clock (revoked first, then used up, then expired, else active). `DELETE` revokes; revoking a revoked one returns it unchanged; a stranger or an unknown id is `not_found`, a member `forbidden`.

**Registering with a code.** The server's `open_registration` option still closes registration altogether (codes included). With a code: its shape is checked first (`invite_code_is_wellformed`), after the password has been hashed so that a malformed code costs what a wrong one does; the invitation's workspace is looked up by hash; the registration advisory lock for that workspace is taken (as for every registration); then **one guarded `UPDATE … SET uses = uses + 1 WHERE code_hash = $1 AND revoked_at IS NULL AND expires_at > now() AND (max_uses IS NULL OR uses < max_uses)`** counts the use under the invitation's row lock: of two registrations on a one-use code the second waits, finds it used up, and fails. The account is created in the same transaction (so a registration that fails afterwards, with a username taken, gives the use back), joins as a member and joins the workspace's default channel, and `MemberJoined` is announced. A wrong, unknown, malformed, expired, revoked or used-up code is `invitation_invalid` with the same message in every case and creates nothing. Without a code, registration joins the default workspace if its policy is `open`, and is `forbidden` ("registration is by invitation") when `invite_only`.

## Several workspaces, profiles and avatars

`PUT /v1/workspaces/{w}`, `POST /v1/invitations/accept`, `PATCH /v1/me`, `PUT` and `DELETE /v1/me/avatar`, `GET /v1/users/{u}/avatar` (`workspaces.rs`, `profile.rs`; D23, protocol 14). A person belongs to any number of workspaces; the bootstrap lists them (oldest first), each with its own log, members, conversations and settings. **Nothing is shared between workspaces except the person**: every read joins through `workspace_members` of the workspace asked about, every event is appended to one workspace's log, and a subscription is to one workspace. A test family builds three workspaces that share people only in part and asks, as a person in two of them, for everything of the third (bootstrap, search, history, a message, people, a profile, the inbox, a file, an emoji, an invitation, a picture) and, as a subscriber of one, for events of the others, requiring "not found" or silence.

**Creating.** `PUT /v1/workspaces/{w}` with `{name}` (`WorkspaceName`), the id chosen by the client, in one transaction under the person's lock (below): the server's `open_workspace_creation` option off is `forbidden`; an id that exists is looked at first: the **same person, same name, still an active member** gets the workspace back (200, the same body), and anything else (another person's, the seeded one, the same person with another name, a creator who has since been deactivated) is one `conflict` with one message, so nothing is said about other people's workspaces; otherwise the creator's workspaces are counted (`created_by`, ten, `limit_reached`, exact because creating takes the person's lock) and the workspace is inserted (`db::insert_workspace`, also used by the seed: default settings, `#general` as the default channel), the creator is its **owner** and joins `#general`. The insert is `ON CONFLICT DO NOTHING`, so two people choosing one id at once leave one workspace and one `conflict`. No event is appended (nobody else is there); the answer is `JoinedWorkspace`, built after the commit by `bootstrap::joined_workspace` in its own `REPEATABLE READ` snapshot, so its `head` is a position to subscribe after.

**Which workspace registration joins.** Without an invitation, the oldest workspace **with no creator** (`created_by IS NULL`): the seeded one. A workspace a person made is never where an open registration lands, even if the seeded one is gone or younger (a test deletes it and checks that registration is refused).

**Accepting.** `POST /v1/invitations/accept` for a signed-in account, in one transaction: the code's shape (`invite_code_is_wellformed`) and its hash are looked up as registration does, and a code of the wrong shape, unknown, revoked, expired and used up are the one `invitation_invalid`. Then, before anything is used: someone who already belongs (active) is returned the workspace with **no use consumed and no event**, and someone whose membership is deactivated is `forbidden`. Otherwise the same guarded `UPDATE … SET uses = uses + 1 …` as registration counts the use, the person joins as a member and joins `#general`, and `accounts::announce_member` appends `MemberJoined` and `MemberAdded` (the function registration uses too, so the two cannot drift). **Deviation from the contract's wording:** the contract said "under the workspace row lock"; the use is counted under the **invitation's** row lock instead, and the workspace row is taken last, by the append. Registration with a code locks in the order invitation row, then workspace row, and `workspace_members`-first would have made an accept and a registration on one invitation able to deadlock (a test runs them against each other for three rounds and requires no server error). Of many people on a one-use code the second waits on the invitation row, finds it used up and fails, as with registration.

**The person's lock.** `profile::lock_person` is a transaction-scoped advisory lock keyed by the person. Creating a workspace, accepting an invitation and changing a profile each take it **first**. That serializes a person's own requests of those kinds, which makes the creation limit exact and a repeated accept idempotent, and, more importantly, fixes the set of workspaces the person belongs to while a profile change fans out: a workspace they join at that moment either commits first (and is announced to, or read with the new profile in its member list) or waits for the change (and reads the new profile), so a workspace never keeps the old profile forever. Nothing takes it in another order, and it is never taken while a workspace row is held.

**A profile change** (`PATCH /v1/me` with `display_name`; `PUT` and `DELETE /v1/me/avatar`), in one transaction: the person's lock, the person's `users` row (the update takes `FOR NO KEY UPDATE`, which does not block the foreign-key checks of their messages and makes setting a status, which reads the row `FOR SHARE` so its answer carries the current profile, take turns with it), then **each workspace the person has a membership of, in id order**: take the workspace row (`lock_workspace`), check that the membership is still active under that lock, and append one `UserProfileChanged` (audience: the whole workspace). Every other transaction takes at most one workspace row at a time, or this order, so two people changing profiles at once with workspaces in common cannot deadlock (a test runs two people changing profiles, a status and a picture in turn while a third creates workspaces and invites both, and then checks that every workspace's log ends with each person's final profile). Deactivated memberships are skipped (the person is not active there, so nothing is said to them or about them; the others in that workspace learn the person's current profile from their next bootstrap, and a reactivated person's stays as it was until one: see Known limits). A change that changes nothing (the same name, no field, the same picture, removing none) commits and announces nothing. Apps (webhook bots) have no profile: the functions refuse them (`forbidden`), though an app cannot sign in to reach them.

**Making an avatar.** The body is the raw image; the `Content-Type` is ignored (the format is found from the bytes: PNG, JPEG, GIF or WebP; anything else, empty or garbled is `unsupported_media`). A declared `Content-Length` over `MAX_AVATAR_UPLOAD_BYTES` (5 MiB) is `payload_too_large` before a byte is read; without one the body is read in chunks and cut off with the same error as soon as it would pass the limit, so at most the limit is held. Decoding runs on the blocking pool behind the attachments' `thumbnail_slots` semaphore, with the attachments' bound of 64 megapixels checked from the header (a pixel bomb is refused for the price of its header) and the camera's orientation applied (`decode_upright`, shared with thumbnails and emoji); the first frame of a GIF or WebP; the largest centred square is cut and scaled to exactly 256 by 256 (`AVATAR_SIZE_PX`; a smaller picture is enlarged) and written as an RGBA PNG. The original is never kept. The same picture again is no change (the stored PNG is compared in the database); a different one gets the **next version number**, and a removed picture's row keeps its number with the PNG set to NULL, so a number is never used twice for one person and a cached `?v=` address cannot show a picture other than the one it was cached for.

**Serving it.** `GET /v1/users/{u}/avatar[?v=n]` answers a PNG to the person themself (even with no active workspace) and to anyone who shares an **active** workspace with them (`active_member!` on both sides, so a deactivated viewer sees nothing through that workspace and a deactivated person is not seen through it). No such person, an app, no picture and a stranger are the same `not_found`, and the picture served is always the person's **current** one, never anyone else's (the version and the bytes come from one statement). With `?v=` equal to the current version the answer is `private, max-age=31536000, immutable`; with a stale or missing `v` it is `private, no-cache` (the client revalidates and learns the new version from the profile event); `ETag` is the version, and a matching `If-None-Match` is a 304. **Deviation from the contract's wording:** the contract said `Cache-Control: public`; the answers are `private`, like emoji and attachments, because the resource is authorized per viewer and a shared cache (a reverse proxy in front of the server) would otherwise serve a picture to someone who may not see it. A desktop client does not notice the difference. Also served with `nosniff` and a `default-src 'none'; sandbox` policy.

## Logging

`logging.rs`, D24; no wire change. The server logs structured `tracing` events and **never logs a credential or content**.

**Setup.** `main` parses the command line, then installs the subscriber (`logging::init`) on standard error: `text` lines (colours only on a terminal) or, with `LAZY_LOG_FORMAT=json` (or `--log-format json`), one JSON object per line with `timestamp` (RFC 3339 UTC), `level`, `target`, `message`, `fields` and `spans` (outermost first, each with its `name` and fields; the `request` span carries `request_id`). The JSON layer is written in `logging.rs` rather than taken from `tracing-subscriber`'s `json` feature, which would add `tracing-serde` to the dependency tree. The filter is `LAZY_LOG`, else `RUST_LOG`, else `info,sqlx=warn`; a filter that does not parse falls back to the default and says so. Two things are fixed whatever the filter says: `axum::rejection` is off (at its most verbose level it logs why a body or query was refused, quoting it), and `log` records from other crates are not bridged into the output (only `tracing` events are written). SQLx statement logging is off in the pool (`db::quiet`: both the ordinary and the slow-statement kind), so the one logger that writes statement text cannot write a statement that was built with data in it.

**Startup.** One `starting` line with the effective configuration that is not secret: server and protocol version, bind address, the database as `host:port/name` (no user, password or options), `migrate`, `seed`, `open_registration`, `open_workspace_creation`, `event_retention_days`, `max_db_connections`, `max_attachment_bytes`, and the public URL as `scheme://host:port` (no credentials, path or query); then `database ready` with the newest migration version; then the existing `listening` and shutdown lines. `Config`'s `Debug` shows the same safe account.

**One line per request**, written when it has been answered (message `request`, target `lazy_server::logging`):

| Field | Meaning |
| --- | --- |
| `request_id` | The client's `x-request-id` if it is 1 to 64 characters of `A-Za-z0-9._-`, else a fresh UUID. Echoed in the response's `x-request-id`, in the `request` span (so in every event logged while the request runs, error lines included) |
| `method`, `route` | The method and the **matched route pattern** (`/v1/conversations/{conversation_id}/messages`, `/hooks/{webhook_id}/{secret}`), never the path: a webhook address holds its secret. A request no route matched is `<unmatched>`, whatever its path |
| `status`, `latency_ms` | The response status and the time to produce it (a WebSocket upgrade is logged when the upgrade is answered) |
| `user_id` | The signed-in person's id, when the request authenticated; the id is all that is said about them |
| `bytes_in`, `bytes_out` | The declared `Content-Length` of the request and the size of the response body, where known |
| `error_code` | The error code of a refusal (`not_found`, `invitation_invalid`, ...), never its message |
| `slow` | Took more than one second and moved less than 1 MiB either way |

Level: `info`; `warn` for a 5xx or a slow request; `debug` for `/healthz`. Query strings, bodies and headers (other than `x-request-id`) are not read by the layer at all. The layer also catches a panic in a handler: the connection is not dropped, the client gets a 500 `internal`, and the request line and an `error` line (`request failed`, "a request handler panicked") carry the request id.

**Errors and panics.** An error is logged through `Describe`, which says what *kind* of failure it was and not its text: a refusal as `refused (code)`, a database error as its SQLSTATE and constraint name (`database error (sqlstate P0001, constraint -)`), a connection error by its I/O kind, a join error as "panicked" or "cancelled" (its `Display` quotes the panic's message), a serde error by its category (its text quotes the value that did not fit). The `internal` errors the server's own code makes carry fixed text without data. The panic hook (`install_panic_hook`) logs the thread and the place (`file:line`) and **withholds the message**: the message of a panic can quote what it was working on, and the default hook would print it to standard error outside every filter. Startup and shutdown (in `main.rs` and `app.rs`) show errors whole: a configuration or migration error holds no request data.

**What is never logged.** Passwords, session tokens, invitation codes, webhook secrets and addresses, password hashes and the hashes of tokens, codes and secrets, message and reply text, display names, usernames, topics, descriptions, channel, group, workspace and emoji names, statuses, search queries, file names, file contents, pictures, request and response bodies, query strings, headers, the text of any error from the database or a parser. A person is `user_id`, a workspace `workspace_id`; both are random ids.

**How that is kept true.** `tests/log_audit.rs` reads this crate's source and fails on a `tracing` call that formats with `Debug` (`?`, `:?`), has a field that is not on its reviewed list (adding one means deciding it can never hold a credential or content), logs an `error` that is not `.describe()`d outside startup, or on `println!`, `eprintln!` or `dbg!`. `tests/log_text.rs` and `tests/log_json.rs` run one broad scenario (below) with a capturing subscriber at TRACE for every crate and fail if any of about 70 secret and content strings appears; `tests/log_server.rs` covers startup and a panicking handler.

## Event audiences

Each event stores who may receive it, when it is appended, and both replay and live delivery use that column. It is always evaluated against **current** membership, read from the database after the events were read and once per distinct conversation in a batch (`events::visibility`).

| Audience | Delivered to | Events |
| --- | --- | --- |
| `workspace` | every workspace member | `user_profile_changed` (appended once in the log of **each** workspace the person is an active member of, in the transaction that made the change), `member_joined`, `group_changed`, `group_deleted`, `emoji_changed`, `user_status_changed`, `workspace_updated`, `member_role_changed`, `member_deactivated` (a person it deactivates does not receive their own: their subscription ends first) |
| `members` | the current members of the event's conversation | `message_created`, `message_edited`, `message_deleted`, `reactions_changed`, `thread_changed`, `conversation_created`, `conversation_updated`, `member_added` |
| `members_and_user` | the current members, and the named person even if they are not (or no longer) one | `member_removed` |
| `user` | the named person, and only while they are a member of the event's conversation (when it has one) | `user_state_changed`, `thread_state_changed`, `notification_settings_changed`, `conversation_notification_prefs_changed`, `saved_changed` (the last three have no conversation: the person's own change reaches all their devices, including for a public channel they only read) |

What follows from evaluating at delivery time:

- Someone removed from a conversation receives their own `member_removed` and nothing else about it afterwards, **including events that committed before the removal but were not yet delivered, and events replayed later from an old cursor.** Their stream may or may not contain earlier events that were delivered live before the removal committed; what can never happen is anything after it.
- Someone who joins later receives the conversation's older events when they replay past them (members see the full history). A client already connected does not: it fetches history on `member_added`.
- A `member_added` for a person who has since left is not delivered to them, so a replay never shows a conversation flashing into the sidebar and out again.
- `user_state_changed` is invisible to everyone but its owner, and stops reaching the owner when they leave the conversation.
- Pruning is unaffected: the pruner deletes a prefix regardless of audience.

## The dispatcher

One task tails the log; a second feeds it wake-ups.

- A listener task holds a `LISTEN lazy_events` connection (reconnecting with backoff) and pokes the dispatcher on each notification. Notifications are hints; nothing depends on receiving them.
- The dispatch loop wakes on a poke or every 500 ms. For each workspace that has had a subscriber it reads `events WHERE seq > dispatched ORDER BY seq LIMIT 200`, publishes the page as a `Batch { after, last_seq, events }` on a bounded broadcast channel (256 batches), and advances `dispatched`. It advances only after a successful read, so a database error is simply retried on the next tick.
- A workspace's stream starts at the log head when its first subscriber arrives. Older history is served from the database, not the dispatcher.

Because the log is gapless and commit-ordered, the dispatcher's batches are contiguous: each batch's `after` equals the previous batch's `last_seq`.

## Retention

Without a bound the event log would grow forever, so the server prunes it.

**What is kept.** Events older than the retention window (default 30 days) are deleted, except that the newest 1000 events of every workspace are always kept, however old. `workspaces.event_floor` records the highest position deleted: events `1..=event_floor` no longer exist, and positions stay gapless from `event_floor + 1` to `event_head`. A cursor `after` is replayable if and only if `after >= event_floor`. Anything older cannot be completed from the log, so the subscriber is sent `snapshot_required` with reason `cursor_expired` and bootstraps again.

**The pruner** (`pruner.rs`) is a task the server owns and stops on shutdown, like the dispatcher. It runs once at startup and then every hour (`RetentionPolicy::interval`, shortened in tests). For each workspace it runs bounded transactions of at most 5000 deletions each; one transaction:

1. `SELECT event_head, event_floor ... FOR NO KEY UPDATE`: the lock a writer's position bump takes, so pruning and writing exclude each other. (`FOR UPDATE` would also block the foreign-key checks that inserts make against the row.)
2. Work out the protected top: positions above `event_head - 1000` are never touched.
3. Of the oldest candidates above the current floor, take the newest whose `occurred_at` is outside the window. That position becomes the new floor.
4. `DELETE` every event at or below it, and set `event_floor`. The floor only ever rises, because candidates start above the old one.

A pass that is told to stop finishes its current chunk (a started server always completes at least one chunk of one workspace) and does no more. A database error is logged and the next interval retries.

**Why the ordering guarantees still hold.**

- *Positions are unchanged.* Pruning deletes a prefix; it never renumbers, never assigns a position, and never touches the newest 1000 events, so D3's argument (gapless, commit-ordered, `n + 1` visible implies `n` visible) applies to the surviving range exactly as before.
- *Pruning and writing never interleave.* A writer holds the workspace row lock from its position bump to its commit; the pruner takes the same lock. A prune therefore never sees a half-committed event and a writer never sees a half-pruned log.
- *Readers cannot see a prune half done.* The delete and the floor update commit together. `events::fetch_after` reads the floor and the page of events in **one SQL statement** (a `LEFT JOIN LATERAL`, which also keeps the read an index range scan bounded by `LIMIT`), so it sees the log and floor either both before the prune or both after. If the floor it returns is above the cursor, the read did not cover `(cursor, floor]`, and the caller must not treat the page as contiguous.
- *Replay cannot silently skip.* Every page of a replay checks that. A prune landing between two pages raises the floor above the cursor, so the next page reports `cursor_expired` rather than continuing from after the hole.
- *Live delivery cannot skip either.* The dispatcher reads with the same function. If pruning ever overtakes it (it stalled for longer than the log retains), its next batch starts at the floor instead of claiming contiguity with its old position. A subscriber then sees `batch.after > cursor`, replays, and is told to bootstrap. In normal operation the dispatcher is within one poll interval of the head, far above the floor.
- *What is unaffected.* History pages come from `messages`, bootstrap from the current tables, and operation status from `operation_receipts`, none of which the pruner touches. Receipts keep their current retention (indefinite; see Known limits).

## Realtime connections

`GET /v1/realtime` authenticates the `Authorization: Bearer` header before upgrading. Each `Subscribe` spawns a task owned by the connection (a `JoinSet`), which:

1. confirms workspace membership (otherwise an `error` frame with `forbidden`, and the connection stays open);
2. **subscribes to the broadcast first**;
3. answers a cursor beyond the head with `snapshot_required` (`cursor_ahead`);
4. replays committed events after the cursor from the database in pages, answering `snapshot_required` (`cursor_expired`) if retention has pruned events after the cursor, including between two pages of the same replay;
5. sends `caught_up` with its cursor;
6. drains the broadcast, skipping anything at or before the cursor.

Everything the dispatcher published before step 2 was committed before step 4's reads, so replay covers it; everything after arrives on the broadcast. There are two further guards, both reusing the replay path: a `Lagged` notice from the broadcast, and a batch whose `after` is beyond the cursor, each trigger a replay from the database.

**Delivery is checked on every batch** against each event's stored [audience](#event-audiences) and the viewer's current membership, so no per-connection cache can go stale. Losing membership of a conversation stops its events immediately (and its history on later replays). Losing workspace membership ends the subscription with a `forbidden` error frame.

**Back-pressure.** Each connection has a bounded outbound queue (256 frames). When it fills, the subscription task waits, stops draining its broadcast receiver, and recovers by replaying from the database once it is more than the channel capacity behind. A single socket write that takes longer than 15 seconds closes the connection. A queue that cannot even accept a ping closes it. The server pings every 20 seconds, drops a connection that has been silent for 60 seconds, and ends a connection whose session was revoked (checked on each ping).

Malformed or binary frames get an `error` frame (`invalid_request`) and the connection continues. Client messages are limited to 64 KiB.

## Known limits

- **Write serialization.** Event-producing writes within one workspace serialize on the `event_head` row for the length of their transaction. This is intended (it is what makes positions commit-ordered) and fine at MVP scale. If it becomes a bottleneck, measure first, then consider per-conversation logs with a workspace-level merge.
- **Receipts are kept forever.** They are not pruned with the event log. A retention window and cleanup job are deferred to Phase 6, together with defining how long a client may rely on an operation id.
- **Retention knobs.** The window is configurable (`--event-retention-days`); the "newest 1000 events always kept" floor is a constant (`RetentionPolicy::DEFAULT_KEEP_NEWEST`), not a flag. Pruning removes a prefix, so one old event that precedes a young one is only removed once the young one ages out too (and a backwards clock step can briefly let a slightly-young event go with its prefix).
- **The between-pages race is tested at two levels.** That a prune landing between two replay pages is detected is tested deterministically on `fetch_after` and end to end only statistically (24 subscribers racing a prune); there is no hook to pause a live replay between pages.
- **A very long outage forces a bootstrap.** A client away for longer than the window (or past the newest 1000 events in a busy workspace) gets `cursor_expired`, which is the intended contract, but it makes the window the effective bound on offline reconnect.
- **Lag recovery is untested end to end.** It reuses the replay path that every subscription runs, which is covered, but forcing a real broadcast lag from a test client is not deterministic.
- **No rate limiting** on sign-in or sending.
- **No TLS** (terminate it in front of the server) and the SQLx build has no TLS feature for the database connection; enable one before connecting to a remote database.
- **No workspace administration API.** Channels are managed through the API, but workspace roles are changed only in the database (the tests do so with SQL), there is no invitation flow, and channels cannot be deleted.
- **Replay filters after reading.** A page of 200 log rows is read and then filtered by audience, so a person in few conversations of a busy workspace pages through many events they will not receive. Pushing the audience test into the query (join on membership) is the fix if it matters; correctness does not depend on it.
- **Sends and membership changes wait for each other.** A send holds the conversation row `FOR SHARE`, and joins, leaves, adds, removes, archives and renames hold it exclusively, so a burst of membership changes in one very busy channel briefly queues its sends (and the reverse). That buys the property that nothing is posted after an archive or by someone already removed.
- **A text query over people or channels reads every candidate.** A substring cannot use an index, so a search costs in proportion to the workspace's people (5 to 12 ms over 20,000) or public channels; a deep `offset` skips rows one by one (22 ms at 15,000), bounded by the 100,000 cap. `pg_trgm` would change that and is not assumed.
- **`GET /v1/operations/{id}` for a created conversation** returns the conversation as it is now, not as it was created, and does not re-check that the caller can still see it.
- **Deletion rewrites events.** To make "deleted" mean the text is gone, the delete transaction replaces the message in its earlier `message_created` and `message_edited` events. Copies that already left the server (a client's cache, a subscriber that received the event live, the dispatcher's in-memory batches) are out of its reach, and database backups taken earlier still hold the text.
- **An edit's original result does not survive deletion.** Repeating an edit of a message that was later deleted returns the tombstone. That is the intended trade for erasing the revisions.
- **Revisions are kept without limit** until the message is deleted. There is no cap on edits per message and no rate limit on editing.
- **Attachments live on one machine's disk.** The directory is local to the server process; several server processes would need a shared filesystem (or another `AttachmentStore`, which the schema and the wire already allow). Back the directory up with the database: a restored database whose directory is lost has rows with no files (downloads then log an error and answer `not_found`), and the reverse leaves files the sweep removes after the grace period.
- **A file is stored once per upload, not once per content.** Identical bytes uploaded twice are two files; there is no de-duplication across attachments.
- **Decoding an image costs memory in proportion to its pixels.** The cap is 64 megapixels (256 MB decoded), with four decoded at once (`thumbnail_slots`); the measured costs are above. An animated GIF or WebP has the first frame as its thumbnail.
- **The pending limits count uploads that have run out of time but not yet been cleaned up** (up to an hour), and a send may still attach one in that window.
- **A thumbnail's type is stored with the row** (`thumbnail_type`), and a thumbnail is made for every image the server decodes, even one smaller than the thumbnail size.
- **The cleanup jobs run in every server process.** They claim rows with `SKIP LOCKED`, so several processes do not conflict, but each lists the whole directory in the sweep.
- **Deleted custom emoji stay in the bootstrap forever.** Their rows are kept so old messages can show `:name:`; the 500 limit counts live emoji only, so the list can grow without bound as emoji are made and deleted (each entry is small). A client that wants it shorter needs a retention rule first.
- **A name that was valid can later be a standard shortcode.** Creating and renaming refuse a name that is a standard shortcode of the dataset in use, but a document written earlier still holds the name it was given (its emoji node carries the id and the name), and a dataset update never rewrites it.
- **A custom emoji's image is decoded in full per upload.** At most 4,194,304 pixels (about 16 MB decoded) with the attachments' four decode slots shared, so a burst of emoji uploads and a burst of attachment thumbnails wait for each other.
- **The emoji ETag is the uploaded bytes' hash.** Two emoji made from identical files have the same ETag; that is harmless (a validator is per URL), but it is not a content hash of what is served.
- **Removing a person from a workspace is not reachable through the API,** so the case "an emoji manager removed from the workspace sees nothing more" is tested by deleting the membership row in SQL.
- **Search is words, not substrings or meanings.** The `simple` configuration does no stemming (`deploy` does not find `deployed`; `deplo` does, as a prefix), no synonyms, no accent folding (`cafe` is not `café`), no substring match inside a word (`ploy` does not find `deploy`), and treats a run of CJK characters as one word, so a prefix finds it and a word in the middle of a sentence without spaces does not. A punctuated token is indexed whole and in parts (`foo-bar`, `foo`, `bar`; an address as a host and as its parts), so the parts are found but the order of the whole can surprise.
- **Relevance only sees the newest 2,000 matches.** An old message with the best match for a very common word is not ranked (the response says `truncated`, and a filter or `sort=recent` reaches it); a query can page no further than 200 results in, after which the person narrows it. Both are D19's bounds on cost, not on correctness.
- **A common word costs a walk.** A word in 5% of the messages costs 20 to 45 ms on a million messages (the 2,001 newest matches are read; 60% takes 6 to 10 ms, because they are near the top), and a word in a large share of file names 130 to 300 ms. Nothing makes these cheaper short of a different index (an ordered index over the word, or a materialised per-conversation one); the 3-second limit bounds the worst.
- **The index is not partitioned by workspace.** `messages_seq_idx` and the generated vectors cover every workspace of the database, and positions are per workspace, so with several large workspaces a newest-first walk reads other workspaces' rows and discards them (the access list keeps the result right, not the cost low). Fine for the one-workspace deployment this is built for.
- **Migration 0011 rewrites `messages`.** About 11 seconds per million messages with the table locked (see [Search](#search)), and the table and its indexes grow by about 40%.
- **A snippet is of the plain-text projection.** A quote shows its `> ` prefixes and a list its markers, because that is what is indexed; a file hit's snippet is the name only.
- **Exclusions are prefixes and apply to what is matched.** `-dra` excludes `draft` (so a query being typed excludes more for a moment), and a file-name hit is not removed by an excluded word in its message's text.
- **A search by a person who can see a hit's conversation but whose conversation list changes in the same instant** sees one snapshot (the list and the matches are read together), never a mixture.
- **Settings are one JSON value per person and workspace.** A field added to `NotificationSettings` later needs a serde default, or the rows written before it stop reading; a snooze already over is kept as sent.
- **A status that ended stays in its row** until its person next sets or clears it (nothing sweeps them), and is never announced when it ends: a client that is open when it expires hides it by comparing `expires_at`, a client that is not sees none at its next bootstrap. The top-level `user` of a bootstrap carries no status (it is per workspace: read `members`).
- **A removal drops a preference without an event.** The removal is itself announced, and a client that handles `member_removed` drops the conversation's preference with it; another device that missed it learns at its next bootstrap. A person who only reads a public channel keeps their preference for it until they join and leave.
- **The inbox cursor is a position, and a thread that moves up is not repeated.** Paging with `before` neither skips nor repeats what was below the cursor when the page was read, but a thread that gets a reply between two pages moves above the cursor and is seen at the top on the next refresh, not on the next page.
- **Mark-all-read marks what existed when it chose.** A reply that arrives while it runs stays unread; more than 500 unread threads need another call, and a call that finds more announces up to 500 events at once.
- **Large announcements are batched.** `append_all` sends more than three events through one statement; their `occurred_at` is one timestamp for the batch, not one per event (positions stay consecutive and ordered).
- **Nothing limits how often settings or status are set.** Each change that differs is an event; there is no rate limit.
- **Saved items are a set per person, not per workspace.** A row is looked up by message, and the workspace comes from the message's conversation; a message that cannot be read (removed from the conversation, or deleted) keeps its row and is hidden, so a deleted message's save is never reclaimed (the row is only removed when the person removes it, or the user is deleted). The bootstrap shows the newest 2,000 only; an older save shows as unsaved in its conversation until the list is paged to it.
- **A deleted message cannot be saved, with `not_found`.** D21 says it cannot but not how it fails; the message is treated as gone, as a thread follow is on a deleted root with no replies.
- **A removal from a conversation does not delete saved rows.** Unlike thread state and preferences, saves are kept so the message returns to the list (with its place) if the person is let back; the cost is rows for conversations the person will never read again.
- **Saved `cursor` values have gaps and are not dense.** They come from an identity column (rolled-back saves and removed ones leave gaps); clients treat them only as an order and a cursor.
- **Deactivation ends a subscription, not the socket.** A person's WebSocket stays open for their other workspaces; the subscription to the one they are deactivated in ends with an `error` frame (`forbidden`) when the batch carrying the deactivation reaches it, and a new one is refused. A client that wants the whole connection gone closes it itself on that frame.
- **Profile changes of a deactivated person are not announced to that workspace.** The fan-out reaches the workspaces the person is an active member of, as the contract says; the others in a workspace where they are deactivated keep the old name and picture (the directory shows them flagged) until their next bootstrap, and a person reactivated after changing their profile is shown with the old one by clients that stayed connected. (An event on reactivation would fix it; it was not asked for.)
- **The setup code has no rate limit, like nothing else here.** It is compared in constant time and a random code of 16 or more characters cannot be guessed, but nothing slows guessing at a short, chosen one; use a generated string. While the workspace has no members every registration waits on its registration lock in turn.
- **Only the default workspace has a setup.** It is the oldest workspace with no creator (the seeded one). A server whose seeded workspace was removed has none, and the setup code then does nothing (registration without an invitation is refused, as always).
- **The invite-only first-account exception is new ground, not an old rule.** Before the seed policy existed an invite-only workspace always had an owner, so "invite-only and no members" never occurred; the server now lets the first registrant in, who becomes the owner, because nobody could have invited them. Only a setup code stops a stranger being that person.
- **`--setup-code` on the command line is visible to other users of the machine** (a process listing); the environment variable is the intended way. Neither is written anywhere by the server.
- **The health check speaks plain HTTP only** and counts only a 200 as healthy (a redirect is not); it does not ask the database anything beyond what `/healthz` itself does (nothing).
- **The request line is written when the response is produced, not when its body has been sent.** A slow download is one line with the time to the first byte; a WebSocket upgrade is logged when the upgrade is answered, not when the connection ends. A request that the client abandons before an answer is not logged (the handler is dropped).
- **`slow` is a threshold, not a measure.** One second, and not for transfers of 1 MiB or more; nothing aggregates latencies.
- **A client's `x-request-id` is logged as sent** when it is 1 to 64 plain characters. It is not authenticated and a client can reuse another's; it is for correlating a client's report with the log, not for security. Nothing sensitive is put there by the clients in this repository.
- **A person and a workspace are logged by id, and no address is.** Ids are random and mean nothing outside the database; the client's IP address is not recorded (a reverse proxy has it).
- **Third-party crates are covered by the scenario's traffic, not by an analysis of their code.** The scenario logs at TRACE for everything, and the output (the server's own events, `axum::serve`, and the test client's) holds none of the strings; a request or a dependency version that makes a library log what it was sent would be caught only if the scenario sends such a thing. `log` records are not written at all.
- **Panics outside a handler** (a background task, a blocking job) are reported by the hook as a place and, where a task is joined, as "the task panicked"; the request that started one has already been answered.
- **A profile change holds each workspace's row until it commits.** It appends in each workspace in turn inside one transaction, so the first workspace's writers wait for the whole fan-out: about 20 ms for a person in 51 workspaces (debug build, measured), growing in proportion to the number of workspaces.
- **Creating workspaces is a budget, not a count of live ones.** There is no way to delete a workspace, so the ten a person may create are never given back, and the creator who is later demoted or leaves still counts.
- **Avatars are rows in Postgres** (a 256 by 256 PNG, usually a few KB, at most a few hundred KB for noise), served from the database on each request that is not a 304; the client is expected to cache by version. A decoded upload costs up to 256 MB (the 64-megapixel bound) while it is decoded, sharing the four thumbnail slots.
- **The workspace id is the client's to choose.** A person who learns another's workspace id can only be told `conflict` for it, which confirms the id exists; ids are random 122-bit values.
- **A used-up or expired invitation is still a member's way back in.** A member presenting any code of a workspace they belong to is handed the workspace whatever the code's state (nothing is used); only non-members get `invitation_invalid` for it.
- **Registrations into one workspace take turns.** The registration advisory lock is per workspace.
- **A used code can be probed only by guessing 192 bits.** Failures are all one answer, but they are not rate-limited (nothing in the server is).
- **Invitation listings are capped at the newest 1,000** (the protocol has no paging for them); a workspace with more invitations in 30 days than that hides the oldest. Used-up and expired invitations stay as rows forever.
- **A profile of a deactivated person is public to the workspace** (flagged), because their old messages are; their status is also served on it until it expires.
- **Role changes need the target's membership row, so a person who left the workspace has nothing to change.** There is no way to remove a person from a workspace in 3F (deactivation is the tool); removing one by SQL leaves their conversation memberships, which no longer give access.
- **A deactivated owner is not an owner that remains,** so a workspace whose only other owners are deactivated cannot demote its last active one; reactivating the others lifts that.
- **Webhook rate limits are per webhook and per process.** The bucket is in memory (it resets on restart and is not shared by several server processes), a channel can have ten webhooks and a workspace any number of channels, and nothing limits a workspace's total or an address by caller (there is no per-IP limit on the public path either; guessing costs a lookup and a hash, and the secret has 256 bits).
- **A lost webhook address cannot be recovered, and creation has no operation id.** If the response is lost the webhook exists, with a visible bot, until an admin lists and deletes it.
- **The address is a bearer credential in a URL.** The server keeps it out of its own logs and errors; a reverse proxy's access log, a CDN, or a client's history will not. A header credential would avoid that.
- **Revoked bots stay in the member list.** The bot user is kept for its messages' sake and remains a workspace member with `is_bot`; nothing says whether its webhook is still in use, and the channel's `member_count` counts a live bot.
- **A bot's messages cannot be edited** (nobody can edit them), and there is no way to rename a webhook or its bot.
- **Webhooks belong to channels.** A direct or group conversation cannot have one (`invalid_request`).
- **Deleting a webhook that exists in a channel the caller cannot read** is `not_found`, while deleting one that does not exist is `204` for anyone, so a caller who guesses a real id can tell it exists. Ids are random 122-bit values.
- **Replies never move the channel's read position, and the replier's thread position moves without an event.** A person who writes in a thread has not read the channel meanwhile, so their `last_read` for the conversation stays, even for a reply also sent to the channel. Their thread `last_read` moves to their reply, and only their *following* starting is announced (`thread_state_changed`), as a channel send moves its author's position without an event; their other devices infer the position from their own `message_created`.
- **A person's thread state starts only from a reply, a mention, or a choice.** Someone who never followed has no unread tracking for a thread (marking one read stores nothing and answers "read to the newest reply"); unfollowing a thread they had no state for is remembered but is not a change anyone is told about. A person who unfollowed with replies unread keeps appearing in the bootstrap while those are unread.
- **An edit does not follow anyone.** Following starts when a reply is created; a mention added to a reply by an edit changes that person's mention count if they have not read past it, but does not make them follow.
- **Thread state follows the conversation's.** Thread state rows are removed with the conversation state: they are deleted with it when someone is removed or leaves, and re-joining starts fresh.
- **The bootstrap's thread candidates read all of a person's state rows.** The limit is applied before counting, so counting is bounded by 500, but choosing the candidates reads every state row the person has (about 21 ms at 20,000, with the plan joining the whole `threads` table when that is cheaper).
- **Migration 0007 is not online.** It adds columns with defaults (instant), backfills `listed` for deleted messages, adds two `CHECK`s that scan `messages`, and creates two indexes and rebuilds two others without `CONCURRENTLY`, so on a large database it holds locks for as long as those scans take (seconds per million messages). The migration runs once, at start-up.
- **Unread in a huge, never-read channel is still a sequential scan** (62 ms at 1.01 million listed messages), as before threads: the planner is right that most of the table matches.
- **A tombstone has `edited_at` cleared.** Deleting is not an edit, and the earlier edit history is erased with the content.
- **Search** is not implemented, so `plain_text` is only maintained (and emptied on deletion) for the day it is.
- **An edit that adds a mention to an already-read message does not make it unread.** Mention rows carry the message's own position and unread is positional, so the new mention is in the message and in `previous_mentions`/`mentions` but not in anyone's count if they are past it. (Removing a mention does lower the count.)
- **`@channel` is a count for whoever is in the conversation now.** It has no per-person rows, so a person who has read past a message never sees it counted, and one who joins later starts past it; there is no per-person history of who an `@channel` "reached".
- **A group's members are not re-checked against the workspace.** Members must be workspace people when set, but there is no way to remove a person from a workspace today (no workspace administration API), so a group cannot hold someone who left. When removal exists it must delete `user_group_members` rows and announce `group_changed`.
- **A freed handle can be reused.** Deleting (or renaming) a group frees its handle, and a person who registers with it afterwards is then what `@handle` means from then on. Old messages keep naming the group by identity, so they still show the handle as it was written.
- **Receipts of deleted groups remain,** like all receipts (see above).
- **One handle lock per name, 64-bit hashed.** `hashtextextended` collisions would make two unrelated handles wait for each other, never produce a wrong answer.
- **Retrying a send returns the message as it is now,** not as it was acknowledged (an edit or deletion since shows through).
- **A reaction needs posting rights.** Someone who left a channel, or a read-only reader of a public one, can neither react nor withdraw, so reading a public channel without joining gives no way to react. (This follows `MessageFacts::can_react`.)
- **`reactions_as_of` on a tombstone** is the deletion's position, not a reaction position. It is the version of "no reactions", chosen so the highest-version rule needs no special case.
- **An edit's repeated result carries the reactions as they are now**, not as they were: only the words are original, since reactions have their own version.
- **Reactions are listed in full on every message.** A message with 50 emoji and many people lists them all; the server caps kinds (50) but not people per emoji.
- **One dispatcher per server process.** Several server processes work against one database (each tails the same log), but that has not been exercised.
