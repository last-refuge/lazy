# Lazy decisions

Answers to the open decisions in [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md), recorded when made. The wire contract itself lives in the rustdoc of `lazy-protocol`.

## D1. Toolchain and GPUI pin (task 0.1, 0.2)

- Rust `1.99.0`, edition 2024, pinned in `rust-toolchain.toml`.
- GPUI and `gpui_platform` are pinned to Zed revision `e5bdd01cd819d6348ae764e69218adfee3d7edab` in the workspace `Cargo.toml`. Both must always share one revision.
- Zed's workspace `[patch]` entries (`async-task`, `calloop`, `khronos-egl`, and others) are not applied. A window crate built against this revision without them compiled on Linux (Wayland and X11 features) on 2026-10-28. Re-check this on each GPUI upgrade, and on macOS and Windows when those targets are added.
- Desktop targets for the MVP: Linux (Wayland, X11). macOS and Windows follow after the MVP; no Linux-specific code goes into shared crates.

## D2. Sign-in method (task 1.1)

Username and password for the MVP.

- Passwords are 8 to 256 bytes, hashed with Argon2id. Usernames are unique case-insensitively.
- A session is an opaque random 256-bit token. The server stores only its SHA-256 hash, with an expiry (30 days) and a revoked flag. Clients send it as `Authorization: Bearer`.
- Registration is open in development. Registering adds the person to the default workspace and its public channels. Production sign-in (single sign-on or email links) replaces this later without changing the session mechanism.

## D3. Commit-safe ordering (task 1.5)

Each workspace has one durable, gapless event log.

- `workspaces.event_head` holds the last assigned position. Every mutation that produces an event runs `UPDATE workspaces SET event_head = event_head + 1 ... RETURNING event_head` inside its transaction, then inserts the event at that position.
- The row lock taken by the update is held until commit. A transaction that gets position `n + 1` therefore cannot start until the transaction holding `n` has committed or rolled back. Positions are assigned in commit order and rolled-back transactions leave no gap. If event `n + 1` is visible to a reader, event `n` is too.
- This serializes event-producing writes within one workspace, which is acceptable for the MVP. The documented escape hatch if it becomes a bottleneck is per-conversation logs with a workspace-level merge; do not optimize before measuring.
- Timestamps and raw database sequences are never used for ordering.

### Snapshots, subscriptions, replay

- Bootstrap reads `event_head` and the conversation and member lists in one `REPEATABLE READ` read-only transaction, so the snapshot corresponds exactly to `head`.
- A single dispatcher tails each workspace's durable log from the database (woken by `LISTEN/NOTIFY`, with a short polling fallback) and publishes events to bounded in-process broadcast channels. Notifications are only wake-up hints.
- A connection subscribes to the broadcast first, then replays from the database starting after the client's cursor, then drains the broadcast skipping positions it already sent. Everything dispatched before the subscription is committed, so the replay query sees it; everything after arrives by broadcast. No committed event can be skipped.
- A receiver that lags behind the broadcast falls back to replaying from the database from its last sent position.
- Each delivered event is checked against the subscriber's current access. A cursor ahead of the log head yields `snapshot_required`.

## D4. Submission and acknowledgment (task 1.4)

- Operation receipts are keyed by `(user_id, operation_id)` with a hash of the request. The same id with the same payload returns the original result; the same id with a different payload is a `conflict`.
- A send is one transaction: authorization check, receipt, event-position bump, message, event, `pg_notify`. The acknowledgment is sent only after commit.
- Receipt retention: kept indefinitely in the MVP. A retention window with cleanup is deferred (Phase 6).

## D5. Client architecture (tasks 1.7, 1.8)

- `lazy-client-core` is a synchronous, I/O-free state machine: inputs in, effects and read-model changes out. It has no GPUI, Tokio, or filesystem dependency.
- `lazy-client-runtime` executes effects on its own Tokio runtime: HTTP, WebSocket, the encrypted journal and drafts files, and secure storage. Results return to the core as inputs over a channel.
- The core lives in a GPUI entity on the foreground executor; the runtime never touches GPUI.
- A submission is durably journaled (written, flushed, and atomically renamed into place) before its HTTP request is issued.

## D6. Local development database (task 0.4)

`scripts/dev-db.sh` runs a project-local Postgres in `.dev/pgdata` on `127.0.0.1:54329` and never touches the system instance. A second, independent instance (`LAZY_PG_INSTANCE=test`, `.dev/pgdata-test`, port 54330) is used by `scripts/test.sh`, so test runs never share a database or its connection limit with a server someone is running by hand. Server code uses runtime-checked SQLx queries, so building does not require a live database.

## D7. MVP scope

The MVP is the Phase 1 slice: register or sign in, one workspace with one channel (`#general`), composer, durable send with idempotent retry, realtime receive, history paging, reconnect with replay, and a GPUI desktop client. Everything after Phase 1 is out of scope until the MVP is verified.

## D9. Event retention, the content cache, and the cursor invariant (tasks 1.5, 1.7, 1.8)

- The server prunes events older than 30 days (`--event-retention-days`, `0` disables) but always keeps the newest 1,000 per workspace. `workspaces.event_floor` records the highest pruned position; a subscriber whose cursor is below it receives `snapshot_required` with reason `cursor_expired`. See `SERVER.md` for why pruning does not weaken the ordering guarantee.
- The client keeps one encrypted, bounded cache file per profile (`cache.enc`: at most 200 messages per conversation, 50 conversations, 4 MiB). It shows cached history at once on restart and resumes the realtime subscription from the cached cursor.
- **Invariant:** the cursor and the messages it covers are written together in one atomic write, and the cursor never runs ahead of the cached messages. Persisting them separately could silently lose messages after a crash.
- `snapshot_required` (expired or ahead) discards the cache and starts fresh. A corrupt cache is set aside and reported. See `CLIENT.md`.

## D11. Conversations and read state, slice 2A (tasks 2.1, 2.6, 2.7)

The wire types are in `lazy-protocol` (`PROTOCOL_VERSION` 2); the rules are in `lazy-domain::conversation`. Decisions that cut across layers:

**What the sidebar holds.** Bootstrap lists the conversations the caller is a *member* of. Public channels the caller has not joined are found by browsing (`GET .../channels/browse`) and joined explicitly. A new account joins only the default channel (`#general`, `is_default`), not every public channel.

**Who receives which event.** Message events go to a conversation's members only. `MemberAdded` and `MemberRemoved` also go to the person they are about, including a person who was just removed. `UserStateChanged` goes only to its owner. The server stores the audience with each event (workspace, conversation members, or one user) instead of inferring it at delivery time. Replay and live delivery use *current* membership: after removal, nothing further about the conversation reaches the removed person, not even events that committed earlier but had not been delivered. Someone who joins a channel receives its older events when they replay past them; clients ignore events for conversations they do not know yet and fetch history on `MemberAdded`, deduplicating by message id.

**Direct and group conversations.** Two people make a `direct` conversation, three to nine a `group`. Both are private, unnamed, and list their `participants`. Opening is idempotent per exact participant set (`ParticipantSet`). "Adding someone" to a group is opening a *new* group with the larger set: it starts with no history and the old group is untouched. Direct and group conversations cannot be left or archived.

**Channel management** follows `ConversationFacts` (see its tests): any member sets the topic and description and adds people; the creator or an admin renames, archives, unarchives, and removes members; admins can add people to public channels they have not joined but never bypass private channels; nobody leaves, archives, or is removed from the default channel. Archived channels stay readable and cannot be posted to. A name already in use is `name_taken`.

**Read state.** A person's read position in a conversation is a message position (`last_read`, 0 for none). Unread count is messages from *other* people after it. The server computes the baseline in bootstrap. Clients then maintain it incrementally: a message from someone else in a member conversation adds one; a message the person authored moves their read position to that message (the server does the same in the send transaction, without an event); `UserStateChanged` replaces the state (another device read or starred). `MarkRead` only moves forward and is clamped to the conversation's newest message. A client marks a conversation read when it is selected, its window is active, and the newest message is on screen. The timeline shows a "New messages" divider where the read position was when the conversation was opened, and keeps it until the person leaves the conversation.

**Idempotency.** Creating a channel and opening a conversation carry an operation id like sends do, and a lost response is reconciled through the operation status (`conversation_committed`). The other management commands are naturally idempotent (they set a state), so they carry none.

**Favorites** are per person (`ConversationUserState::favorite`) and sync across devices through `UserStateChanged`.

## D12. Message lifecycle and rich text, slice 2B (task 2.2, parts of 2.8)

The wire types are in `lazy-protocol` (`PROTOCOL_VERSION` 3); the rules are in `lazy-domain::message` and `lazy-domain::markdown`.

**Documents.** A message is a `MessageDocument` (version 2; version 1 still reads). Blocks: paragraph, code block (optional language), quote, bulleted list, numbered list. Inline items: text with marks (bold, italic, strike, code), link (with marks, never code), line break. Limits: 100 blocks, 100 items per list, 40,000 bytes of text, 2,048 bytes per address. Links must be `http`, `https`, `mailto`, or `lazy`; anything else is plain text. `plain_text()` projects every block for notifications and search.

**Source syntax.** The composer takes Slack-style text and the editor shows it back: `*bold*`, `_italic_`, `~strike~`, `` `code` ``, `[text](url)`, bare web addresses, fenced code, `> ` quotes, `- ` and `1. ` lists, and backslash-escapes. A marker opens only at the start of a word and closes only at its end, so `snake_case` and `2*3*4` stay plain. Parsing never fails for a reason of syntax; the only errors are the document limits. Parsing is linear in the input (tested against pathological nesting). `to_markdown` writes source that parses back to the same document. A very rare arrangement of adjacent marks and punctuation has no such source (none in 40 million random markup-dense inputs, then one in the next 4 million); its words are written unchanged and only its formatting is lost. The rule: *editing a message never changes its words.*

**Editing.** Only the author edits, and only where they could post (not in an archived channel, not after leaving). An edit carries `base_revision`; if the message has moved on the server answers `stale_revision` (409) and the client fetches the current message and tells the person, rather than overwriting. Edits are submissions like sends: an operation id, journaled before the request, an unknown outcome reconciled through the operation status (`edit_committed`). The same operation id returns its original result even after the revision moved on. An edit that changes nothing commits nothing. A message keeps its position, so editing never reorders a conversation; `edited_at` and `revision` change. The previous revision is kept in `message_revisions` on the server (not sent to clients) until deletion purges it.

A client allows one edit of a message in flight at a time. Further local edits of the same message wait and are sent as one edit on top of the acknowledged revision. If the edit comes back stale, the person's text stays in the editor beside a notice naming the newer version.

**Deleting.** The author deletes their own messages; an admin or owner deletes anyone's in a conversation they can read, including archived ones, but never reaches into a private channel they are not in. Deleting turns the message into a tombstone: same id, author, and position, the fixed placeholder document, `deleted` set, a higher revision, and every earlier revision purged from the server. Deleting is idempotent (the second request returns the tombstone), so it carries no operation id. History and bootstrap leave deleted messages out in this slice (deleted root messages that have replies are kept as tombstones when threads arrive, slice 2D). A conversation's unread count excludes deleted messages; a client that has counted a message as unread stops counting it when the deletion arrives, and only if the message is from someone else and after the person's read position.

**Who receives what.** `MessageEdited` and `MessageDeleted` go to the conversation's members, like the original message, and replay and live delivery use current membership as in D11.

**Permalinks.** `lazy://{workspace}/{conversation}/{message}` names a message without naming a server. "Copy link" puts one on the clipboard; a `lazy://` link in a message opens in the app: select the conversation, then load older history, up to a bounded number of pages, until the message is found, and show it highlighted. A message beyond the bound, or one the person may not read, shows a short notice instead.

**Decisions made while building 2B.**

*Server.* Edit and delete lock the conversation row, then the message row, and take the event position last, so a no-op edit or a repeated delete commits without an event and leaves no gap (D3). Deleting rewrites the deleted message's *earlier* events (`message_created`, `message_edited`) into tombstones (`events.message_id` finds them), so a replay never serves deleted text; positions are untouched. A tombstone has an empty text projection and no `edited_at`. An edit's receipt stores the revision it produced, so a repeat reads it back from the revision table; after deletion that is gone and the tombstone is returned. Any `base_revision` mismatch is `stale_revision`. A failed PATCH is `not_found`, then `forbidden`, then stale, and keeps no receipt. `MarkRead` clamps to the newest message including tombstones.

*Client.* The coalesced (waiting) edit is not journaled; a crash loses only unsent text. A stale edit fetches the message, shows the newer version, and keeps the person's text as a conflict that they can save on top (replacing the other change) or discard. `forbidden` and `not_found` revert the row with a notice. An unknown outcome is asked about and resent with the same operation at most three times, then fails with the journal kept. Text written while an old edit's outcome is unknown waits; if the server has no record of the old one it is dropped and the new edit goes on the same base revision (a late arrival of the old request would be stale, never a lost edit). An unresolved edit whose message is not on screen is re-asked at every catch-up. A delete is retried by the runtime on a lost answer (it is idempotent); the row goes on the answer or the event, and the unread count follows only the event, subtracting only a message that was actually counted (from someone else, after the read position, counted by the baseline or by a live event). `MessageCreated`/`MessageEdited` carrying `deleted=true` never add or change a row and never count as unread. A result with `deleted=true` removes the row and tells the person. A stale send receipt or late answer never downgrades a row to an older revision. Permalinks: a loaded message needs no request; otherwise fetch, select, page up to 10 older pages; "unavailable" when the loaded range covers the position but the row is missing; a public channel the person has not joined gets a join offer and the link opens after joining; no read-only view.

*UI.* The timeline is one tab stop with a roving cursor (arrows, Home/End, Enter opens the actions menu) rather than a stop per message; see D10. Rich text uses the bundled Lilex for code (D8). Editing opens on the message source; the formatting shortcuts (Ctrl+B, Ctrl+I, Ctrl+Shift+X) only help at word boundaries because the parser opens a marker at the start of a word.

## D13. Emoji and reactions, slice 2C-1 (task 2.4)

The wire types are in `lazy-protocol` (`PROTOCOL_VERSION` 4); the dataset and rules are in `lazy-domain::emoji` and `MessageFacts::can_react`.

**Dataset.** Unicode emoji come from the `emojis` crate, pinned in the workspace manifest (0.9.1, Unicode 18 data; licenses MIT OR Apache-2.0 and Unicode-3.0, both already allowed by `deny.toml`). It is static data with no I/O, so shared crates may use it. It supplies CLDR names, GitHub shortcodes, groups, and skin-tone variants. Search keywords are the name's and shortcodes' words; the dataset has no further synonyms, so a search for a word that appears in neither finds nothing. Search ranks an exact shortcode, then a shortcode prefix, then a name prefix, then other word matches, shorter names first. Skin-tone variants are folded under their default in the picker order and chosen with a saved tone preference (a number 0 to 5, `skin_tone_index`).

**Reaction values.** A reaction's emoji is one dataset glyph in its canonical spelling (`ReactionEmoji`), so `❤` and `❤️` are one reaction, and skin tones are different reactions. Anything else is refused while parsing a request. Custom workspace emoji (task 3.2) will be another form of this value.

**State, not deltas.** `PUT /v1/messages/{id}/reactions` sets whether the caller reacted with one emoji. It is idempotent, so like favorites it carries no operation id and is not journaled; asking for what already holds commits nothing and appends no event. Each message lists its reactions (`ReactionSummary`: emoji and the people, oldest reaction first) and carries `reactions_as_of`, the log position of the change that produced them. `ReactionsChanged` carries the complete new list. A client keeps, per message, the reactions with the highest `reactions_as_of` whichever way they arrive (history page, response, event; an event's position is its envelope `seq`), so a history page that was in flight while a reaction changed cannot undo it. Content has its own version (`revision`); the two are independent.

**Rules.** Anyone who could post in the conversation may react to any message in it; archived conversations and deleted messages accept none. A message holds at most 50 different emoji (`MAX_REACTION_KINDS`); adding a 51st is `limit_reached` (422). Deleting a message removes its reactions. A person leaving a channel keeps their past reactions. `ReactionsChanged` goes to the conversation's members and follows the D11 membership rules on replay.

**Shortcodes.** The composer converts `:shortcode:` to the emoji when the text is sent or an edit is saved (`replace_shortcodes`), not inside the parser: only where the shortcode stands alone (not after a letter or digit, so `10:30:45` is untouched), not after a backslash, and not in code. The stored document holds the glyph, so reading back is exact and the markdown round trip is unaffected.

**Local preferences.** The skin tone and the recently used emoji are kept per profile on the person's machine, not synced and not secret; a missing or damaged file silently falls back to defaults.

**Decisions made while building 2C-1.**

*Server.* A tombstone's `reactions_as_of` is the deletion's position, so a client that keeps the highest version ends with none. A repeated edit or an operation-status read returns the message with its *current* reactions. A malformed emoji is `invalid_request` before authorization (as for edits). Someone who can read but not post (a public channel they have not joined, or one they left) can neither react nor withdraw. Reaction events carry `events.message_id`. Fetching the reactions for a page of 100 messages out of 300,000 messages and 90,000 reactions is one query of about 0.1 ms.

*Client.* Reactions are not journaled: they set a state, and repeating them is harmless (the "journal before sending" rule is for requests that are not). The display flips at once and includes the person's own pending change (a new emoji goes last, the person last among its users). One request is in flight per (message, emoji); rapid toggles coalesce to the final wish; a request the held list already satisfies is skipped. An unknown outcome is repeated up to three times after the first attempt, then the display reverts with a notice. After a success the row shows the server's state even if another device changed it meanwhile. A 51st different emoji is refused locally with the same notice as `limit_reached`. An expired session reverts pending changes without retry. Content and reactions are versioned independently when taken from one payload; ties keep what is held; a reaction list for a message that is not loaded is remembered while a history page may be in flight. Emoji preferences live in `emoji-prefs.json` in the profile (plain, versioned; a missing, old, newer, or damaged file reads as defaults and is rewritten on the next save; signing out deletes it like every other local file). Using the picker records a recent emoji; toggling a chip does not.

*UI.* Emoji draw in colour everywhere a message body, chip, picker, menu, tooltip, or input shows them, by shaping each emoji cluster in a bundled Noto Color Emoji (D8). The earlier note that family sequences render badly was a misreading of Noto's grey glyphs. Emoji in channel topics and display names still use the system fallback. The Unicode 18 thumb-sign glyphs are newer than the font, so the picker shows those without skin tones. A bare `❤` without its variation selector stays text, as Unicode specifies. After an edit begun from the composer the keyboard returns to the composer; from the toolbar, menu, or cursor, to the message row. The actions menu for one's own message is: Add reaction…, one toggle per existing reaction, Edit, Delete, Copy link, Copy text. The delete dialog starts on Cancel. Tab stops: the composer, then its emoji button, then Send; the emoji picker traps Tab through search, group tabs, grid, and skin tones.

## D14. Mentions and user groups, slice 2C-2 (task 2.5)

The wire types are in `lazy-protocol` (`PROTOCOL_VERSION` 5); the document, syntax, and handle rules are in `lazy-domain` (`mention`, `document`, `markdown`).

**What can be mentioned.** A person (`@alice`, by username), a user group (`@design-team`), or the whole conversation (`@channel`). `@here` and `@everyone` are reserved and mean nothing yet (`@here` needs presence, task 3.4; `@everyone` would duplicate `@channel`); typed, they stay plain text. A *handle* is 2 to 32 lowercase letters, digits, `.`, `_`, or `-`, starting and ending with a letter or digit. Usernames, group handles, and the reserved handles share one namespace: a group cannot take a username or a reserved word, a new account cannot take a group handle or a reserved word (both checked under a per-handle advisory lock so a registration and a group creation cannot race), and an existing username that happens to be reserved or ends in punctuation simply cannot be mentioned.

**Document and syntax.** `Inline::Mention { target, handle, marks }` holds the target (a person, group, or channel, by identity) and the handle as written, so a renamed or deleted person or group still reads sensibly and still notifies by identity. A document containing a mention is written as version 3; every other document is still written as version 2, so messages without mentions are byte-for-byte what the previous build wrote. At most 50 mentions per message; a mention cannot be code. The composer turns `@name` into a mention through a `MentionDirectory`, which the client builds for the conversation (see below); a name the directory does not resolve stays text, which is also how autocomplete is permission-aware. A mention opens only at the start of a word (so `bob@x.com` is untouched), takes the longest name the directory knows (so `@alice.` ends a sentence and `@alice_` ends an italic span), is not recognized in code, in link text, or after a backslash, and is written back as `@handle` (lowercase). Written source escapes an `@` that could open a mention, so a literal `@alice` round-trips as literal text; editing an old message that contains `@name` text therefore shows `\@name` until the person removes the backslash. The round trip held for 16 million mention-heavy random inputs.

**Who is notified.** The server works it out when a message is committed or edited and returns it on the message as `Mentions { users, channel }`: the people named, plus the members of each group named, limited to people in the conversation and never the author, and `channel` when `@channel` was used (every member, not listed). It is stored with the message, so history and events report what was decided at the time. Naming someone who is not in the conversation notifies no one (and a mention of a person outside the workspace, or of a group that does not exist, is `invalid_request`). `@channel` is open to anyone who can post, except in the default channel (which reaches the whole workspace), where only admins and owners may use it; anyone else gets `forbidden` and the client does not offer it there.

**Counting.** `mention_count` is the number of unread messages (from someone else, after the read position, not deleted) for which `Mentions::includes(me)`. The server computes the baseline. Clients keep it incrementally with the same discipline as the unread count (D11, D12): a message counts when it is created, an edit adds or removes it using the event's `previous_mentions` against the new `mentions`, and a deletion removes it using the event's `had_mentions`, in each case only if it was actually counted. Neither needs the earlier version of the message to be loaded.

**User groups.** A group has a handle, a display name, and a membership of up to 200 people from the workspace; a workspace has up to 100 groups. Only admins and owners create, change, and delete groups. Creating carries an operation id (reconciled through `group_committed`); changing sets the handle, name, and the complete membership; deleting is idempotent. Messages that mentioned a group keep naming it by identity and keep their notified set. `GroupChanged` and `GroupDeleted` go to everyone in the workspace, and groups arrive in the bootstrap. A group notifies its members as they were when the message was sent.

**Autocomplete.** `GET /v1/conversations/{id}/members` returns who is in a conversation, so the composer offers people who can see it: in a private channel or a direct or group conversation only its members; in a public channel its members first, then other workspace members marked as not being in the channel (naming one of them notifies no one). Groups are offered everywhere, and `@channel` where the person may use it.

## D15. Threads, slice 2D (tasks 2.3, 2.6, 2.7; specifies the thread items of 0.6)

The wire types are in `lazy-protocol`; the rules are in `lazy-domain::message` (`MessageFacts::can_reply`).

**Shape.** A thread is a top-level message (the *root*) and its replies, in the same conversation. Threads are flat: a reply to a reply is a reply to the same root, and the client names the root. A reply is an ordinary message in every other way (it can be edited, deleted, reacted to, and mention people) and inherits the conversation's access: whoever can read the conversation can read its threads, and whoever can post can reply. A reply carries `thread_root`; a root that has replies carries a `thread` summary (reply count, the position and time of the latest reply, up to five recent repliers). The summary has its own version, `as_of` (the position of the latest change to the thread), and clients keep the highest one however it arrives, exactly as for reactions (D13).

**Where replies appear.** The conversation's history and bootstrap list top-level messages only, plus replies sent with *also send to channel*. Such a reply is the same message with the same identity and content as in its thread, shown in the channel with a "replied to a thread" header; nothing is copied. Thread history is `GET /v1/messages/{root}/replies`, paged like conversation history. A conversation's unread count and mention count consider only what its history lists (top-level messages and also-in-channel replies); replies are counted by their thread.

**Deleted roots.** Deleting a root that has replies leaves a tombstone: the message keeps its place in the conversation and its thread, shows as deleted with its reply count, and its replies stay readable. When the last reply of a deleted root is deleted the tombstone goes too. Deleting a root without replies removes it as in D12. History and bootstrap therefore list deleted roots that still have replies. Nobody can reply to a deleted root (`not_found`).

**Following and read state.** A person follows a thread when they reply to it, when they started it and someone else replies, when a reply mentions them by name, or when they choose to; they can unfollow. Per person and thread the server keeps `following`, a read position, an unread count (replies from others after it, not deleted), and a mention count (replies that mention them). The bootstrap lists the states of threads the person follows or that have unread replies (the newest 500 by activity). The thread read position only moves forward and is clamped to the thread's newest reply. A client marks a thread read when its pane is open, its window is active, and the newest reply is on screen. Following state, reads, and counts reach the person's other devices through an owner-only `ThreadStateChanged` event. Clients keep unread counts for the threads they hold incrementally, with the counting discipline of D11 and D12 (a reply counts when it is created, edits and deletions adjust only what was counted).

**Notification rules (for task 3.4).** A reply notifies the thread's followers other than its author. Muting a conversation silences its threads; a mention in a reply notifies regardless of following, subject to the person's notification preferences.

**Access.** Membership removal applies to threads exactly as to conversations: events stop, history and thread reads become `not_found`, and replay never delivers a removed member anything further about a thread. A private channel's thread is as invisible to a non-member as the channel.

**Events.** A reply is announced by `MessageCreated` (with `thread_root`) followed by `ThreadChanged` carrying the root's new summary (`None` when no replies remain). Both go to the conversation's members. Deleting a reply announces `MessageDeleted` and `ThreadChanged`.

**Permalinks.** A permalink to a reply opens the thread pane on its root and highlights the reply; the conversation timeline behind it keeps its reading position. Opening a thread never moves the channel's reading position.

**Decisions made while building 2C-2.**

*Server.* `Mentions.users` and `UserGroup.members` are sorted by user id. Named people are still listed when `@channel` is also used. A mention added by an edit to a message the person has already read does not make it unread (a mention's position is its message's own). An edit recomputes group membership as of the edit. A no-op edit does not revalidate mentions. Earlier revisions keep their mentions, so a repeated edit returns the original ones. The mention namespace is global for usernames; registration refuses a handle used by a group in any workspace, and group handles are unique per workspace, case-insensitively. A repeated `create_group` after the group was deleted is a `conflict` and its operation status is `not_found`; deleting a group that does not exist is a success for any signed-in caller; an update that changes nothing appends no event. The conversation members list is in join order, and the client adds the rest of the workspace itself. When a deletion rewrites a message's earlier events into tombstones, only the `message` payload becomes a tombstone: `previous_mentions` on rewritten edit events is kept, and `had_mentions` on the deletion is the mentions of the message's last version (user ids, not content), which is what lets a client that missed the earlier events still subtract the right mentions. `@channel` is stored as a flag next to the stored set so the mention count is an index-only lookup: on 1.2 million messages every count measured under 1 ms except a person with 22,000 mentions (6.7 ms); counting all 101 conversations of one person takes one statement of about 5 ms.

*Client.* A mention is counted with the same tracked state as unread (D11, D12): a baseline-counted message has no entry until an event reveals its state (an edit's `previous_mentions` or the deletion's `had_mentions`), a tombstone-form edit only catches the entry up, and the cache records the tracked mentions and a marker for how far recounting went (older files load). The answer to a mark-read request is no longer used for the count on a timeline that is not complete (it can be ahead of the events and subtract twice); the remainder waits for `UserStateChanged`, and with a complete timeline unread and mentions are recounted from the rows. Member lists are fetched on selecting a conversation, kept current by `MemberAdded` and `MemberRemoved`, buffered while a fetch is in flight, marked stale at catch-up, cleared on `snapshot_required`, and not cached; a channel offers no people until its list arrives, so a name typed in the instant after switching channels, before the list has arrived, stays plain text. Direct and group conversations use their participants. Refusals have specific wording (`@channel` where it is not allowed, an invalid mention), and an edit refused for those reasons keeps its text. Group creation is reconciled like channel creation; update and delete are plain and delete is retried.

*UI.* A message that notifies the person (their name, a group they are in, or `@channel`) tints its row with a bar at the left edge; the person's own messages never do. A mention shows the person's current display name (or the group's name, or `@channel`), and falls back to the handle it was written with. Autocomplete offers up to eight candidates in the core's order, marks people outside the channel, never appears in code, after a letter, or during composition, and floats at the caret in the composer (inline under the text in the editor). Groups are managed from a "User groups…" link in the sidebar footer that only admins and owners see. Primary buttons now show a keyboard focus outline (they had none, in the older dialogs too). The tab stops added are that link, and in the group dialog the list, Close, Delete…, Edit, New group, and in the editor Handle, Name, People search, Cancel, Save; Escape steps back from the editor to the list and from the list closes the dialog. See D10.

**Decisions made while building 2D.**

*Server.* Each message is marked with `thread_root_id`, `in_channel`, and `listed` (whether the conversation's history lists it: top-level messages, in-channel replies, and deleted roots that still have replies). The summary lives in its own `threads` table so a busy thread does not rewrite its root row; the thread state table holds following, an explicit-unfollow flag, and the read position, and unread and mention counts are derived from the replies, never stored. Lock order is the conversation row, the root's message row, the reply or its state rows, and the workspace position last. A reply never moves the channel's read position, not even the author's own reply that was also sent to the channel. A replier's thread position moves to their reply silently (an event only when their following starts). A person pulled in by a mention or as the root's author starts with only that reply unread. Following explicitly with no state starts at the thread's newest reply; unfollowing with no state is remembered silently; marking read with no state stores nothing. Thread commands need conversation membership (readers of a public channel they have not joined get `forbidden`). `@channel` counts in a thread's mention count but does not by itself make anyone follow; the follow triggers are the people the reply names, directly or through a group. Edits follow nobody. A top-level message with no replies has an empty replies page, and a deleted one with no replies is `not_found`; replies to a deleted root or a deleted reply are `not_found`, a reply to a reply is `invalid_request`. The rewritten earlier events of a tombstoned root carry no `thread` summary. Deleting the last reply of a tombstoned root removes the root and purges the followers' state (without an event). Leaving or being removed from a conversation deletes the person's thread state there. Measured on 1.48 million messages (280,000 replies in 50,000 threads, warm cache, debug build): channel history newest 50 in 0.2 ms index-only; a replies page from a 2,000-reply thread 0.09 ms; thread counts for 2,000 unread replies 1.4 ms; the bootstrap thread list for a person following 800 threads 3.2 ms and 20,000 threads about 21 ms.

*Client.* Counts are kept only for threads whose state the client holds. A follow change not yet saved shows a placeholder state with no position (no counts, never cached, dropped if the change ends as "not following"). Only the open thread's replies are held and they are not cached; the root is a separate one-row timeline with the same version rules as any message. An also-in-channel reply appears in the channel only after the server confirms it, and in the pane at once. A root's summary version is its `as_of`; "no replies" has the version of its event; the memory of events that arrived while a page was in flight is cleared whenever a new request starts. A root seen only through its deletion becomes a placeholder row when the loaded range could hold it. Replies sent from a closed pane are parked, and a parked reply of unknown outcome is asked about again at every catch-up (the person could never see its row to retry it); a lost root fetch is retried at catch-up too. A permalink to a reply always opens its thread. A send, reply, or edit whose text contains `@` waits for the conversation's member list (a failed fetch sends it as plain text), and text typed behind a held one waits too, so order is kept. Reply drafts use the existing drafts file through an additive field. Reactions: a client no longer fires an add that would exceed the limit while a removal on the same message is still in flight (see the reactions note below).

*UI.* The thread pane sits to the right of the conversation, with a drag handle (a 1 px line that thickens on hover, drag, and focus; Left/Right resize by 16 px, with Shift by 64 px, Home to the maximum of 720 px, End to the minimum of 320 px) and a width remembered for the session. Below 680 px of space beside the sidebar the pane replaces the conversation and the header shows Back instead of Close; the conversation's scroll position is kept for the way back. Opening or closing a thread never changes the conversation's scroll position. A message with a summary line has two keyboard stops (the message, then its summary line; Enter on the summary opens the thread, Enter on the message opens the menu). Opening a thread from the keyboard moves focus to the reply box, and Escape returns it to where it came from. Inside the pane the stops are the resize handle, Back (narrow only), Follow, Close, the replies (one stop with a roving cursor), the reply box, the also-send checkbox (off for each thread), the emoji button, and Send; the pane comes after the conversation's Send in the tab order. The actions menu for one's own message is now: Add reaction…, one toggle per reaction, Reply in thread, Edit, Delete, Copy link, Copy text (the pane's menu has no Reply in thread, and a tombstone has no menu); the hover toolbar is React, Reply, Edit, Delete, Copy link, Copy. A deleted root shows "This message was deleted" with its reply count and no actions.

## D16. Incoming webhooks and bot identity, slice 2E (task 2.9), and the rest of 2.8

This is a prototype: its job is to show what bot identity, authorization, and rendering need before integrations are built properly in Phase 4. What it showed is recorded at the end of this entry once built.

**Webhooks.** An admin or owner who can read a conversation creates an incoming webhook for it and is shown its address once: `{public-url}/hooks/{id}/{secret}`. The secret is 256 random bits; the server keeps only its SHA-256 hash, compares in constant time, and never logs the path. A wrong secret, an unknown id, and a revoked webhook all answer `not_found` identically. Anything that can send an HTTP `POST` with `{"text": "..."}` posts into that one conversation, and only that one. There is no operation id on creation: if the answer is lost, the admin deletes the webhook that has no address and makes another. At most 10 per conversation.

**The bot.** Each webhook has a bot user (`is_bot`): a workspace member with the role `member`, a generated username (`bot-` and eight characters of the webhook id), and the webhook's name as its display name. It cannot sign in. It joins the conversation when the webhook is created (announced like any member) and is removed when the webhook is deleted; its past messages stay, attributed to it. Clients never offer a bot as a person to message, mention, or put in a group, and show an "APP" badge beside its name.

**Delivery.** A delivery goes through the same send transaction as a person's message, with the bot as the author, so ordering, events, unread counts, replay, edits by nobody, deletion by moderators, and reactions all behave as for any message. The text is parsed as composer source (formatting and `:shortcode:` emoji work); `@names` stay plain text, so a webhook cannot notify people by name. An `Idempotency-Key` header (up to 64 printable ASCII characters) makes a retry post once (the key and the webhook id become the operation id); without one every delivery is a new message. Each webhook is limited to a burst of 30 deliveries and one more per second (`rate_limited` with `Retry-After`), the body to 64 KiB (`payload_too_large`), and an archived conversation is `conflict`. Messages from a webhook cannot be edited (the bot is nobody who can edit); moderators delete them.

**Selection restoration (task 2.8).** The plan item is read as: the app reopens on the conversation the person last had open (per workspace, if they are still in it), and each conversation keeps the caret and selection of its draft, so switching away and back, or restarting, puts the cursor where it was. Timeline text selection is not restored.

**Timeline text selection (task 2.8).** The timeline's text can be selected with the mouse across messages, including ones scrolled out of view, and copied. The selection is a range over the conversation's loaded messages (message and character position), not over what is on screen, so copying includes the rows that are currently scrolled away. Ctrl+A in the timeline selects everything loaded; with the keyboard cursor on a message, Shift+Up and Shift+Down extend by whole messages. Copying a selection that spans messages writes each as its author and time on one line followed by its plain text, separated by a blank line; a selection inside one message copies just the selected text. Escape clears it.

**Empty states and errors (task 2.8).** Every place the app can show nothing, or fail, says what happened and what to do next.

**Decisions made while building the webhook prototype.** The setting is `LAZY_PUBLIC_URL` (command line `--public-url`; default `http://` and the listening address). A bot's username is `bot-` plus the *last* eight hex digits of the webhook id (a version-7 id begins with a timestamp, and the first eight collided within a minute); people cannot register a name of that shape. A bot is a real user row marked `is_bot`, tied to a password hash of `!` by a database check in both directions, and `sessions` has a foreign key that makes a session for a bot impossible; signing in as one fails exactly like a wrong password. The server refuses a bot as a person in a direct or group conversation, as an added channel member, as a group member, and as a mention, and refuses removing one by hand; webhooks belong to channels only. Revoking keeps the row with the secret hash cleared (for audit); deleting a webhook that does not exist is a success for anyone, but deleting one in a channel the caller cannot read is `not_found`. The rate limit sits after address authentication, so guesses never use anyone's allowance, and `Retry-After` is whole seconds rounded up. A retry after revocation is `not_found`, because the address is checked first. The client holds the one-time address in a wrapper whose `Debug` prints `SecretUrl(<redacted>)`, with no `Display` or `Serialize`, and never caches, saves, or logs it. Clients show a bot's name and an "APP" badge but never offer it as a person; a message from a bot cannot be edited by anyone; moderators delete it.

**What the prototype showed (task 2.9).**

*Bot identity.* A bot has to be a real user row, because authors, events, receipts, reactions, and threads all point at a user id; the integration framework in Phase 4 should keep that. The username namespace is shared with people and group handles, so reserving a shape for bots was necessary. Display names are not unique, so two bots can look identical. There is no rename. A revoked bot stays in the workspace member list for good, and nothing on the user says whether its webhook is still in use. A bot counts in `member_count` and in a channel's members list, so any screen that shows "N members" or "who would be notified" includes an integration unless it filters on `is_bot`.

*Authorization.* Only admins and owners who can read the channel may create a webhook, so an admin cannot give a private channel a webhook unless they are in it. The address is a bearer credential: the server redacts its own logs (tower-http's default request span logs the whole URI at debug, so a custom span was needed), but any proxy or CDN in front will log it. Creation has no operation id, so a lost answer leaves a working webhook and a visible bot until an admin lists and deletes it. The scope is exactly the channel, enforced by the bot's membership, so archiving stops delivery and unarchiving resumes it.

*Rendering and behavior.* Almost everything worked because a delivery is an ordinary send: ordering, events, replay, unread counts, reactions, threads, and deletion needed no change. What was awkward: an integration cannot correct a message it sent (no editing); the rate limit is per webhook and per process, so it does not hold across several server processes; a flood competes with people for the workspace's position lock; and a text limit of 40,000 bytes applies inside the 64 KiB body, so texts between the two are `invalid_request`. For Phase 4: give integrations a first-class identity (name, avatar, a way to see what is still in use), let them edit or replace their own messages, and decide whether an integration counts as a member.

**Decisions made while building the rest of 2E.**

*Client.* A client no longer fires an add of a new emoji that would exceed the 50-kind limit while a withdrawal of another kind on the same message is still in flight; it holds the add until the withdrawal returns (a withdrawal makes room only if nobody else uses that kind; an add nothing can make room for is refused locally at once). This removed a race that made a reactions end-to-end test fail about one run in four. Carets are saved as UTF-8 byte offsets, clamped to the text and moved back to a grapheme boundary on read and on save; a caret without a draft is ignored and emptying the draft drops it. The last open conversation is saved on every change (bounded to 50 workspaces), restored only if the person is still a member, and forgotten when they leave it. A bot is refused locally with "Apps can't be messaged." for a new direct message, "Apps join a conversation through their webhook." for adding to a channel, and "Apps can't be members of a group." for groups. The webhook list is loaded on request, not pushed; a lost answer to a create is never repeated (the core says it is not known whether it was created and loads the list), and a delete answered `not_found` counts as done. A bug in 2D was found by the longer simulation: a new snapshot asks again for the open thread's root while an earlier fetch may still be in flight, and the pane tracked it as a flag, so an older answer arriving first left a stale summary; it now counts the fetches in flight and merges every answer.

*UI.* Timeline text selection is a range over the conversation's loaded messages (message index and character offset), not over rendered rows, so copying includes rows scrolled out of view; it works in the thread pane too, with one selection at a time across the timeline, the pane, and the composers. The selection keys apply only while the timeline itself has focus, which is also the guard against acting during composition: Ctrl+A selects every loaded message, Ctrl+C copies the selection (or the cursor message if there is none), Shift+Up and Shift+Down extend by whole messages, Escape clears it (and returns focus to the composer if the selection was made with the mouse), and plain Up, Down, Home, and End clear a keyboard selection. With the mouse: drag selects (auto-scrolling near an edge), double-click selects a word, triple-click a message, Shift+click extends. Copy format: inside one message just the selected text; across messages each as `Author  time` then its text, with a blank line between (a date is added to the time when the first and last messages are on different days); a link copies its text, a mention its pill label, code keeps its newlines, and lists keep their markers. Selection adds no tab stops. The Integrations section of the channel Details dialog, for admins and owners, shows the new webhook's address once in a read-only, selectable field with Copy address and Done; the field is emptied on Done, Escape, closing the dialog by any route, and losing the channel, and is never shown again. New keyboard stops: the Dismiss buttons of the notice and favorite-error banners and the root "Try again" (these were mouse-only), "Try again" on a failed history load, and in Integrations each row's Delete…, Add incoming webhook, the name field with Cancel and Create webhook, the address field with Copy address and Done, and the delete confirmation. The audit of empty and failing states (kept in `tests/states.rs`) covers: no conversations, no channels or direct messages, an empty channel, an empty archived channel, history loading, first-page and older-page failure (both now say what happened and offer Try again), thread failure, webhooks (empty, loading, failed, full), groups empty, browse (loading, empty, failed), an unreachable server at start, an expired session, a lost connection, notices, the archived composer, and the member list not yet loaded while typing `@`.

## D17. Attachments, slice 3A (task 3.1); the storage backend decision

The wire types are in `lazy-protocol` (`PROTOCOL_VERSION` 8); the pure rules (sizes, names, media types) are in `lazy-domain::attachment`.

**Storage backend (decided).** File bytes live on the server's local filesystem behind an `AttachmentStore` trait (put from a stream, get, delete, with the in-memory and filesystem implementations the tests need); Postgres holds the metadata and who may read each file, never the bytes. A different backend (an object store) can replace the implementation later without changing the schema or the wire. The directory is `--attachments-dir` (`LAZY_ATTACHMENTS_DIR`), files are stored at `{dir}/{first two hex digits of the id}/{id}`, and an upload is written to `{dir}/tmp/{id}.part`, flushed to disk, and renamed into place, so a crash never leaves a partial file under a real name. The size limit is `--max-attachment-bytes` (default 25 MiB).

**Upload.** `PUT /v1/conversations/{conversation}/attachments/{attachment}` with the raw bytes as the body, `Content-Type` as declared, and the file name percent-encoded in `x-attachment-name`. The client chooses the id, so a retry is the same upload: the same id with the same bytes returns the existing attachment, and the same id with different bytes is `conflict`. `Content-Length` is required and checked against the limit before any byte is read (`payload_too_large`), and the limit is enforced again while streaming, so a lying header cannot exceed it; the body is streamed to disk with its SHA-256 computed on the way, never buffered whole. Anyone who can post in the conversation may upload for it. An upload is *pending*: visible to its uploader only, and removed after 24 hours unless a message is sent naming it. A person may hold at most 50 pending uploads and 200 MiB of them (`limit_reached`).

**What a file is.** The server decides the media type from the first bytes (`resolve_media_type`): recognised signatures win over the declared type, so a file cannot pass as an image by claiming to be one; an unrecognised file keeps its declared type only if that is well formed and not active content (HTML, SVG and other XML, scripts, stylesheets), otherwise it is `application/octet-stream`. Only raster images (PNG, JPEG, GIF, WebP) are ever shown inline; SVG is a download. File names are sanitised (`sanitize_file_name`: path separators, control characters, directionality overrides, and a leading dot removed; at most 255 bytes). A file recognised as an image is decoded to read its dimensions and make a thumbnail, with a cap of 64 million pixels (a decompression-bomb guard); an image that does not decode is `unsupported_media`. Thumbnails (long side at most 640 px; JPEG at quality 80, or PNG if the image has transparency; the first frame of a GIF) are generated on a blocking thread pool with a bounded number at once, so a burst of uploads cannot starve the server's async threads.

**Attaching.** A message names its attachments in `attachment_ids` (at most 10). They are checked and attached in the same transaction that commits the message: each must be the sender's, for this conversation, pending, and unattached, or nothing is sent. A message that has attachments may have an empty document (`MessageDocument::empty`; its plain text is empty and everything that reads text must cope); a message without them may not. Attachments are immutable: an edit changes the text only, and an edit may empty the text of a message that has attachments. Thread replies and also-in-channel replies can carry attachments like any message. A webhook cannot attach files.

**Download.** `GET /v1/attachments/{id}` and `/thumbnail` require the same access as reading the message's conversation (the uploader alone while pending), and a deleted message's files answer `not_found` at once. Responses carry the stored media type, `Content-Disposition: inline` only for the previewable raster types and `attachment; filename*=UTF-8''...` for everything else, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, an `ETag` of the SHA-256, `Content-Length`, and `Cache-Control: private, max-age=31536000, immutable` (an attachment's bytes never change). Range requests are not supported yet.

**Cleanup.** An hourly job removes pending uploads past their 24 hours, and the files of deleted messages' attachments (rows are marked at deletion, so access ends immediately and the bytes follow within the hour), and a daily sweep removes files that have no row (a crash between rename and commit). Each is reported in the server log by count, never by name.

**Client.** Files for a message are copied into the profile's encrypted `outbox` when chosen, so a restart or a lost connection can finish the upload. The composer shows each file as a chip with its state (reading, uploading with progress, uploaded, failed with retry) and Cancel; up to three upload at once. Sending with files still uploading is allowed: the message is journaled first, appears as pending ("Uploading 2 of 3 files"), uploads (repeating any upload whose outcome is unknown, since the upload is idempotent), and is sent when all are in; a failure is a failed row with Retry, as for any send. Downloads stream to a temporary file beside the destination, are checked against the SHA-256, and are renamed into place; they can be cancelled. Thumbnails are fetched lazily as rows come into view and kept in a bounded (64 MiB) encrypted on-disk cache. Images show a preview in the timeline (fit in 360 by 240) and open in a viewer on click; other files show a chip with an icon, name, size, and Download. Dropping files on the window or the composer, pasting an image or files from the clipboard, and the Attach button all add files.

**Decisions made while building 3A.**

*Server.* The upload is staged to `tmp/{id}.{nonce}.part` (the nonce keeps two uploads of one id from sharing a staging file), checked (type, image decode, thumbnail), and only then, under a per-person and a per-id advisory lock, is the file stored and the row written last: a crash can leave a file with no row (the daily sweep removes it once it is older than a grace period) but never a row with no file. Files named in a send are claimed in the message's own transaction in id order, and any failure sends nothing. A retry of an upload already on a message returns it (200); the same id after deletion or expiry is `conflict`. In a send, a missing, foreign, other-conversation, or deleted file is `not_found` and one already on a message is `invalid_request`. A missing `Content-Length` (or a chunked body) is `invalid_request`. Pending uploads are limited exactly (50 files, 200 MiB) under a per-person lock and also checked early from the declared size. Cleanup deletes files before rows and skips locked rows so it cannot deadlock with sends. Uploads and downloads get a 15-minute timeout (other requests 30 seconds). A thumbnail is made for every decoded image, even small ones. The default directory is `attachments` relative to where the server runs (`scripts/run-server.sh` sets `.dev/attachments`). Measured in a release build on loopback with a warm cache: a 25 MiB upload 22 ms alone and 70 ms each with eight at once, a download 10 to 15 ms, server memory 31 MB idle and 71 MB at peak after eight simultaneous 25 MiB uploads and downloads (so plain files stream), a 12-megapixel image 100 to 130 ms with its decode and thumbnail, and the files query for a history page of 300,000 messages 0.06 ms. Images are the memory cost: a decode at the 64-megapixel cap is about 256 MB, so four at once could reach about 1 GB, and eight 12-megapixel uploads at once peaked at 462 MB. The thumbnail ignores EXIF orientation, so a phone photo can show rotated. New direct dependencies: `image` (PNG, JPEG, GIF, and WebP only), `bytes`, `subtle`, and uuid's `v5` feature; every new crate offers a licence on the allow list.

*Client.* Files are copied into the encrypted outbox and uploaded as soon as they are chosen, not when the message is sent; composer files are not kept across a restart (only the files of sent messages survive, and the runtime deletes any other copy at start). A failed chip blocks the send with a notice instead of sending the rest. A message waiting for its files blocks later messages in its conversation. The journal entry of a send with files is written only when every copy is in the outbox, so it never names a file that is not there; a copy that fails before then fails the row with no journal entry, and a retry copies the file again from its source (retrying a failed message uploads all its files again). The core, not the runtime, repeats an upload of unknown outcome (same id, three attempts). A repeated request for a whole image that failed is a new request (so the viewer's Try again works), while a failed thumbnail is only retried when the connection catches up (rows ask on every draw). Replies to a thread that has ended keep no copies. A tombstone's own file list is ignored. The thumbnails of rows the core no longer holds are not found by a deletion; their cache entries age out of the 64 MiB least-recently-used cache.

*UI.* Dropped files go to the composer under the pointer (the pane's reply box over the pane), with an overlay naming the target; a folder is refused with a message. Pasting an image becomes a file named "Pasted image.png"; pasting a list of files works where GPUI reads it (Wayland and macOS; the X11 backend has that path commented out). Images show a thumbnail fitted within 360 by 240 (narrower in the pane) and animated GIFs show their first frame only. A message's keyboard stops are the message, then each of its files, then its thread summary. Enter on a picture opens the viewer; Enter on a file downloads it (cancels while downloading, retries when failed). The actions menu for a message with exactly one file ends with Download and Copy file name. Copying a selection that includes a message's files writes `[file: name (size)]` lines after its text. The tab order of a composer is the input, Attach, the emoji button, Send; the attachments tray is one stop before the input (Left, Right, Home, End move, Delete or Backspace removes, Enter retries, Escape returns to the input); the viewer's controls are the picture, Previous, Next, Download or Cancel, Copy name, Close. A failed message row has a Discard button after Send again. The timeline holds at most about 192 MiB of decoded pixels and evicts the least recently used.

## D18. Custom emoji, slice 3B (task 3.2)

The wire types are in `lazy-protocol` (`PROTOCOL_VERSION` 9); the name rules, limits, document item, and reaction type are in `lazy-domain` (`emoji`, `document`, `markdown`, `names`).

**What it is.** A workspace has custom emoji: an image and a name. Admins and owners add, rename, and delete them; everyone uses them. A name is 2 to 32 lowercase letters, digits, and underscores, starting and ending with a letter or digit, unique among the workspace's live emoji, and never a standard emoji shortcode (so `:tada:` always means the standard one; `EmojiName` enforces this). A workspace has at most 500 live emoji (`limit_reached`).

**Images.** An upload (`PUT /v1/workspaces/{id}/emoji/{emoji_id}`, raw bytes, name in `x-emoji-name`, the client's own id so a retry is the same upload) must be a PNG, JPEG, GIF, or WebP of at most 512 KiB and 4 million pixels, decoded by the server (`unsupported_media` if it does not decode). The server stores a PNG whose long side is at most 128 pixels (the aspect kept, never enlarged; the first frame of an animated GIF, so custom emoji are not animated yet) in the attachment store (D17) and serves it at `GET /v1/emoji/{id}` to workspace members with the immutable cache headers. The original bytes are not kept.

**Deleting.** Deleting is soft: the emoji stays in the workspace's list with `deleted` set so messages and reactions that used it keep showing `:name:` as muted text; its image is removed by the cleanup job; its name becomes free for a new emoji. A deleted emoji cannot be newly used (a message containing it is `invalid_request`, a reaction with it too), but existing reactions with it can still be withdrawn. Renaming changes how it reads everywhere, because messages and reactions name it by identity.

**In messages.** `:name:` in composer text becomes an inline emoji (`Inline::Emoji`, document version 4) when the composer's directory knows the name; otherwise it stays text. Standard shortcodes are still replaced before parsing, and the two cannot clash. A literal `:name:` in a message is written back with the colon escaped, so editing a message never turns text into an emoji (the same rule that protects `@name`). The server checks that every emoji in a document is live and belongs to the conversation's workspace. A custom emoji counts as one of a message's 50 reaction kinds like any other. The plain-text projection of an emoji is `:name:`, as it was written. A webhook cannot use custom emoji.

**In the client.** The directory that resolves `@names` also resolves `:names:` from the live emoji. Images are fetched lazily as emoji come into view and kept in a bounded (16 MiB) encrypted on-disk cache, with decoded images held in memory by the UI; a failed or missing image shows the muted `:name:` text. The picker lists the workspace's emoji as a Custom group right after Recently used and finds them by name; autocomplete after `:` offers custom emoji before standard ones, with a preview. Recently used emoji can be custom (the preferences file stores `custom:{id}`, and an entry for an emoji that is no longer live is skipped when shown). A custom reaction chip shows the image with the usual count and highlight.

**Admin screen.** Admins and owners see a "Custom emoji…" link in the sidebar footer beside "User groups…". It opens a dialog listing the emoji (image, `:name:`, who added it, Rename, Delete with confirmation) and an Add form (file dialog, name field with live validation against the name rules and the live names, a preview of the 128-pixel result is not possible before upload, so the chosen file's own preview is shown). Errors from the server (name taken, limit reached, unsupported or too large an image) are shown in place.

**Decisions made while building 3B.**

*Server.* Emoji and attachments no longer share a file namespace: both ids are chosen by clients and visible to the workspace, so with one namespace someone could give a file the id of an emoji (or the reverse) and replace the other's bytes. The emoji image is stored as `{dir}/{xx}/{id}.emoji`, a test uploads each with the other's id, and the orphan sweep accounts for a file by a row of its own kind. The `ETag` of an emoji is the SHA-256 of the uploaded bytes, not of the stored PNG. Over the pixel cap is `unsupported_media`, as for attachments. Deleting an unknown id is a quiet `204`, as for webhooks; renaming to the emoji's own name appends no event. Messages and reactions lock the emoji row `FOR SHARE` so a use and a deletion take turns: every use that landed has a log position before the deletion's. An edit checks only the emoji it adds, so an old emoji deleted since does not block editing the rest of a message, but an edit cannot add a dead one. The bootstrap list includes deleted emoji (marked), ordered by name and then id. EXIF orientation is now applied to attachment thumbnails as well (and attachment `width` and `height` are the upright dimensions), which closes a 3A gap. Measured in a release build on loopback, a whole upload request (hash, decode, resize, PNG encode, file write, and transaction) takes 5 to 11 ms for a 512 KiB PNG and about 37 ms for a 4-megapixel JPEG (it is the pixels, not the bytes, that cost), and 38 to 125 ms each with eight at once because four decodes run at a time; resident memory peaked at 134 MB; serving a stored image takes under 2 ms.

*Client.* The emoji list is one flat list across workspaces (like user groups), and `can_manage_emoji` and adding use the primary workspace. The recently used list hides custom emoji that are not live, but the saved file keeps them until newer ones push them out (so an emoji that is briefly unknown is not forgotten); the file version stays 1 and `custom:{id}` strings are additive. A reaction with an emoji the core does not know is refused like a deleted one. A deleted emoji is final in the core: a later "live" event for it is ignored, because the order of an event and an answer is not guaranteed; a rename is applied from whichever arrives. An add has no journal and no outbox: the core repeats an upload of unknown outcome with the same id up to three times, a rename is a single attempt, and the runtime repeats a delete. Emoji images are kept in a second encrypted image cache (`<profile>/emoji/`, 16 MiB) keyed by the emoji id; the core holds at most 600 images (12 MiB), with four fetches at once and 128 queued. The default simulation run stays deterministic (a fixed seed), with its weights rebalanced as new actions were added.

*UI.* An inline custom emoji is a picture about 1.25 line-heights tall (aspect kept, between half and twice as wide as tall), drawn over room reserved with non-breaking spaces measured once at start; each distinct picture is decoded once, off the main thread, and the text is laid out again once per picture that finishes decoding, not on failures or repeats. While loading, on failure, or when deleted or unknown it reads as a muted `:name:`. Emoji inside link text and code stay plain text, because those inlines cannot hold an emoji. Copy and selection write `:name:`. The picker's Custom section comes right after Recently used with its own tab; an empty section says so, and offers "Add custom emoji" only to admins. The admin dialog opens from a "Custom emoji…" footer link beside "User groups…" and has list, Add, Rename, and Delete views (the list is one tab stop; Escape steps back one view); the form's name field is read-only while an upload is in progress, and cancelling during an upload returns to the list without stopping it. Animated images show their first frame only. Scrolling 100 messages with 5 custom emoji each in a debug build averaged 69 ms a step over decoded pictures, about 8% above the same text without pictures.

## D19. Search, slice 3C (task 3.3)

The wire types are in `lazy-protocol` (`PROTOCOL_VERSION` 10); the query language is `lazy_domain::search::SearchQuery`.

**Index.** Postgres full-text search over the plain-text projection, with the `simple` configuration (no stemming and no language assumption, so every script works the same) and no accent folding (the `unaccent` extension is not assumed). `messages.search_vector` is a stored generated column over `plain_text` with a GIN index, so an edit reindexes itself and a deletion (whose text is empty) leaves the index with the same statement; attachment names are indexed the same way. The projection is what people see: `@alice` and `:party_parrot:` are text. Adding the generated column rewrites the `messages` table, which is acceptable now and noted for a very large deployment.

**Query language.** Words (each matches as a prefix, so `deplo` finds `deploy`), `"quoted phrases"` (adjacent words in order), `-excluded`, and the filters `from:alice`, `in:design`, `after:2026-09-01`, `before:2026-10-01` (UTC days), and `has:file` or `has:image`. Values of one filter combine with OR, different filters with AND. A query of only filters lists matches newest first. Anything with a colon that is not a filter (a time, an address) is text. A filter naming someone or a channel that does not exist matches nothing and is not an error. An unusable query (nothing to search for, a bad date, over 200 characters, over 12 words) is `invalid_request` with the reason, and clients check the same rules before asking.

**What a person can find.** Only messages in conversations they are in and in public channels of the workspace (including ones they have not joined: the hit carries the conversation, and opening it offers to join, as a permalink does); never private channels or direct conversations they are not in, never anything after they are removed, never a deleted message (a deleted root with replies is not a result, its replies are), and attachment results obey the same rule through their message. Thread replies are results and carry `thread_root` so the thread opens. Authorization is part of the query, not a filter applied afterward.

**Cost is bounded.** Ranking happens among the newest 2,000 matches (the response says `truncated` when more matched, and the person narrows with a filter); a page is at most 50 results (default 20) and a query can page no further than 200 results in; each search runs with a 3-second statement timeout and answers `unavailable` ("that search took too long; narrow it with in: or from:") rather than holding a connection; snippets are produced only for the page returned. Relevance is the text-search rank, ties broken by newest; `recent` orders by newest.

**Snippets.** The server produces a short excerpt (about 8 to 24 words) around the first match with the matched words marked as character ranges (counted in characters, not bytes, so emoji and CJK text highlight correctly). A file hit's snippet is the file name.

**Client and UI.** Ctrl+F opens search from anywhere (and focuses the field if open); typing searches after a short pause and a newer query discards an older one's answer; Enter searches at once. Results replace the conversation area (the thread pane stays) and show, for each hit, where it is (a channel name or the people of a conversation), who wrote it, when, and the snippet with highlights, with "in thread" for replies and a file icon for file hits; a hit in a channel the person has not joined says "Not joined". The filters the query contains are shown as chips that remove themselves from the text. Up and Down move through the results while the field keeps focus, Enter opens the active hit (selecting the conversation, scrolling to the message and highlighting it, or opening the thread for a reply, as a permalink does), Escape closes search and returns focus. Recent queries (the last 10) are kept on the person's machine and shown when the field is empty. The empty result says what to try; every failure says what happened and what to do; "Show more" pages until the 200-result limit, after which the person is told to narrow the search.



**Decisions made while building 3C.**

*Server.* An offset beyond the 200-result limit is `invalid_request`, and the page is cut at the 200th result (so `offset=150, limit=50` returns 50 with `has_more` false, and `offset=200` an empty page). A message is one hit: a text match wins, otherwise the first matching file by position; the query must be satisfied by the text or by one file's name, not combined across both, and exclusions apply to what is matched. Phrase words and exclusions match as prefixes too. Ranking is `ts_rank_cd` with length normalisation; `recent` and filters-only queries never report `truncated`. `has:image` means the four decoded raster types, so SVG is excluded; `after:` is inclusive and `before:` exclusive, both at UTC midnight; highlight ranges count Unicode scalar values; a filters-only hit shows the first 24 words with no highlights. A timeout (SQLSTATE 57014) becomes `unavailable`. NUL is replaced by a space before parsing. File names are indexed with punctuation turned into spaces, so `report` finds `Quarterly_Report-v2.pdf`. The access list (the conversations the caller can read) is computed in the same snapshot and passed as a parameter, because joining it as a CTE made the planner estimate one row and an `in:` naming a private channel the caller was not in walked the whole table (433 ms for no results); JIT is off for the search transaction and the statement is unprepared (without both, whole requests showed 500 to 900 ms outliers on 3 ms searches that `EXPLAIN` could not reproduce). Measured on 1,000,000 messages in 200 channels (database time, warm cache): a rare word 0.2 to 0.6 ms, a common word (in 60% of messages) 6 to 10 ms, two words about 25 to 49 ms, a phrase 3.5 ms, a prefix of a common word 17 to 38 ms, `from:` only 2 to 6 ms, a date range only 16 to 20 ms, text plus several filters about 20 ms, and a word in 83,333 file names 125 to 306 ms (bounded by the 3-second limit); whole requests in a release build 2 to 43 ms. Migration 0011 took about 11 s on that table (6.8 s for the generated column and table rewrite, 2.6 s for the index) and locks `messages` meanwhile.

*Client.* A run clears the hits and sets `Loading`, so hits always answer the last run even while the typed text is ahead; `LoadMoreSearch` and a resync use the answered run's text and sort, `RunSearch` and `SetSearchSort` the typed text. After a snapshot resync a deletion during the gap is never delivered, so the shown search is re-run from the first page. An edit updates a hit's message (when the revision is newer) but not its snippet; a deletion removes the hit; anything deleted or edited while a request is out is applied to its answer. Recent searches are recorded only when a hit is opened, as the run's text, deduplicated ignoring case (keeping the newest spelling), at most 10 of at most 200 characters, in `recent-searches.json` (plain, versioned, atomic, silently defaulted when damaged, deleted at sign-out). Generations only go up over the session. The workspace searched is the primary one; results are never cached to disk. `unavailable` is a retryable failure for search only ("That search took too long. Narrow it with in: or from:"), and the runtime does not retry a 503 whose body is `unavailable`, since a timed-out search would only time out again. The runtime keeps one search slot: a newer search, a cancel, and sign-out hang up on the one waiting. Someone removed from a private conversation keeps its hits until the next run, and opening one gives the permalink's "can't be read" notice.

*UI.* A "Search  Ctrl+F" entry sits at the top of the sidebar (always visible, even with no conversation); the real field lives in the results header. Ctrl+F works from anywhere in the shell (including with the composer focused) and does nothing while a dialog is up; Escape closes and returns focus to where it was; choosing another conversation ends the search. Typing waits 250 ms (GPUI's own timer, so tests move the clock); Enter searches at once; nothing runs during composition. Highlights are cut into pieces once when results arrive, clamped, and never end inside an emoji, CJK character, or combining sequence; rows have a fixed two-line height so the list never re-measures, and skeleton rows have the same height so nothing jumps. Tab order: the field, the sort control (Left and Right choose), each chip's remove button, the results list (one stop), Show more or Try again, Close. In the field, Up and Down move the active row, PageUp and PageDown move a screenful, Enter opens the active hit (or searches now if none), Escape first clears the active row and then closes, Alt+Home and Alt+End jump to the first and last (Ctrl+Home and Ctrl+End are text-caret actions there and run before key listeners); with the list itself focused, Home and End and Ctrl+Home and Ctrl+End work. Moving to the last row asks for the next page. Opening a hit shows "Looking for the message…" until the conversation, thread, notice, or join offer is there (the core's `opening_link()` says so), then closes search. With an empty field Up and Down choose a recent search; there is no "Clear recent".

## D20. Notifications and attention, slice 3D (task 3.4); where notification decisions are computed

The wire types are in `lazy-protocol` (`PROTOCOL_VERSION` 11); the rules, settings, and status are in `lazy_domain::notification`.

**Where decisions are computed (decided).** By one pure function, `lazy_domain::notification::decide`, from the person's settings, their preference for the conversation, whether they follow the thread, and what the message is (its author, the conversation's kind, whether it is a reply, whether it names the person or uses `@channel`). Clients evaluate it for every message they receive live, to show a desktop notification; a push worker will evaluate the same function on the server for devices that are not connected, when phone clients exist. The server stores and syncs the preferences and a person's status; it does not store a notification per recipient, because one message to a large channel would write a row (or an event) for every member. Keeping the rules in one tested function is what keeps the desktop, the server, and the phone in agreement.

**The rules.** A person's own messages and messages in a muted conversation never notify. The conversation's own level applies, else the workspace's setting for its kind (channels default to mentions, direct and group conversations to all). `nothing` silences everything, mentions and threads included; `mentions` allows being named, `@channel` (if the setting allows), and replies in followed threads (if the setting allows); `all` also notifies every channel message (a reply that was not sent to the channel is not a channel message) and every direct or group message. Being named is the strongest reason, then a followed thread, then `@channel`, then a direct message, then everything else. Pausing, by a snooze (`dnd_until`) or by daily quiet hours (set in the person's own time, with their UTC offset recorded so every device agrees), does not remove a notification: it marks it paused, so nothing pops up but it still counts. Muting a conversation also removes it from badge totals and dims its unread count. Unread and mention counts themselves never depend on any preference.

**Settings and status.** Settings are per person and workspace (`PUT /v1/workspaces/{id}/notification-settings`, replaced whole, in the bootstrap, announced to the person's other devices by an owner-only event); a conversation preference is `PUT /v1/conversations/{id}/notification-prefs` (a level or none, and a mute; resetting both deletes it). A status is up to 100 characters of text, an optional emoji (standard or custom), and an optional end; it travels on the user, is announced to the workspace, and is not announced again when it expires: clients compare the end with the time and hide it. A status already past its end is refused.

**Desktop notifications.** A client notifies only for messages that arrive live after it has caught up (never for replayed history or the burst after a reconnect), never for edits, and never while the window is active and the message is in the conversation (or the open thread) the person is looking at. Notifications are grouped per conversation: a newer one replaces the earlier one, saying how many new messages there are. The title is the conversation (the sender for a direct message) and the body is `Sender: text`, shortened; with "show message text" off it says only who and where. Clicking one raises the window and opens the message as a permalink does. A notification is withdrawn when its conversation is read or its message is deleted. The platform part is a small interface in `lazy-desktop` (Linux: the freedesktop notification service over D-Bus), so macOS and Windows add an implementation without touching the rules.

**Badge.** The attention count is the mentions in unmuted conversations, plus the unread messages of unmuted direct and group conversations, plus the unread replies of followed threads in unmuted conversations. It is shown in the window title ("(3) Lazy") and, where the platform supports it, as the launcher's count. Unread channels without mentions do not add to it (their sidebar bold and count remain).

**Thread inbox.** A "Threads" entry in the sidebar, with the unread count of followed threads, opens a list of the threads the person follows, most recently active first (`GET /v1/workspaces/{id}/inbox`, paged by the position of the latest reply, optionally only those with unread replies): the root's excerpt, the newest reply and who wrote it, the channel, how many replies, and how many are unread. Enter opens the thread in the pane; "Mark all read" marks every followed thread read (at most 500 at a time).

**Where it is set.** A "Preferences…" link in the sidebar footer opens a dialog with Notifications (the defaults for channels and for direct messages, thread replies, `@channel`, desktop notifications, showing text, pause for a while or until tomorrow, quiet hours) and Status (text, emoji, clear after). A bell button in a conversation's header opens that conversation's preference (all messages, only mentions, nothing, mute). A status shows as a small emoji beside the person's name in messages and in people lists, with the text as a tooltip. Theme, reduced motion, and the other settings arrive in task 3.6.

**Decisions made while building 3D.**

*Server.* The settings `PUT` body is the `NotificationSettings` value itself. A `dnd_until` in the past is accepted and stored as given (it means no snooze). Preference events carry no conversation, so someone who only reads a public channel still hears their own change on their other devices. A status end time is truncated to the microsecond the database stores, so a repeated request is the same status; an ended status is served as none and its row stays until the person next sets or clears it; the bootstrap's top-level `user` has no status (read it from `members`). A preference is deleted, with no event of its own, when someone leaves or is removed from the conversation. The inbox is paged by the position of the latest reply, lists tombstoned roots that still have replies and not roots with none left, and the page is chosen first by walking `threads_activity_idx` and probing the person's state, then only that page's threads are counted, so the cost no longer depends on how many threads someone follows; mark-all-read marks what existed when it chose and does not take the per-thread locks `mark_read` takes. `events::append_all` now sends batches of more than three events through one reserve, one insert, and one notify (the rows and positions are the same as before). Measured with one person following 20,000 of 60,000 threads (whole calls from a debug test binary): the first page 179 ms before the redesign and 10 ms after, an unread-only page 59 ms to 5.5 ms, a deep page 38 ms to 4.7 ms, and mark-all-read for 500 threads 130 to 166 ms to about 31 ms.

*Client.* "Mentions me" for the rules is "the person is in `mentions.users`" and `@channel` is `mentions_channel` (the shared `Mentions::includes` counts `@channel` as naming everyone, which would make every `@channel` a mention). `attention_count()` counts a mention inside a direct or group conversation once, as one of its unread messages. A channel notification is titled `#name`, a direct message by the sender, a group by its people; with the text hidden the body is `New message` in a direct message and `Sender: New message` elsewhere; with two or more unseen it reads `3 new messages. Latest: Sender: text`, or just `3 new messages` with text hidden. Paused notifications are not held; they still count in the badge. "Looking at it" means the window is active and the conversation is selected (or the thread is open, for a thread-only reply), and clearing a conversation's notifications also needs the view at the bottom. Settings, preferences, and status are of the primary workspace. Saving is the latest wish with up to three attempts, then a revert with a notice, and is not journaled because the `PUT`s are idempotent. The inbox refreshes by asking for the first page again, quietly (so paging restarts), and shows the core's own thread state because the server announces a thread's state only on follow, unfollow, or read; after a snapshot resync it asks again, because a thread followed during the gap arrives in the bootstrap rather than as an event, and a snapshot request now ends "liveness" so nothing between the request and the next catch-up counts as news. The core is told the time by `Input::Clock` (the runtime sends it before the first frame of a batch whenever more than a second has passed, and every 30 seconds); quiet hours use the event's own time.

*UI and desktop.* The platform notifier is a small trait in `lazy-desktop` with a Linux implementation over D-Bus (`zbus` directly rather than `notify-rust`, because one connection can replace by id, close by id, and hear every action), running on a worker thread; with no session bus it logs once and carries on; a fake notifier records calls for tests. The window title is `Lazy`, `(n) Lazy`, or `(99+) Lazy`, and the launcher count is set through the Unity launcher signal where the dock supports it. The sidebar has a "Threads" entry (unread pill capped at 99+) and a "Preferences…" link; the header has a bell before Favorite (Up and Down move in its menu, Enter chooses, Escape closes); a muted conversation is dimmed in the sidebar with a quiet unread count and the bell shows the muted glyph. The inbox view has an All and Unread toggle, Mark all read, fixed-height rows, and its list starts focused. Preferences covers channel and direct levels, thread replies, `@channel`, desktop, show content, pause (with Resume and the end time), quiet hours (times, days, a read-only UTC offset), and status (100-character counter, emoji picker, Clear after); Escape closes the pause or clear-after menu or the picker first, then the dialog. The status emoji shows beside the author in message rows, in the `@` list and in the people picker, with the text as tooltip; the footer shows your own status and a 🔕 while paused ("paused during your quiet hours" when that is the cause). Not done: the member list in the Details dialog does not show statuses, and a custom-emoji status draws a bullet there and in places without the image cache.


## D21. Discovery, slice 3E (task 3.5): channel directory, people, quick switcher, saved items

The wire types are in `lazy-protocol` (`PROTOCOL_VERSION` 12); the fuzzy matcher the quick switcher uses is `lazy_domain::fuzzy` (written and tested in 3D).

**Channel directory.** `GET /v1/workspaces/{id}/channels/browse` is now queried and paged instead of returning every public channel: `query` (a case-insensitive substring of the name, topic, or description, with `%`, `_`, and `\` matched literally), `joined` (only joined, only not joined, or both), `include_archived` (default no), `sort` (`name`, or `members` with the most first), `offset`, and `limit` (default 50, at most 100), and the response says `has_more`. Ties are broken by name and then id so a page never repeats or skips a channel. A response from a server that predates the paging reads as one page with `has_more` false. Only public channels are listed, as before; a private channel is never discoverable by browsing. The "Browse channels" dialog gains a search box, an All / Not joined filter, a sort control, the member count and topic on each row, "Join" and "Open" buttons, and "Load more".

**People directory and profiles.** `GET /v1/workspaces/{id}/people` pages the workspace's people (not integration bots) by display name, then username, then id, each as a `Person`: the public `User` (with its status unless it has ended), the workspace role, and when they joined. `query` matches the display name or username as the channel query does. `GET .../people/{user_id}` returns one `Person`, bots included (their `user.is_bot` is set); a user who is not in the workspace is `not_found`. The bootstrap still lists every member, so names resolve without a request; the directory exists for roles, join dates, and workspaces too large to scan. A profile shows the name, `@username`, status, role, and "Member since", with a "Message" button that opens (or creates) the direct conversation, and it opens from the people directory, a person's name in the timeline, the quick switcher and the people picker. A "People" entry sits in the sidebar.

**Quick switcher.** Entirely a client feature, with no wire change. Ctrl+K opens it over the window; typing filters, Up and Down move, Enter opens, Escape closes. With no text it lists the conversations the person visited most recently, then those with unread messages, at most 12. With text it fuzzy-matches (`lazy_domain::fuzzy_match`) a channel's name, a direct or group conversation's participants' display names and usernames, and people with no conversation yet (choosing one opens a direct message), plus the fixed destinations "Threads", "Saved", and "Search" when their words match; the score is the fuzzy score plus a bonus for how recently the conversation was visited and a small one for unread. At the end it offers "Browse channels matching ..." which opens the directory with that text. Archived channels the person is in are listed after live ones. The recent list (the last 20 conversation ids visited, per workspace) is a local preference, stored in the profile and not synced between devices; ids that no longer name a conversation are ignored.

**Saved items.** `PUT /v1/messages/{id}/saved` with `{"saved": true|false}` saves or unsaves a message for the caller; it is idempotent (saving what is saved keeps its place in the list and announces nothing; removing what is not saved does nothing), needs the same access as reading the message (otherwise `not_found`; a deleted message cannot be saved but can be removed), and announces an owner-only `SavedChanged` event to the caller's devices. `GET /v1/workspaces/{id}/saved` pages the caller's saved messages, most recently saved first, with `before` as the cursor of the last item seen (a number the server assigns when the message is saved, larger being later; it orders the list and means nothing else, and is not an event position). Items whose message was deleted or whose conversation the caller can no longer read are left out and return if the caller can read them again. The bootstrap carries the newest 2,000 saved ids so rows can show the marker; a message saved before those shows as not saved in its conversation until the saved list has been paged to it, which is accepted. Saving is not journaled: like the favorite flag it is a state `PUT`, the latest wish wins, and repeating it is harmless. The message actions menu gains "Save for later" or "Remove from saved", a saved row shows a bookmark mark beside its time, and a "Saved" entry in the sidebar opens a list like the thread inbox whose rows jump to the message in its conversation.

**Decisions made while building 3E.**

*Server.* Saving a deleted message is `not_found`, but removing a saved one is allowed. Text matching is `strpos(lower(x), lower($q))`, so `%`, `_`, and `\` are literal with no escaping; surrounding blanks are trimmed, a blank query is no filter, and a NUL in the query becomes a space. A page `limit` is clamped to 1 to 100 (default 50), a query over 100 characters or an `offset` over 100,000 is `invalid_request`. Leaving or being removed from a conversation deletes the person's preferences and thread state there but keeps their saved rows, so the message returns to their list, with its cursor, if they are let back in. People are ordered by `lower(display_name)`, then username, then id. Migration 0013 adds `saved_messages` (an identity `saved_order`, cascades on user and message, a listing index `(user_id, saved_order DESC)` and a `(message_id)` index for the cascade) and three directory indexes (public channels by name and by member count, users by `lower(display_name), username, id`). Measured with 20,000 people, 5,050 channels, 100,000 messages, and 50,000 saved messages for one person (whole calls from a debug test binary, first call and median of the next four): the first channel page 4.9 and 0.9 ms by name, 1.3 and 1.0 ms by members; a deep channel page (offset 4,000) 2.8 and 2.5 ms; the first people page 3.5 and 0.8 ms; a deep people page (offset 15,000) 20.9 and 21.8 ms; a people text query 5 to 12 ms; the first saved page 5.7 and 3.1 ms; a saved page from the middle or near the oldest about 3 ms; the 2,000 saved ids of the bootstrap 6.6 ms in the database; the whole bootstrap with its 20,001 members 108.5 ms. Nothing scans a whole table for a first page. There is no `pg_trgm`, so a text query still reads every candidate. Saved events carry no conversation, so someone who only reads a public channel still hears their own save on every device.

*Client.* `BrowseChannels` now means "open the directory with the current settings and load page one"; the directory's state lives on `BrowseView` (`ActionKind::Browse`, `ActionOutcome::Browse`, and `Effect::BrowseChannels` are gone) and `CloseBrowse` forgets the list. A joined or left channel updates the loaded rows without a request. `OpenSaved` and `OpenPeople` ask again when the open list failed and is empty. Saving is optimistic, one idempotent `PUT` carries the latest wish with up to three attempts, and a failure puts back what the server last said with a notice. The open saved list is asked for again when the server says a message is saved (the answer to the `PUT`, or the event) and the list lacks it, not at the person's own flip, because the server may answer the list before it has heard of the save. A username match scores 10 less than a title match, so a conversation named for the text beats a group that merely contains someone with that username. With no text the switcher is not de-duplicated against the open conversation (the most recent entry is usually the one already open; the UI preselects the second row). Recents are kept per profile, because the core knows only its primary workspace.

*UI.* The channel directory stays a dialog; People is a view with its own sidebar entry. The people picker does not open profiles, quick switcher person rows show no status emoji, and Details lists the first 8 members and then "and N more. Find everyone in People." Save for later and View profile are the last two items in the message menu so existing keyboard sequences do not move. Keys: Ctrl+K (Cmd+K on a Mac) opens the switcher from anywhere in the shell, does nothing over another dialog, and closes it from inside; Up and Down wrap, Enter opens, Escape closes and returns the keyboard to where it was. In the directory dialog Left and Right choose the All / Not joined filter and Up and Down move the highlighted row, Enter joining or opening it; row buttons (Join, Open, Remove) are mouse-only. The saved list is one tab stop that starts focused (Up, Down, Page Up, Page Down, Home, End, Enter, and Delete or Backspace to remove). A list's tab stop is the whole body so it exists while loading and when empty, and "Try again" moves the keyboard to a control that stays on screen.


## D22. Workspace administration, slice 3F (task 3.6: invitations, deactivation, roles, workspace settings)

The wire types are in `lazy-protocol` (`PROTOCOL_VERSION` 13); the rules are in `lazy_domain::workspace` (and `WorkspaceRole::can_manage_workspace`). Several workspaces in one window, profile editing and avatars, and appearance settings are slice 3G.

**Who may do what.** Owners and admins manage the workspace: its name and settings, invitations, and members. Role changes follow `check_role_change`: members change nothing; owners set anyone's role to anything, including their own, as long as another owner remains (`conflict`: "a workspace needs at least one owner"); admins move members and admins between those two roles and never touch an owner or make one. Deactivation follows `check_member_action`: owners may deactivate anyone but themself, admins members, members no one, and nobody deactivates themself (so the last owner stays). Everything else answers `forbidden`. The server checks these against the roles it reads under the workspace row lock, so two owners demoting each other at once leave one.

**Workspace settings.** `PATCH /v1/workspaces/{id}` changes the name (`WorkspaceName`: 1 to 64 characters, trimmed, no control characters) and the settings: `registration` (`open`, the default, or `invite_only`) and `channel_creation` (`everyone`, the default, or `admins_only`). A change commits and announces `WorkspaceUpdated` to the whole workspace; asking for what already is changes and announces nothing. The server enforces the channel policy on channel creation (`forbidden`; direct and group conversations are unaffected) and the registration policy when someone registers.

**Invitations.** An invitation has a code the person types, at least 128 bits of randomness in 22 or more URL-safe characters (`invite_code_is_wellformed` says what shape is accepted). The server keeps only a hash of the code and shows the code once, in the response that creates the invitation, so a lost code means revoking that invitation and making another. It is valid from creation until `expires_at` (1 hour to 30 days, default 7 days), up to `max_uses` times (1 to 1,000, or unlimited), unless revoked; a workspace may have 100 active invitations. `GET .../invitations` (admins) lists those created in the last 30 days and those still active, newest first, each with a `state` the server works out (`active`, `expired`, `revoked`, `used_up`); `DELETE /v1/invitations/{id}` revokes, and revoking a revoked one returns it unchanged. Creating is not idempotent and is not journaled: an unknown outcome is reconciled by listing, and an invitation whose code was lost is revoked. Registering with a code creates the account and joins the invitation's workspace as a member and its default channel in one transaction that also counts the use under a row lock (with `max_uses` 1, exactly one of two simultaneous registrations wins); a wrong, expired, revoked, or used-up code is `invitation_invalid` and the same answer in all four cases, and creates nothing. Registering without a code joins the default workspace when its policy is `open`, and is `forbidden` ("registration is by invitation") when `invite_only`. The server's own `open_registration` option still closes registration altogether. Accepting an invitation as an existing account is slice 3G, with several workspaces.

**Deactivation.** A deactivated membership gives no access: the workspace leaves the person's bootstrap, their live connections to it end and cannot resume, and every history read, search, attachment, emoji, group, inbox, saved, people, and realtime request answers as it does for someone who is not a member. Their session stays valid (the account is theirs and may belong to other workspaces). Their messages, role, profile, and conversation memberships stay, but give nothing while deactivated, and reactivating restores everything. They stay in the bootstrap's `members` with `deactivated` set so old messages keep their author's name; they are left out of mention resolution (a mention of them stays plain text and notifies no one), of adding to channels and of opening direct conversations (`invalid_request`), of the people directory unless an admin asks for them (`include_deactivated`), and, on the client, of the `@` list, the people picker, and the quick switcher. Existing direct conversations with them remain and can still be written in. Channel member counts still count them. `MemberDeactivated` goes to everyone else in the workspace; the person's own client learns from the connection ending and the bootstrap that no longer lists the workspace, and shows that they no longer have access.

**Roles in the client.** `MemberRoleChanged` (to everyone in the workspace, the person included) updates the loaded directory and profile and, when it is the signed-in person's own role, what the interface offers at once: the "Workspace settings…" and "Invite people…" links, the admin sections in profiles, and the new-channel button when the policy says admins only. The client uses `lazy_domain::workspace` only to decide what to offer; the server decides.

**Where it is.** "Workspace settings…" and "Invite people…" are links in the sidebar footer for admins and owners. The settings dialog has the name and the two policies; the invitations dialog lists invitations with state, uses, and expiry, creates one (expiry and number of uses), shows the new code once with Copy, and revokes. A profile viewed by an admin or owner has a role control and Deactivate or Reactivate (with a confirmation); the people directory has "Show deactivated" for them. The register form has an optional invitation code.

**Decisions made while building 3F.**

*Server.* Role and deactivation requests answer with a `PersonResponse` (the protocol names no type). Deactivation ends the person's subscription to that workspace, not the whole WebSocket, which stays for their other workspaces; resubscribing is refused from the start, from an old cursor, and from the current head. A single place decides access: `access.rs` (`active_member!` for SQL, `active_role` and `require_member` in code), used by workspace-role lookups, `conversations::load` (so every message, thread, reaction, attachment, and webhook-management request), event visibility for replay and live delivery, the bootstrap, discovery, and notifications. An audit of every `workspace_members` use and every direct `conversation_members` read found two gaps that no endpoint test had covered, now closed: `GET /v1/operations/{id}` told a deactivated person what an operation had produced, and a pending upload could be downloaded by its uploader without a workspace check. One test asks the same 45 requests as a deactivated person and as a stranger across every endpoint family and requires the same status and error code (after checking they differ while the person is active). An invitation's `state` is decided in the order revoked, used up, expired, active. The server option `open_registration=false` closes invitation registration too. A malformed code is refused after the password is hashed and answers like a wrong one. The channel-creation policy is checked before the operation receipt, so a member who may no longer create channels is refused even on a retry. A deactivated person's profile still resolves, flagged, for every member. The invitation list is capped at the newest 1,000 (the protocol has no paging for it). Migration 0014 adds `workspaces.settings`, `workspace_members.deactivated_at`, and `workspace_invitations` (only `code_hash`, unique).

*Client.* `access_lost()` is known only within a run or from a restored cache and is not persisted. A `forbidden` or `not_found` realtime error frame is treated like a snapshot request: full resync, cache discarded, then the bootstrap says whether access is gone; an empty bootstrap leaves the session Ready with no workspace and unsubscribes. `Input::RetryLoad` doubles as "check again" when the session is Ready with no workspace. The role and deactivation outcomes are built from the request, not from the response body. A revoke whose answer was lost reloads the list, as a create does. A deactivated person already in a group stays when the group is edited; only adding one is refused. `SetPeopleIncludeDeactivated` belongs to the open directory and closing forgets it, so it must be sent after `OpenPeople`. `Input::Register` and `SignIn` carry the raw password and code, so the `Debug` text of an `Input` shows them: nothing logs an `Input`, and anything that ever does (the structured logging of task 3.8) must redact them. The `InviteCode` type redacts itself and is never cached or logged; the UI reads it in exactly one place, the invitations dialog's field, and a test reads the UI sources and fails if it is exposed anywhere else.

*UI.* The admin commands (Workspace settings, Invite people, User groups, Custom emoji) first sat in the sidebar's footer, folding into an "Admin" menu in a narrow window; D27 moved them to the Menu's Workspace tab alone. A role chosen in the profile applies at once, with no confirmation of its own. "Create a channel" in the sidebar menu is shown off, with the reason, when the policy says admins only; it is the only new-channel entry point. Deactivating and revoking confirm first, with the safe button (Cancel, Keep) focused; Escape cancels the confirmation before it closes the dialog. The settings dialog follows another admin's change where you have not edited and closes itself if you are demoted. After a successful creation the code is selectable text in a monospace field that ignores typing; closing the dialog drops it. A deactivated person sees "You no longer have access to <workspace>" with Sign out focused, and the shell returns by itself if a later check finds the workspace again. Keys: the Menu's Workspace tab for the admin commands (Up, Down, Enter, Escape); settings: name (Enter saves), who can register, who can create channels (Left and Right choose), Save; invitations: the new code's field, Copy, Done, then Expires in and Uses (Left and Right), Create, each active row's Revoke, Try again; profile: Try again, role (Left and Right set it at once), Deactivate or Reactivate, then Message (or Edit status) and Close, with Message focused on opening; people: search, Show deactivated, Show more or Try again, Close; register: username, display name, password, invitation code, button, link.


## D23. Several workspaces, profiles and avatars, appearance; slice 3G (task 3.6: the rest)

The wire types are in `lazy-protocol` (`PROTOCOL_VERSION` 14). Limits are in `lazy_domain::workspace` (`MAX_WORKSPACES_CREATED`, `MAX_AVATAR_UPLOAD_BYTES`, `AVATAR_SIZE_PX`).

**Several workspaces.** A person may belong to any number of workspaces; the bootstrap already lists them all and the runtime already keeps one realtime connection per workspace. Everything workspace-scoped (members and statuses, user groups, custom emoji, notification settings and preferences, saved messages, the thread inbox, the directory, invitations, search, the quick switcher, workspace settings) follows the **active workspace**, and the core keeps each workspace's own copy so switching loses nothing and a workspace in the background keeps receiving events, counting what needs the person's attention, and notifying under its own settings. A notification from a workspace other than the active one is titled with the workspace's name first. The window title and launcher count are the sum over all workspaces. Which workspace was active is a local preference restored at start (the first workspace if it is gone); each workspace remembers its own selected conversation (as in D8). The **rail** is a slim column at the left edge, always visible: one square per workspace showing its initials, the active one marked, an attention count (the same number as `attention_count()` would be if that workspace were active) or a dot for unread messages that do not need attention, the name as tooltip, and a "+" that opens "Add a workspace". Ctrl+1 to Ctrl+9 (Cmd on a Mac) switch to the n-th workspace. When a workspace stops listing (deactivation, D22), it leaves the rail with a notice and another becomes active; with none left the no-access screen shows.

**Adding a workspace.** `PUT /v1/workspaces/{id}` with a client-chosen id creates one (idempotent; the creator is its owner; at most ten each; the server may switch it off). `POST /v1/invitations/accept` with a code joins an existing one as the signed-in person (the code of a workspace they already belong to returns it without using the invitation; a deactivated member is `forbidden`). Both return the workspace as a `WorkspaceBootstrap`, the client subscribes after its `head` and makes it active. "Add a workspace" offers "Create a workspace" (a name) and "Join with an invitation code".

**Profile and avatar.** `PATCH /v1/me` changes the display name; `PUT /v1/me/avatar` sets the avatar from the picture in the body (PNG, JPEG, WebP, or GIF, up to 5 MiB; decoded within the bounds the attachment previews use, rotated by its orientation, cropped to the centre square, and stored as a 256 by 256 PNG); `DELETE /v1/me/avatar` removes it. `User.avatar_version` is 0 without an avatar and otherwise a number that changes with the picture, and `GET /v1/users/{id}/avatar?v=<version>` returns the PNG to anyone who shares an active workspace with that person (otherwise `not_found`) with a far-future cache lifetime. A change is announced as `UserProfileChanged` in every workspace log the person belongs to. Clients fetch avatars as they fetch custom emoji images (on demand, cached on disk keyed by person and version, decoded off the render path) and draw initials until the picture arrives or when there is none. Avatars appear beside authors in the timeline, in the directory, in profiles, in the Details list, and in the sidebar footer. Preferences gains a Profile section (display name, "Choose picture…", "Remove picture") and an Appearance section.

**Appearance settings.** Theme (follow the system, light, or dark) and reduced motion (follow the system, on, or off) are local to a device, not synced: what suits one display does not suit another. They are kept in the profile directory with the other small preferences, take effect at once, and the choice "follow the system" tracks the operating system's appearance as before. Reduced motion turns off every animation the interface has (the caret blink excepted, which is the platform's) and replaces smooth scrolling to a message with a jump. Notification settings, the third item in the plan's list, were done in D20.

**Decisions made while building 3G.**

*Server.* Migration 0015 adds `users.avatar_version`, a `user_avatars` table, and `workspaces.created_by`. A person's ten-workspace limit counts the workspaces they created, and registration's default workspace is now the oldest one with no creator, so a person-made workspace is never an open-registration target even if the seeded one is gone. The server option `--open-workspace-creation` (default true) switches creation off. Avatar responses carry `Cache-Control: private` (the picture is authorized per viewer, and a shared cache would serve it to people who may not see it), with a long lifetime when `?v=` is the current version; a stale or missing `?v=` gets the current picture with `private, no-cache`; a person can always fetch their own picture, even with no active workspace. The format is detected from the bytes (the Content-Type is a hint only); an oversize body is cut off while streaming; decoding shares the attachment previews' semaphore, 64-megapixel bound, and orientation handling; the stored picture is a centre-cropped 256 by 256 PNG; version numbers are never reused and a removed picture's bytes are deleted. `UserProfileChanged` is appended in every active workspace's log in one transaction, locking the workspace rows in id order (a profile change holds each row until commit: about 20 ms across 51 workspaces, measured on a debug build). An invitation's use is counted under the invitation's row lock before the workspace's, matching registration, so an accept and a registration on one invitation cannot deadlock (a test runs them against each other). A member presenting any code for their own workspace gets the workspace back whatever the code's state, with no use consumed and no event. Profile changes are not announced into a workspace where the person is deactivated: the others there keep the old name until their next bootstrap, and a reactivated person's stale profile stays until then (an event on reactivation would fix it). Mutation run: 46 mutants, 43 caught by failing tests and 2 by hangs, and one survives (a pre-check unreachable through the API); the two person-lock mutants needed tests that hold the lock from another session.

*Client.* The loaded workspace's state lives in the core's ordinary fields and the other workspaces' copies are parked in a `WorkspaceScope`; switching, and applying an event or an answer for a background workspace, swap scopes around the existing handlers, so the old code is unchanged, and `handle` always ends with the loaded scope equal to the active one. `member(id)` is strictly the active workspace's people, while `display_name(id)` names a person from any workspace. `primary_workspace()` stays and means the active entry. The avatar cache holds at most 200 pictures or 24 MiB in the core and a per-version disk cache in the runtime; the version of a person's avatar is looked up in the members of any workspace, the directory pages held, and the loaded profile (`avatar_version(user)`). A notification is titled with the workspace's name first only for a background workspace when the person has several, and clicking it switches to that workspace first. After a restart nothing is notified until the first bootstrap of the run has said what the notification settings are (the cache holds none), a change to the older rule that the single-workspace model in the simulation learned too. Appearance and the active workspace are small versioned files; sign-out removes the active workspace file and keeps `appearance.json`, since appearance belongs to the device. A profile event that arrives in one log before an older one in another shows the older for a moment; the logs converge. The simulation for several workspaces is a second suite with three workspaces of its own (rail invariants: each workspace's rail attention equals what its own `attention_count()` would be if active, and the total is their sum; no state leaks between workspaces); it found three defects (pictures of an older version survived a bootstrap that changed the version; a joined workspace's newer facts about people already known were not applied to the copies elsewhere; and the notification-after-restart case above). 25 mutations, all caught after tests were added.

*UI.* The rail is a 64 px column (48 px below 760 px) that is always visible; its squares show initials, an active bar and ring, a red badge for attention, and a dot for other unread messages, with the name as tooltip and accessible label. After a switch the keyboard goes to the new workspace's composer. Choosing Join in the Add dialog does not move focus. Typed text and refusals are cleared when the dialog closes, and the invitation code is read in two places only (the invitations dialog's field and the add dialog's), enforced by source-count tests. Preferences' Profile section previews the avatar and Appearance applies at once, also on `Input::Started` since the core restores the saved choices there without announcing a change. Avatars are requested only for people on screen, at the version the view was given, and have a fixed size so rows do not jump. Reduced motion: the interface has no animations of its own (scrolls are jumps, the jump highlight is a timed static highlight, the caret blink is the platform's); the setting is wired to GPUI's `reduce_motion`, which holds still animated images and spinners, and since GPUI cannot read the operating system's preference "System" means full motion and the dialog says so. Preferences no longer scrolls on mouse focus: clicking a control at the fold scrolled the dialog between press and release and lost the click (latent since 3D).


## D24. Commands, shortcuts, menus, window state, dialogs, and logging; slices 3H and 3I (tasks 3.7 and 3.8)

No wire change (`PROTOCOL_VERSION` stays 14).

**One command system.** Every action the person can start from more than one place (a button, a shortcut, a menu item, the palette) is a `Command` in one registry in `lazy-ui`: an identifier, a label, an optional shortcut (written per platform: Ctrl on Linux and Windows, Cmd on a Mac), a group (File, Go, View, Workspace, Help), and an availability rule computed from one snapshot of the app (signed in, which view is open, a conversation selected, the person's role and the workspace's policies, a dialog open, the composer focused). Availability is `Enabled`, `Disabled` with a reason shown to the person, or `Hidden`. Buttons, menu items, shortcuts, and palette rows all ask the registry, so a shortcut can never do what the button for it would refuse, and a disabled command says why wherever it is shown. A shortcut never runs while a dialog other than its own is open, while an input method has text in composition, or where it would take a key the focused text field needs for editing. The registry replaces the scattered `on_action` handlers for the existing shortcuts (Ctrl+K, Ctrl+F, Ctrl+1 to 9) without changing them, and adds the ones listed in `llm-docs/TOUR.md`.

**Menus.** The same registry produces the menus: the native menu bar on a Mac, and on Linux and Windows (which GPUI gives no native menu bar) a "Menu" button at the top of the sidebar that opens the same groups in the in-window menu, reachable by keyboard. A "Keyboard shortcuts" dialog (Ctrl+/) lists every command that has one, generated from the registry, so it cannot drift. Typing `>` in the quick switcher lists commands instead of places (fuzzy matched, only the ones available, each with its shortcut); choosing one runs it.

**Window state.** The window's size, whether it is maximized or full screen, and its position where the platform lets an application place its own window (not Wayland) are saved in the profile directory (`window-state.json`, versioned, debounced, damaged or unknown means defaults) and restored; saved bounds that fall outside every connected display, or below the minimum size, are discarded in favour of a centred default. The selected conversation and drafts were already restored (D8).

**Dialogs.** Every dialog is built on the shared modal: opening moves the keyboard inside it, Tab and Shift+Tab cycle within it, Escape dismisses it, and closing returns the keyboard to what had it before when that still exists (otherwise the composer). Escape while an input method has text in composition cancels the composition and does not close the dialog; Enter in a text field commits the composition before it submits anything. One test walks the list of all dialogs and checks these rules for each, so a new dialog cannot skip them.

**Logging.** The server and the desktop client log structured events with `tracing` and never log credentials or content: no passwords, session tokens, invitation codes, webhook secrets, message or reply text, file names, topics, display names, or search queries; requests are logged by method, matched route pattern (never the raw path, which can hold a webhook secret), status, duration, and a request id; the person by id. The `Debug` text of the client's `Input` redacts the password, invitation code, and typed text of the inputs that carry them. `LAZY_LOG` (or `RUST_LOG`) sets the filter; `LAZY_LOG_FORMAT=json` selects JSON lines on the server. The desktop client writes to `logs/lazy.log` in its profile directory (about 5 MiB per file, the newest three kept) as well as to the terminal when there is one. Tests run a representative scenario with a capturing subscriber at the most verbose level and fail if any known secret or content string appears in the output. **Help, Diagnostics…** shows and copies a report with no secrets or content: application and protocol versions, operating system, server address, profile and log folders, per-workspace connection states, counts of conversations and queued operations, and the last few error codes.

**Dogfooding.** `llm-docs/DOGFOOD.md` is the guide for the first users: how to run the server and a client, a checklist of what to try, what is known to be unverified, how to find the log folder and copy diagnostics, and how to report a problem; `.github/ISSUE_TEMPLATE/dogfood.md` is the issue form. Onboarding the users and watching them work without help (tasks 3.8 and 3.9) is for the owner.

**Decisions made while building 3H and 3I.**

*Commands and menus.* One `RunCommand` action replaces the separate actions for search, the quick switcher, and the workspace shortcuts; the sidebar links, the "+" menus, the rail's "+", Sign out, and the header's Favorite and Details buttons all go through `run_command`. Shortcuts (Ctrl on Linux and Windows, Cmd on a Mac): quick switcher Ctrl+K, command palette Ctrl+Shift+P, search Ctrl+F, Threads Ctrl+Shift+T, Saved Ctrl+Shift+S, People Ctrl+Shift+E, Browse channels Ctrl+Shift+L, New message Ctrl+N, Preferences Ctrl+, , keyboard shortcuts Ctrl+/, previous and next conversation Alt+Up and Alt+Down, previous and next unread conversation Alt+Shift+Up and Alt+Shift+Down, workspace 1 to 9 Ctrl+1 to Ctrl+9. Create a channel, add a workspace, workspace settings, invite people, user groups, custom emoji, details, favorite, diagnostics, and sign out have no shortcut (menu and palette only). Switching to the workspace that is already open is `Hidden`, so Ctrl+n does nothing then. The menu is a "Menu" button with tabbed groups at the top of the sidebar on Linux and Windows (Left and Right change group, disabled items are dimmed with their reason and each item shows its shortcut, the menu keeps one width and scrolls in a short window); on a Mac the same registry feeds `cx.set_menus` (compile-checked and structure-tested only). The key binding strings for the commands are leaked once at start because GPUI's `KeyBinding::new` wants `&'static str`.

*Window state.* `window-state.json` is discarded for a centred default when the saved bounds are off every display, below the 640 by 480 minimum, not finite, or from another version or damaged; a window larger than the largest display is brought down to it. Wayland (detected by the `WAYLAND_DISPLAY` variable, an approximation of what GPUI picked) restores size and maximized only. Saves are debounced on resize or move and written at close.

*Dialogs.* One test walks all 16 dialogs plus the palette, the command menu, the emoji picker, and the image viewer, with an exhaustive `match` on the dialog enum and a check of the dialogs folder so that a new dialog cannot skip it. It found one real defect: Escape during composition was ignored by every dialog with a text field (9 of 16) and never cancelled the composition; the shared modal now cancels the composition (`TextInput::cancel_composition`) and does not close the dialog, which changes the behavior of every modal overlay. Seven dialogs have no text field reachable on open, so the composition rules were not exercised for them.

*Logging.* The server's request line carries the request id, method, matched route pattern, status, latency, user id, byte counts, error code, and a slow flag (an unmatched request logs as `<unmatched>`; `/healthz` is debug; a 5xx or a request over 1 second is a warning; transfers of 1 MiB or more are not judged slow); a client's `x-request-id` is kept when it is 1 to 64 plain characters, echoed in the response, and present on every line of that request; a handler panic now answers a logged 500 (the connection used to drop) and the panic hook reports only the place; the JSON format is hand-written to avoid changing `Cargo.lock`; records from the `log` crate are no longer bridged, because they can carry frame contents. Seven existing calls leaked and were fixed, each demonstrated by a mutant: the request span logged the full URI with its query (search text), failed requests logged whole database and internal errors (a Postgres message can quote data; one quoted a stored character), malformed WebSocket frames and event decode failures quoted their content, join errors quote a panic's message, `Config`'s derived `Debug` printed the database password, and the default panic hook printed every panic message to stderr outside the filter. On the client, `Input`, `Effect`, `JournalEntry`, `StartupState`, `ContentCache`, `LocalFile`, `FileSource`, and `DesktopNotification` print names, ids, numbers, and lengths (`<redacted 12 chars>`) and never text, with exhaustive matches so a new variant is hidden until someone decides otherwise; defects found and fixed: reqwest's error text ends with the request URL and query (a search string reached the notice shown to the person), `serde_json` error text quotes the offending value (response bodies, realtime frames, stored files, the cache), tokio's `JoinError` repeats a panic message, and derived `Debug` on the file and notification types printed names, paths, and bodies. The client records events for realtime open and close, snapshot required, retries, upload failures by reason code, cache discards, and sign-in by user id, and traces every effect through the redacted `Debug`. The whole-system test (`crates/lazy-e2e/tests/logging.rs`) found one more leak that neither crate's own test could: the WebSocket library `tungstenite` logs every frame, message text included, at TRACE. Both programs' filters now add `tungstenite=off` and `tokio_tungstenite=off` after whatever was asked for, as the server already did for `axum::rejection`, so `LAZY_LOG=trace` cannot switch them on. At DEBUG and TRACE `hyper_util` still logs the server's host and port, which is no secret. The desktop writes about 5 MiB per file and keeps three, with its own 80-line rotation; lines logged before the profile directory is known (64 KB at most) are written when it is; a failure to open the log never stops the app. Diagnostics shows the server address without credentials, query, or fragment, and a test scans the report and the clipboard for 15 planted strings.

## D25. Packaging, deployment, first-run safety, and choosing the server (dogfood preparation)

No wire change (`PROTOCOL_VERSION` stays 14). Everything here was written to be built and run by the manual GitHub workflows (`release`, `server`, `ci`) and not on the owner's machine; what has and has not been checked is in `VERIFICATION.md`.

**First-run safety.** Whoever registers first becomes a workspace's owner, which on a server strangers can reach is a race. `LAZY_SETUP_CODE` (at least 16 characters, refused at startup when shorter, never logged, redacted in `Debug`, compared in constant time) closes it: while the default workspace has no members, registration must carry the code in the invitation-code field, and a missing or wrong code gets one answer (`forbidden`, "this server needs its setup code to create the first account"). Once any member exists, even a deactivated one, the code does nothing and is not an alternative invitation. `LAZY_SEED_REGISTRATION=invite_only` seeds the workspace the server creates as invitation-only. An invitation-only workspace with no members and no setup code still lets its first registrant in as owner, since nobody could have invited them (that state did not exist before; a public server should always set a setup code). `lazy-server healthcheck` exits 0 only for a 200 from `/healthz` within 3 seconds, so the container's `HEALTHCHECK` needs no curl. There is no rate limit on setup-code guesses; a generated code of 16 or more characters is not guessable.

**The server image.** `Dockerfile` builds `lazy-server` from `Cargo.toml`, `Cargo.lock`, and the three server crates only (`.dockerignore` whitelists them, and the workspace's `members = ["crates/*"]` then names just those, so the desktop client and the GPUI git dependency are never fetched or compiled; a build of exactly that file set resolved offline and built in 44 seconds to a 12 MB binary). It uses the `dist` profile (release, stripped), the image's own Rust 1.99 toolchain (`rust-toolchain.toml` is left out so rustup does not fetch components), a Debian bookworm slim runtime with no CA certificates (the server makes no outbound requests), a non-root user, `/data/attachments` as a volume, and the `healthcheck` command. `docker-compose.yml` runs it with `postgres:18` (volume at `/var/lib/postgresql`, the layout PostgreSQL 18 expects) and requires `POSTGRES_PASSWORD` and `LAZY_SETUP_CODE` in `.env`; `deploy/coolify/docker-compose.yaml` is the same stack using Coolify's magic variables (`SERVICE_URL_LAZY_8080`, `SERVICE_PASSWORD_POSTGRES`, `SERVICE_PASSWORD_SETUPCODE`) so the domain, certificate, and secrets are Coolify's. The server cannot yet speak TLS to Postgres, only one replica is supported, and only amd64 is built. `deploy/smoke-test.sh` checks a running server from outside (health, the setup-code rules, the owner, invitation-only afterwards, sign-in, and with `--after-restart` that the owner survived); the `server` workflow builds the image, starts the compose stack, runs it twice around a restart, and optionally pushes to `ghcr.io/<repo>/server`.

**Client packages.** The `release` workflow (manual, version as an input stamped into the workspace version) builds `lazy-desktop` with the `dist` profile on `ubuntu-22.04` (the oldest runner, glibc 2.35), `macos-15` (aarch64 and x86_64 joined with `lipo`, built with the `runtime-shaders` feature so the runner needs no Metal toolchain), and `windows-2022`, and packages a `.deb` (assembled with `ar` and `tar`, so no dpkg is needed) and a tarball with an `install.sh`, a `.dmg` holding an ad-hoc-signed `Lazy.app`, and an Inno Setup per-user installer plus a zip. Signing and notarization on macOS happen only when the `APPLE_*` secrets exist; Windows is unsigned (SmartScreen warns). A draft pre-release with `SHA256SUMS` is created when asked. The Linux package is `lazy-chat` with the command `lazy`; the macOS bundle id is `io.github.last-refuge.lazy` (changeable through `LAZY_BUNDLE_ID` before anyone installs it) and the Windows `AppId` GUID must never change. There is no app icon: the owner is creating the brand, every package builds without one, and `packaging/make-icons.sh` turns a master picture into the ICO, ICNS, and PNG files when it exists. `lazy-desktop` gained the Windows release subsystem attribute (no console window), a build script that embeds version information and, when present, the icon (a no-op off Windows), and the log file now opens before the runtime starts so a failed start is written to it. Desktop notifications and the launcher count exist only on Linux; on macOS and Windows the notifier is a stub, so those users see unread counts and the window-title badge but no operating system notifications.

## D28. Updating from inside Lazy

No wire change (`PROTOCOL_VERSION` stays 14). Written under the no-local-builds rule: **none of it has been compiled or run** (`VERIFICATION.md`). Release 0.5.0 has no updater, so the first release that has one is installed by hand, once.

**Finding out.** A running Lazy asks 20 seconds after it starts, and then every 30 minutes, what the newest release is. It reads `releases/latest/download/SHA256SUMS` from GitHub's download pages, not the releases API: the API allows 60 requests an hour per address, which one office of Lazy users would use up, and the download pages have no such limit. The file names in `SHA256SUMS` carry the version (`Lazy-Setup-0.6.0-windows-x64.exe`), so one small file says what the newest release is and what the file for this install must hash to; `lazy-client-core::update` holds the names (`Package`), the version rules (semantic versioning, pre-releases before their release), and the parsing, all pure and tested. `latest` skips drafts and pre-releases, so there is one channel, the stable one. `LAZY_RELEASES_URL` points the check somewhere else (a mirror, a test).

**Telling the person.** Automatic checks are silent: they never show "checking" or a failure, and the screen shows nothing for "up to date". A newer release puts a bar across the top of the window, on every screen including sign-in and "can't reach the server": "Lazy 0.6.0 is available" with **Update now** and **Later**. **Later** hides the bar for that release until the next start or the next time the person asks, and a still newer release shows it again. **Help, Check for updates…** asks at once, answers either way ("You're up to date", or why it could not tell), shows the release's notes, and has the switch for the automatic checks (kept in `updates.json` in the profile folder). No operating system notification: the notifier is for messages and exists only on Linux.

**Getting it.** **Update now** streams the file to `<profile>/updates/<file>.part`, checks its SHA-256 against the sum in `SHA256SUMS`, and renames it into place; a file that does not match is deleted, a copy fetched earlier is used again if it still matches, and older files are removed. The person keeps working while it comes. **Restart to update** is the step with a cost, so it is the person's: the desktop starts the installer detached and Lazy quits.

- *Windows, installed with the setup program* (an uninstaller beside `lazy.exe`): the new setup runs silently (`/SILENT /CLOSEAPPLICATIONS /LAZYUPDATE=1`); it replaces Lazy, and a `[Run]` entry that only runs with `/LAZYUPDATE=1` starts the new one. An install for everyone asks for permission as Windows always does. Files Lazy fetches itself carry no "downloaded from the internet" mark, so SmartScreen does not ask again.
- *macOS, in an app bundle:* a shell script waits for Lazy to quit, mounts the disk image, copies `Lazy.app` beside the old one, swaps them, and opens the new one; if the swap fails (no right to change the folder) the old app is put back and the disk image is opened to drag, as on first install. Run from the disk image, nothing is replaced.
- *Linux, the `.deb` at `/usr/bin/lazy`:* after Lazy quits, `pkexec apt-get install -y` the file (the desktop's own password dialog), then Lazy starts again, the new one or the old one if that failed. Needs `pkexec` and `apt-get`.
- *Linux, the tarball in the home folder (`~/.local/bin/lazy`):* unpack and run its `install.sh --prefix` the same prefix, then start Lazy again.
- *Anything else* (a portable zip, a build from source, a system install by root): the button is **View release**, which opens the page.

Every script writes to `update.log` beside the other logs and ends with Lazy running again, whatever happened.

**Switches.** The checkbox in the dialog; `LAZY_UPDATE_CHECK=0` for a packager or an administrator; development builds (debug) do not check unless `LAZY_UPDATE_CHECK=1`.

**Where it lives.** The state machine's data in `lazy-client-core` (no I/O, so a phone client could reuse the version rules); the 30-minute loop, the HTTP, and the checked download in `lazy-client-runtime` (`Updater`, started with `Runtime::start_updater`); the platform rules and the process start in `lazy-desktop` (`updater`); the model, the bar, and the dialog in `lazy-ui` (`updates`, `dialogs/updates`), talking to the desktop only through the `UpdateHost` trait, as the core talks to the runtime through `EffectSink`. The core is not involved: an update is not part of a conversation's state.

**What it does not do.**
- *It does not prove who made the file.* The checksum comes from the same place as the file, so it catches truncation and corruption, not a release published by someone who should not have. Signing the releases (the Apple and Windows secrets in `RELEASE.md`) is the answer, and until then the trust is in the GitHub repository's owner.
- *It does not check the server.* A release that changes the wire protocol makes the updated client unable to talk to a server that has not been updated; the release notes must say so, and the server should be updated first or at the same time.
- *macOS may ask again for the keychain.* An ad-hoc signature is different for every build, and the Keychain ties its permission to the signature; after an update the first read of the stored sign-in may prompt. Unverified; a Developer ID signature removes the question.
- *Windows needs the person to be at the machine for an all-users install*, since Windows asks for permission.
- *A pre-release is never offered*, and neither is a release without a file for this install.

## D29. The first run: an address, a code, and an account worth meeting

No `PROTOCOL_VERSION` change: two new routes, and a client falls back when a server answers 404. The plan is `ONBOARDING.md`; **nothing here has been compiled or run** (`VERIFICATION.md`).

**The model.** No links and no central directory: whoever runs a server hands people its address (a domain or an IP) and an invitation code. The person installs Lazy, enters both, and Lazy checks the address, remembers it, asks the server what the code is for without using it, and walks them through creating the account. A workspace is private and invited-to, so the invitation carries the discovery; a directory would serve public communities, which this is not, and would bring hosting, moderation, and abuse with it.

**The code is made to be said and typed.** A new invitation is 20 characters of Crockford's base32 (no `I`, `L`, `O`, `U`; 100 bits), shown in five groups of four. Every place that reads a code (registration, accepting, previewing, the client) first puts it in canonical form: case, spaces, dashes of every kind, zero-width characters, and `O`/`I`/`L` for `0`/`1` are forgiven *only* for a 20-character code of that alphabet, so a code pasted from a chat message works. Anything else, including the 32-character codes issued before, is only trimmed and otherwise untouched. 100 bits is what protects the code from guessing, since nothing on the server is rate-limited.

**Two routes before anyone has signed in.** `GET /v1/server` says how accounts are taken (`open`, `invite_only`, `closed`) and whether the server waits for its setup code; it holds no name and no count, and says "waiting for a setup code" only when one is configured. `POST /v1/invitations/preview` says what a valid code is for (workspace name, who invited, how many people are there; or "setup") and answers every other code with the one `invitation_invalid` registration gives. A POST so that a code is never in an address or a log.

**Five screens, each asking one thing:** connect (address and code), you're invited (the proof, before any password exists, that they reached the right server), let's set you up (name, a username suggested from it, password; the one request that makes the account), add a picture (optional), you're all set. A server too old to preview skips the second; a server open to anyone skips the code. The steps live in the view; the core holds only what the server said, which is what a phone client would reuse. The new screens are opt-in (`onboarding::enable`), so the sign-in card stays first for anyone who chose a server before, for the environment-fixed address, for the tests, and for developers.

**The look.** A Forest panel with the logo, Moss at 288 px, and the tagline beside the step on wide windows; stacked on narrow ones. Moss changes pose with the screen (welcome, primary, celebrate), never appears in an error, and is drawn from 768 px pictures prepared at twice the size so it is as sharp as the small ones. Screens arrive in 220 ms with GPUI's animation, which it shows at once under reduced motion. Headings are Nunito Bold, sentence case, in the brand's voice.

**Invite people** gains **Copy message to send**: where to get Lazy, the server's address (without `https://`), the code in groups, and for how long and how many it works.

**The owner.** A code that previews as `setup` makes the person the owner, and two screens follow the picture: name the workspace (the server seeds "Lazy") and the first invitation, made by itself for 7 days and up to 25 people, shown with the whole message to send. The owner's first run ends with the thing the next person needs.

**Setup codes have an invitation code's shape.** A setup code is typed into the same field, so the server refuses to start with one that is not 20 to 64 letters, digits, `-` and `_` (it was 16 characters of anything, and a short one or one with other characters could not be typed into the app), and compares it in the form the app sends (`canonical_invite_code` on both sides; padding still refused). The cost is that a server configured with an older, shorter code will not restart until the variable is fixed or, if people have signed up, removed; the message says so.

**Known gaps** are listed in `ONBOARDING.md` (a warning for plain `http://`, a show/hide button for the password, and a limit on how often a stranger may ask).
