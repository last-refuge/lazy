# Lazy client: core and runtime

Two crates implement the client's behavior without any UI code:

| Crate | Role | Depends on |
| --- | --- | --- |
| `lazy-client-core` | A synchronous, I/O-free state machine. Person actions and runtime reports go in; effects and change notifications come out. | `lazy-domain`, `lazy-protocol` |
| `lazy-client-runtime` | Executes the core's effects: HTTP, realtime WebSocket, encrypted local files, secure storage. Reports results back as inputs. | `lazy-client-core`, Tokio, reqwest, tokio-tungstenite |

The UI (GPUI) owns a `ClientCore` and a `Runtime`, and only moves values between them. Neither crate knows about GPUI, so phone clients can reuse both.

```
person ──Input──▶ ClientCore ──Output { effects, changes }──▶ host
                      ▲                                         │
                      │                                         ├─ changes ▶ refresh views
         Input ◀──────┴──── Receiver<Input> ◀── Runtime ◀──────┘ effects
```

### `Change` (what the UI refreshes)

`PhaseChanged`, `ConnectionChanged`, `DirectoryChanged` (workspaces, conversations, members, names), `SelectionChanged`, `DraftChanged { conversation }`, `TimelineReset { conversation }`, `TimelineSplice { conversation, at, removed, inserted }`, `TimelineItemUpdated { conversation, index }`, `HistoryStatusChanged { conversation }`, `NoticeChanged`.

**Apply the changes of one `Output` in order, then read the final state from the core.** A timeline change describes the row list as it was at that point in the sequence, so replaying splices in order keeps a virtualized list's length structure in step with the model; row *contents* are read from the core's final state at render time. In GPUI terms: `ListState::splice(at..at + removed, inserted)` for a splice, `remeasure`/invalidate for `TimelineItemUpdated`, and reset the list state for `TimelineReset`. Prepending older history is always one splice at `0`.

## Timelines

`timeline(conversation)` is a `&[TimelineItem]`: confirmed messages sorted by event-log position (`seq`, never timestamps), then messages still being delivered in submission order. Each row has:

* `key: ItemKey`: `Operation(id)` for messages this client sent, which stays the key after confirmation so the row keeps its identity; `Message(id)` for everything else.
* `delivery`: `Confirmed { message_id, seq, created_at, revision }`, `Pending`, `UnknownOutcome` (asking the server whether it committed), or `Failed { reason, retry }`.
* `retry`: `NewOperation` (the server definitively refused; retrying composes a fresh operation from the same text) or `SameOperation` (outcome unknown; retrying asks the server first, then resends the *same* operation if needed).

Invariants, checked after every step of the randomized simulation: confirmed rows precede unconfirmed rows, confirmed rows are strictly ordered by `seq`, no message id appears twice, no row key appears twice.

## Sending: the state machine

```
SendMessage ─ empty ─▶ ignored (no operation)
     │
     ▼
 Pending ── PersistSubmission ─▶ (journal flushed) ── SubmissionPersisted ─▶ Queued
     │                                  │ SubmissionPersistFailed              │ its turn (see "The send queue")
     │                                  ▼                                      ▼
     │                         Failed{NewOperation}  (journal entry settled)   SendMessage effect
     ▼
 SendResult
   Ok(ack) ───────────────────────────▶ Confirmed ── SettleSubmission
   Rejected (definitive) ─────────────▶ Failed{NewOperation} ── SettleSubmission
   Unknown (timeout / 5xx / garbled) ─▶ UnknownOutcome ── QueryOperationStatus
                                              │
                    Committed{message} ───────┼──▶ Confirmed ── SettleSubmission
                    NotFound ─────────────────┼──▶ Queued again: resend the SAME operation id (≤ 3 times)
                    query itself failed ──────┴──▶ Failed{SameOperation}  (journal entry kept)
```

### The send queue

Messages in a conversation go out **one at a time, in the order they were submitted**, so the server commits them in that order. Every submission is still journaled immediately and appears as `Pending` in submission order; only its `SendMessage` effect waits for its turn.

* The head of a conversation's queue is its earliest operation that is not `Failed`. Only the head may have a send in flight. If the head is still being journaled, being sent, or being checked with the server (`UnknownOutcome`, including a resend after "no record"), everything behind it waits, so a later message can never overtake an earlier one whose outcome is not yet known.
* Conversations have independent queues.
* A `Failed` message does not hold anything up, whether the server definitively rejected it or the client gave up with an unknown outcome. Its successor is released the moment it fails.
* After a restart, recovered journal entries are queued first, ordered by `submitted_at` (ties keep journal order), before any message typed after startup. All of them are checked with the server first, in parallel; the resends that follow still go one at a time in that order.
* Retrying a `NewOperation` failure composes a new submission at the back of the queue (its row is replaced by a new one at the bottom). Retrying a `SameOperation` failure asks the server first, and if the server has no record, resends the **same** operation id **at the back of the queue**: the row moves to the bottom of the timeline too, because later messages may already have been sent while it was given up on.
* Nothing is released while the session is not `Ready`; queued messages go out when the app is ready again. Session expiry fails every unfinished message instead of releasing the queue into refused requests.
* Tested by 12 scenario tests (20 rapid sends one at a time and in order with no row moving; slow journal write; failure and unknown outcome behind and ahead of others; recovery order; both retry kinds; expiry; unreachable server) and by the randomized simulation, which asserts that, for one sender, committed order equals submission order for every message the client never gave up on. With the queue disabled the simulation fails ("committed out of submission order").

Rules the code enforces and the tests cover:

* The journal write is durable before the HTTP request exists.
* An unknown outcome never produces a new operation id. Only `RetryOperation` on a `NewOperation` failure composes a new one.
* The live `MessageCreated { operation_id }` event and the acknowledgment may arrive in either order; the message appears once and `SettleSubmission` is emitted once. A history page that already contains the message is merged into the local row.
* After a restart, journal entries for the signed-in person appear as `UnknownOutcome` rows and are checked with the server before anything is resent. Entries for other people are ignored (and kept).
* `Unauthenticated` anywhere signs the person out (`ForgetSession`) and turns unfinished sends into `Failed{SameOperation}`, so signing in again and retrying reconciles them.

## Synchronizing

1. **First run** (no usable cache). `LoadBootstrap` → `BootstrapLoaded`. The core resets confirmed content (rows still being sent survive), records `head` as the applied position, emits `Subscribe { workspace, after: head }`, selects `#general` (or the first conversation), and fetches its newest page.
2. Events are applied only if `seq` is greater than the applied position, then deduplicated by message id. `CaughtUp` advances the position and makes the connection `Live`.
3. `SnapshotRequired` (cursor expired **or** ahead of the server's log): the core discards the content cache (`DiscardCache`), clears confirmed content, and asks for a fresh bootstrap (not duplicated if one is in flight); the answer is handled as a first run. Nothing is cached in between, because the cursor on hand is known to be bad.
4. **Restart with a cache**: see below.
5. The runtime tracks the last position it forwarded per workspace and resubscribes from it on reconnect, so the core does not drive reconnects. A repeated `Subscribe` for a workspace replaces the position, on the open connection if there is one. After a `snapshot_required` frame the runtime does **not** reconnect on its own: the position it holds is known to be refused, so it waits for the core's fresh `Subscribe` (otherwise it would just be refused again).

### History

`FetchHistory` carries a per-conversation `generation`. A response is applied to the conversation it was requested for (never to whatever is selected), and only if its generation is still current; resets and newer requests supersede older ones. `LoadOlder` pages from the *history floor*, the lower bound of the contiguous range loaded from history, **not** from the oldest row: a message sent from this client can be acknowledged at a position below the newest page, and paging from that row would skip the gap (found by the simulation; regression-tested).

## The content cache

The client keeps a bounded, encrypted, **regenerable** cache so a restart shows the last conversation instantly and resumes from where it stopped. The cache can be absent, trimmed, or thrown away at any time; the client then behaves as on a first run.

**What it holds** (`ContentCache`): who it belongs to; per workspace, the directory from the last bootstrap (workspace, role, conversations, members), the **applied event cursor**, and, for each conversation whose history was loaded, the newest ≤ 200 *confirmed* messages plus a `has_more` flag for older ones. Pending and failed messages are never cached (the journal owns those). A conversation that has only seen live events is left out: its timeline is partial, so it fetches its newest page when opened, as on a first run.

**The invariant: the cursor never runs ahead of the messages it covers.** For every cached conversation, all messages between the oldest cached one and the cursor are present; if older ones exist, `has_more` is true. Messages *beyond* the cursor may be present (replay re-delivers and deduplicates them); a cursor *behind* the messages is always safe. This is guaranteed three ways: the cursor and messages are one value written in one atomic file replacement (`cache.enc`), so a crash leaves the old cache or the new one, never a mixture; the core only caches contiguous ranges (from the *history floor* up, so a message acknowledged below the loaded range is excluded); and a restored timeline's floor accounts for the cursor (a message acknowledged beyond the cursor must not be mistaken for the bottom of the loaded range, or replay would later deliver messages below it that a cache write would then exclude, found by the simulation and regression-tested).

**Bounds and eviction** (deterministic): ≤ 200 messages per conversation (the newest; older are dropped and `has_more` set), ≤ 50 conversations with messages (least recently active evicted first, ties by conversation id), ≤ 4 MiB for the file. The core applies the count limits when it builds the cache and again when it loads one. The runtime enforces the byte limit when it saves: while the sealed file is too large it evicts the least recently active whole timeline and tries again; dropping a timeline never makes the cache inconsistent, and a directory too large to fit leaves no cache at all.

**Writing.** The core emits `Effect::PersistCache` at the end of any `handle` call that changed what the cache holds, never from render. The runtime keeps only the latest pending cache and writes it after `save_debounce`, flushing on shutdown. Building the cache costs time proportional to its size and runs on the UI thread, so live events on a big cache are batched (one write per 500 cached messages' worth of events; structural changes, a loaded page, the directory, members, are saved at once). Skipping a write is always safe: an older cache just means a slightly longer replay. Measured with a full cache (50 × 200 messages): about 0.09 ms per live event in a release build (0.18 ms unoptimized), against 2.2 ms (4.5 ms) per event if every event rebuilt it.

**Starting with a session and a cache.**

1. `Started` shows the cached directory and timelines **immediately**: the phase is `Ready`, the connection is `Connecting`, and `TimelineReset` / `DirectoryChanged` / `SelectionChanged` fire so the UI draws content before any network result.
2. The core emits `Subscribe { after: cached cursor }` (not the bootstrap head) and `LoadBootstrap` to revalidate. Replay fills the gap. Nothing is refetched for a cached conversation; a selected conversation that was not cached fetches its newest page as usual.
3. `BootstrapLoaded` revalidates: the directory is refreshed (new conversations and members appear); conversations the person can no longer read lose their content (and the selection moves if it was one of them). If the bootstrap shows the cache cannot be trusted (another person, a workspace missing, or a cached cursor *ahead* of the server's `head`), it is handled as a first run.
4. If the network is down, cached content stays on screen (no error screen); the realtime connection keeps retrying by itself, and every time it opens the bootstrap is requested again (never duplicated). `Unauthenticated` signs the person out as usual.
5. Journal recovery happens at once (the person is known from the cache): recovered operations are checked with the server, ordered first, and the per-conversation send queue and its ordering guarantee are unchanged.
6. A cache belonging to someone else is never shown: it is ignored without a session, and another person signing in discards it. Sign-out deletes it with everything else. A corrupt cache is set aside and reported in `Started.problems`; a cache from a newer format is left untouched and not used.

**Edits and deletes (not in the protocol yet).** A cached message the server later edits or deletes is an *event* with a position greater than the cursor, so replay applies it through the same path that applies new messages (matched by message id) and the next cache write carries the result; nothing in the cache design needs to change. An edit or delete that happened while the client was away is covered because replay runs from the cached cursor. If the server has pruned those events (`snapshot_required`, cursor expired), the whole cache is discarded, so a stale cached message can never outlive the events that would have corrected it. When those events are added they must be applied by message id to timeline rows *and* mark the cache dirty; that is the only requirement.

| Call | Meaning |

**Inputs from the UI**: `CreateChannel { name, visibility, topic, description }` (raw text; an empty topic or description means none; the name is trimmed, lowercased, and spaces become hyphens), `OpenConversation { participants }`, `BrowseChannels`, `JoinChannel(id)`, `LeaveChannel(id)`, `AddMembers { id, users }`, `RemoveMember { id, user }`, `UpdateConversation { id, name, topic, description }` (`None` = unchanged, `Some("")` clears), `ArchiveConversation(id)`, `UnarchiveConversation(id)`, `SetFavorite { id, favorite }`, `DismissAction(kind)`, and two pieces of view state the core cannot know: **`WindowActive(bool)`** (assumed true) and **`TimelineAtBottom { conversation, at_bottom }`** (assumed false until reported, and forgotten when the person leaves the conversation). Without those two reports nothing is ever marked read.

**Changes**: `ConversationStateChanged { conversation }` (title, member count, archived, favorite, unread counts, or marker), `BrowseChanged`, `ActionChanged(kind)`, and `ConversationOpened(id)`. The latter means a created channel or an opened direct/group conversation is ready and **already selected**; navigate to it. Joining does not navigate (the UI may send `SelectConversation` afterwards). `DirectoryChanged`, `SelectionChanged`, `TimelineReset`, and `NoticeChanged` fire as before.

**Runtime reports** (not for the UI): `ConversationCommandResult { operation, result }` for create and open, `ActionResult { kind, result }` for everything else, `MarkReadResult { conversation, up_to, result }`.

### Actions

Each `ActionKind` has one `ActionState`. Starting an action that is already `InFlight` is ignored (a double click cannot send twice). Input that can be checked locally fails immediately with a readable message and sends nothing: a channel name that is empty, too long, or uses other characters; a topic over 250 characters or with line breaks; a description over 1,000; an open with no other person or more than nine. Server refusals are turned into words (`name_taken` → "That name is already taken. Choose another."; `forbidden` → "You're not allowed to do that."; an unreachable server → "Couldn't reach the server. Check your connection and try again."). `Failed` stays until the action is started again or `DismissAction`. An expired session ends the session instead of showing a dialog error.

**Create and open carry an operation id and follow the same rules as sends.** If the answer is lost, the core asks `QueryOperationStatus`; `conversation_committed` finishes the action, `not_found` resends the **same** request with the **same** operation id (at most three times), and it never creates anew with a fresh id. After giving up the action is `Failed("... Try again to check.")` but the operation is kept: starting the same create again continues it (asking first); starting a different one begins a new operation. A late "it committed" answer is accepted whatever the request is doing. The other commands set a state, so repeating them is harmless and they carry no id. Successful create/open adds the conversation, selects it, fetches its newest page, and emits `ConversationOpened`.

### Unread counting

The server computes each conversation's baseline at a known log position; the client then keeps it current by applying events in order:

* a message by someone else in a conversation the person belongs to adds one, unless it is at or before the read position;
* a message by the person moves the read position to it and leaves nothing unread (the server does the same in the send transaction, without an event);
* `UserStateChanged` replaces the whole state, since the server computed it at its own position;
* events for a conversation the client does not know are ignored (they still advance the cursor), and no timeline is created for them.

Every state also remembers the log position it is **current to** (`as_of`, saved in the cache). Events at or before it are never counted again. That is what makes a message count exactly once across replay after a cached restart, a reconnect, and a bootstrap that teaches the client a conversation the cache did not know. The answer to a mark-read request recounts from the timeline, but only messages up to the applied position, because a history page can hold messages whose events have not arrived yet.

### Marking read

Evaluated after every input, never from render. The core emits `MarkRead { conversation, up_to }` when the conversation is **selected**, the **window is active**, the timeline reports it is **at the bottom**, its history is **loaded**, it has **unread messages**, and the newest loaded message is beyond the read position. `up_to` is the newest loaded message position, so requests only ever move forward and are never sent because of the person's own message. At most one request per conversation is in flight (that is the debounce): messages arriving meanwhile are covered by one follow-up when the answer returns. A failed request is not retried for the same position until something changes (a new message, the window or bottom state, or reselecting).

### The "New messages" divider

When a conversation is selected the core captures its read position (if it has unread messages) and `unread_marker` returns the first confirmed row after it, as soon as that row is loaded. It stays while the conversation is marked read underneath it and is dropped only when the person selects another conversation. If nothing was unread on opening but messages arrive while the person is not looking (window inactive or scrolled up), the divider starts at the first of them.

### Membership events

* `ConversationCreated`: adds an unknown conversation (everything before it counts as read) or replaces a known one. `ConversationUpdated`: replaces a known conversation, ignores an unknown one.
* `MemberAdded` for me: adds the conversation, **fetches its newest page**, does not select it, starts its read position at the event. `MemberAdded` for someone else: replaces the snapshot (it carries the current member count).
* `MemberRemoved` for me: the conversation, its timeline, draft, read state, divider, unsent messages (their journal entries are released), and cache entry are dropped; if it was open, the default conversation opens instead and a notice says "You were removed from #name". If the person asked to leave (`LeaveChannel`), whichever of the answer and the event arrives first removes it, silently. `MemberRemoved` for someone else decrements the member count (a later `ConversationUpdated` snapshot is authoritative).

### Cache and persistence

The cache carries the directory (with the new conversation fields), each conversation's read state **and the position it is current to**, under the same atomic cursor-and-messages write, so a restart shows favorites and unread counts at once and replay counts only what is new. On revalidation the cached state is kept (replay brings it up to date); conversations the cache did not know take the bootstrap's baseline, current to its head; a cache from before read state existed supplies none and the bootstrap does. Conversations the person can no longer read lose their state with their content. Drafts remain per conversation and are removed with a removed conversation; sign-out deletes everything. Writes caused only by counting a live message are batched like other live events.

## Editing, deleting, and permalinks (slice 2B)

The contract is `llm-docs/DECISIONS.md` D12 and `PROTOCOL_VERSION` 3. Sent text is now parsed with `MessageDocument::from_markdown`; a limit error (`DocumentError`) is a notice and the draft stays. Pending rows show the parsed document.

### What the UI calls

| Call | Meaning |
| --- | --- |
| `TimelineItem::edited_at`, `is_edited()`, `revision()` | The "(edited)" mark and the server's revision. |
| `TimelineItem::edit: EditState` | `None`; `Saving` (the row's `document` already shows the new text); `Failed { reason, text, retry }` and `Conflict { text }` (the row shows the server's version again and `text` is what the person wrote). |
| `can_edit_message(conversation, message)` | The author, in a conversation they can still post in (not archived, not left). |
| `can_delete_message(conversation, message)` | The author (same condition), or an admin/owner of the workspace for anyone's message in a conversation they can read. From `lazy_domain::MessageFacts`; the server decides. |
| `edit_text(conversation, message)` | Where the editor starts: the person's latest text if an edit is waiting, saving, failed, or conflicted; otherwise the message as composer source (`to_markdown`). |
| `jump_target()` → `Option<JumpTarget { conversation, key }>` | Where a permalink landed. `Change::JumpTargetChanged` fires on set (again for the same message opened twice) and on clear. |
| `join_offer()` → `Option<ConversationId>` | With the notice for a permalink into a public channel the person has not joined. |
| `action(ActionKind::DeleteMessage(id))` | `InFlight`, `Failed(reason)`. |

**Inputs**: `EditMessage { conversation, message, text }` (composer source), `CancelEdit { conversation, message }`, `RetryEdit { conversation, message }`, `DeleteMessage { conversation, message }`, `OpenPermalink(Permalink)`, `ClearJumpTarget`. An edit shows as `TimelineItemUpdated`; a deleted message leaves the timeline as a `TimelineSplice` with `removed: 1` (there is no `deleted` on a row).

### Edits

An edit is a submission like a send: an operation id, journaled (`JournalEntry` with `kind: Edit { message_id, base_revision }`) before the request, reconciled through `GET /v1/operations/{id}` (`edit_committed`) when the answer is lost, never made again under a fresh id. What differs is concurrency, which is **per message**.

* **One in flight.** The row shows the new text at once (`EditState::Saving`); the server's text is kept aside, so a failure can show it again and the content cache never records an unsaved edit.
* **Coalescing.** Text written meanwhile replaces a single waiting edit (the latest text wins) and goes out as one new operation on top of the revision the first one produced, unless it leaves the message as the server has it. Writing the original text back while an edit is in flight is sent as a revert. The waiting edit is not journaled: the journal's entry for the message is the one in flight, and a crash loses only the unsent text.
* **Local checks** (no request): empty text is a notice ("Delete it instead"), unchanged text is ignored, a document over the limits is a notice, a message the person may not edit is a notice.
* **Outcomes.** Committed (response, status, or the edit event carrying our operation id, whichever comes first; the others change nothing): the row takes the new revision. Lost answer: `QueryOperationStatus`; `not_found` resends the **same** operation (three times at most, then `Failed { retry: SameOperation }`, journal kept). `stale_revision`: the journal entry is released, the message is fetched, and the row shows the newer version with `Conflict { text }` and a notice; if the fetch fails the state is `Failed { retry: NewOperation }`. `forbidden`/`not_found`: the row reverts, the edit is forgotten, and a notice says why (there is nothing to retry). Any other refusal: `Failed { retry: NewOperation }`, journal released. A tombstone as the result (the message was deleted) removes the row and settles the edit with a notice.
* **After a failure.** `RetryEdit`: `SameOperation` asks the server first; `NewOperation` and `Conflict` send the kept text as a **new** operation on top of the revision the row now has (for a conflict, that replaces the other change). `CancelEdit` forgets a failed or conflicted edit, or drops the waiting text; a request already sent cannot be taken back. Writing new text while an edit is failed or conflicted is a fresh edit, except after an unknown outcome: then the new text waits and the old operation is asked about first (if the server has no record the old text is dropped, since the person has written something newer).
* **Restart.** A journaled edit comes back as `Saving` on its row (once the message is loaded), is asked about, and is resolved as above. An edit whose outcome is still unknown and whose message is not on screen is asked about again each time the connection catches up.
* **Sessions.** An expired session stops running edits as `Failed { retry: SameOperation }`; they continue after signing in again.

### Events

* `MessageEdited { message, operation_id }` replaces a loaded row only if its revision is higher (older, equal, and duplicate deliveries change nothing). If our own edit is waiting and a newer revision arrives, the server's version moves underneath the displayed text and the stale answer that follows becomes the conflict. An edit for a message that is not loaded is remembered while a history page that may predate it is in flight, and applied when the page is merged; otherwise it is dropped (the page that loads the message has it).
* `MessageDeleted { message }` removes the row, drops its edits (releasing a journal entry, after the write is reported if it was still in flight), clears the delete action, and ends a permalink or jump that pointed at it. It is also remembered for a page in flight.
* **A deleted message's earlier events arrive as tombstones.** `MessageCreated` or `MessageEdited` with `deleted: true` (a replay after the deletion) never adds or changes a row and never counts as unread. A tombstone creation is still a position: the person's own message moves their read position. A send of ours that arrives as a tombstone ends without ever showing.

### Unread counts and deletions

A deletion event subtracts one only if that message was counted. With `event_seq` the deletion's own position and `message.seq` the creation's: nothing if the deletion is at or before the state's position (`as_of`, which already excludes it), if the message is the person's own, or if it is at or before the read position. Otherwise it was counted iff its creation is at or before `as_of` (the server's baseline included it) **or** it arrived as a live, counted creation event after `as_of` (`counted_unread`, saved in the cache beside `as_of`). A message the client only ever saw as a replayed tombstone was never counted, so its deletion subtracts nothing. The result is the same count whether the client saw the creation live, only through a replay, or with the cursor between the two, and whether or not the message is loaded.

### Deleting

`DeleteMessage` is one request, retried by the runtime after a lost answer because deleting is idempotent. The row stays until the answer or the event arrives; the unread count follows the event only (it is delivered in log order), so a deletion is never subtracted twice. A refusal or unreachable server sets `action(DeleteMessage(id))` to `Failed(reason)` and a notice; sending the input again retries. `not_found` just removes the row. Deletion while offline needs nothing special: replay delivers the event.

### Permalinks

`OpenPermalink` checks the workspace ("a workspace you're not in" notice), then: a message already loaded in its conversation is selected and jumped to without a request. Otherwise `GET /v1/messages/{id}` tells the core the message's conversation and position (or that it is deleted, missing, or unreadable, each a notice). A conversation the person belongs to is selected and older history is paged (`request_history` before the loaded floor, at most `PERMALINK_MAX_PAGES` = 10 pages for the link) until the row appears (then `jump_target`), the loaded range covers the message's position without containing it ("isn't available, may have been deleted"), or the bound is reached ("too far back, scroll up"). A channel the person has not joined is not shown (there is no read-only view): the notice offers to join it (`join_offer`), and the link opens by itself once the channel is joined. Selecting another conversation abandons the link; the jump target is dropped when the person leaves the conversation or the row disappears.

### Persistence and upgrades

`Message` carries `edited_at` and `deleted` with defaults, so a cached message from an older build reads as unedited and not deleted; the runtime still discards a cache stamped with a different `PROTOCOL_VERSION` silently (version 2's is discarded). `CachedUserState::counted` is skipped when empty and defaults, so a saved read state from before it reads unchanged. `JournalEntry::kind` is skipped for sends and defaults to `Send`: journal files written before edits existed load, and a send is stored byte-for-byte as before. An edit entry's `document` is the new content and its `conversation_id` the message's conversation.

## Reactions and emoji (slice 2C-1)

The contract is `llm-docs/DECISIONS.md` D13 and `PROTOCOL_VERSION` 4.

### What the UI calls

| Call | Meaning |
| --- | --- |
| `TimelineItem::reactions` → `Vec<ReactionSummary { emoji, users }>` | The list **to show**: one entry per emoji in the order each was first used, `users` oldest first. It already includes the person's own change while that is being saved, so a click shows at once. `reacted_by(user, emoji)` reads it. |
| `TimelineItem::reactions_as_of` | The log position of the server's list the row is built from (informational). |
| `can_react_message(conversation, message)` | From `MessageFacts::can_react`: anyone who could post in the conversation may react to any message in it; not in an archived conversation, nor to a deleted message. The server decides. |
| `reacted_by_me(conversation, message, emoji)` | As shown, including a change still being saved. |
| `emoji_prefs()` → `EmojiPrefs { skin_tone: u8, recent: Vec<ReactionEmoji> }` | `skin_tone` is `lazy_domain::emoji::skin_tone_index` (0 default, 1 to 5 light to dark); `recent` is most recent first, no repeats, at most `MAX_RECENT_EMOJI` (24). `Change::EmojiPrefsChanged` fires when either changes. |
| `pending_reaction_changes()` | Diagnostics: reaction changes not yet saved. |

**Inputs**: `ToggleReaction { conversation, message, emoji }` (flips what is shown; pass `item.message_id()`), `RecordEmojiUse(emoji)` (the UI sends it when the person picks an emoji; toggling does not record), `SetSkinTone(u8)` (0 to 5; anything else is ignored). Failures are a `notice()`; a reaction has no per-row failure state because a failure simply reverts the row.

### Toggling

* **State, not an operation, and deliberately not journaled.** `PUT /v1/messages/{id}/reactions` sets whether the person has reacted with one emoji. Like a favorite (D11) it is idempotent and carries no operation id, so repeating it cannot do harm and there is nothing to reconcile. The rule to journal before sending, and to reconcile an unknown outcome by asking, is for requests that are not idempotent (sends, edits, creating a channel); applying it here would only add a file write to every click.
* **Optimistic.** The row changes at once: the person's pending changes are laid over the server's list (kept aside in the timeline, like an unsaved edit). A new emoji goes last, and the person goes last among those who used an emoji, which is the order the server will give.
* **One request in flight per (message, emoji).** Further toggles of the same emoji only change what the person wants. When the request finishes: if the person wants what it asked for, the toggle is done and the row shows the **server's** state; otherwise the next request carries the final wish. So rapid toggles collapse to the final state. A request is not made at all when the server's list (as held) already has what the person wants, which happens when another device or an event settled it while the request was in flight. Different emoji, and different messages, are independent.
* **Others meanwhile.** An event for the same (message, emoji) from other people updates the list underneath; it never flips the person's pending state.
* **Local checks** (no request, a notice): reacting where `can_react_message` is false; adding a 51st different emoji (`MAX_REACTION_KINDS`, "This message already has the most different reactions it can hold.").
* **Unknown outcome.** The request is repeated (the same request, for the person's latest wish) up to three times, then the row reverts and a notice says the reaction wasn't saved. If one of the attempts had in fact been applied, the event brings the row up to date.
* **Refusals** revert the row and say why: `limit_reached` (the sentence above), `forbidden` ("You can't react to messages here."), `not_found` ("That message no longer exists."), `invalid_request` ("That emoji can't be used as a reaction."), anything else in plain words. An expired session reverts every pending change and ends the session as usual; deleting the message, leaving the conversation, or a response that is a tombstone drops its pending changes with the row.

### The version rule

Each message's reactions carry a version of their own, `reactions_as_of` (the log position of the change that produced them), independent of `revision`. A row keeps **the reactions with the highest `reactions_as_of`, whichever way they arrive**: a history page, the response to a request, a fetch, the payload of a `MessageCreated` or `MessageEdited`, or `ReactionsChanged`, whose version is the event's envelope `seq`. A strictly higher version replaces the list; an equal or lower one changes nothing (ties keep what is held); content and reactions are taken from a payload independently (an edit's payload built before a reaction change brings the new text and leaves the newer reactions).

The class of bug this prevents is the one found in slice 2B: a history page requested before a change arrives after the change's event. For a message that is not loaded yet, a reaction list that arrives while a page may be in flight is remembered (like an edit or deletion) and applied when the page is merged, whichever is newer. A send that is confirmed after a page already brought the message in keeps the page's newer reactions. Events for unknown messages and conversations are ignored; a deleted message's reactions go with its row, and a tombstone has none.

### Composer: shortcodes

`SendMessage` and `EditMessage` text pass through `lazy_domain::emoji::replace_shortcodes` and then the source parser, so `:tada:` is stored as the glyph (only where the shortcode stands alone: not after a letter or digit, so `10:30:45` is untouched; not after a backslash; not in a code span or fence; unknown names stay as typed). Drafts and the editor's source are never rewritten: a draft stays as typed, `edit_text` returns what was typed while an edit is waiting, saving, failed, or conflicted, and the saved message reads back with the glyph. Typing the shortcode of what is already there is an edit that changes nothing.

### Emoji preferences

The skin tone and recent emoji are **per profile, on this machine**: not synced, not secret, not encrypted. The runtime reads `<profile>/emoji-prefs.json` at startup into `StartupState::emoji_prefs` and saves the whole file (atomically, debounced like drafts) after each change from `Effect::PersistEmojiPrefs`. The file is `{"version": 1, "skin_tone": 0..=5, "recent": ["🎉", ...]}` as pretty JSON. Reading never fails: a missing, unreadable, damaged, or differently versioned file (older without a version, or newer) is the defaults, and the next save writes a fresh one; unknown fields are ignored; a tone beyond 5 becomes 0; entries that are not emoji (the dataset changed) are skipped; repeats are dropped and the list cut to 24. Preferences are saved even where the encrypted state cannot be (no credential store). **Signing out** resets them in the core and deletes the file, like the rest of the local data; a different person signing in on the same profile does not inherit someone's recents.

### Cache and upgrades

The content cache carries each message's `reactions` and `reactions_as_of` as the **server** has them (never a pending change), written under the same cursor-and-messages atomic write, so a restart shows reactions at once and replay brings them up to date; a cache never runs ahead of a reaction change its cursor has passed. `PROTOCOL_VERSION` 4 makes the runtime discard a cache stamped 3 silently (tested with a version-3-shaped file); `Message::reactions` and `reactions_as_of` default, so a message without them reads as having none.

## Mentions, groups, and members (slice 2C-2)

The contract is `llm-docs/DECISIONS.md` D14 and `PROTOCOL_VERSION` 5.

### What the UI calls

| Call | Meaning |
| --- | --- |
| `mention_candidates(conversation, query)` → `Vec<MentionCandidate { target, handle, display_name, kind, in_conversation }>` | What to suggest for the text after an `@` (a leading `@` is forgiven; empty lists everything). People in the conversation first, then in a **public** channel only the other members of the workspace with `in_conversation: false` (naming them is allowed but notifies no one, so say so), then user groups, then `@channel` where the person may use it. Within each: handle starts with the text, handle contains it, a display-name word starts with it, display name contains it; each by display name; case-insensitive. | `mention_directory(conversation)` → `MapDirectory` | The same sources keyed by handle. **Sending and editing parse with it** (`MessageDocument::from_markdown_with`, after shortcodes), so a typed `@alice` becomes a mention exactly when autocomplete would have offered it, and anything else stays text. | `conversation_members(conversation)` → `Option<&[UserId]>` | Participants of a direct or group conversation (always known); for a channel the people fetched when it is selected, kept current by `MemberAdded` and `MemberRemoved`, **not saved**. `None` until a channel's list arrives. `Change::ConversationMembersChanged { conversation }`. |
| `groups()`, `group(id)`, `can_manage_groups()` | The workspace's groups ordered by handle (`UserGroup { id, workspace_id, handle, name, members }`); admins and owners manage them. `Change::GroupsChanged`. |

| `user_state(c).mention_count` | Unread messages that mention the person. |

**Inputs**: `CreateGroup { handle, name, members }`, `UpdateGroup { id, handle, name, members }` (`None` leaves a field unchanged; `members`, when given, is the complete new list), `DeleteGroup(id)`. Raw text is validated by the core (a leading `@` and capitals in a handle are forgiven; 2 to 32 characters; not `channel`, `here`, `everyone`, or anyone's username; a group has at most 200 people and a workspace at most 100 groups). `ActionKind::{CreateGroup, UpdateGroup(id), DeleteGroup(id)}` carry progress and readable errors ("That handle is already used by a person, another group, or a reserved word.", "Only admins and owners can manage groups.", the limits, "That group no longer exists.").

### Sending and editing

`SendMessage` and `EditMessage` run the text through shortcodes, then `from_markdown_with(mention_directory(conversation))`. The editor's source shows a mention as `@handle`; a mention of someone who is no longer offered becomes plain text when the message is edited, because the directory no longer knows them. A refusal that the mention explains gets a specific reason on the failed row or edit (and the person's words are kept): `forbidden` for a message with `@channel` ("You can't use @channel here: in the default channel it is for admins and owners."), `invalid_request` for a message with any mention ("A mention in that message isn't valid: the person may have left the workspace, or the group may no longer exist."). An edit refused for `@channel` is `Failed { retry: NewOperation }` with the text kept, not forgotten as other `forbidden` edits are.

### Mention counts

`mention_count` is the number of unread messages (from someone else, after the read position, not deleted) that notify the person. It follows the unread count's discipline (D11, D12): **the server's baseline is authoritative and events adjust only messages that were counted.** Each counted message has an entry in `counted_unread` whose value is whether the client currently counts it as mentioning the person:

* a message counted from its live creation event starts with `mentions.includes(me)`; a **tombstone creation never counts**; the person's own messages never count and read everything;
* an edit moves the entry to the new mentions, and only if the message was counted; an edit at or before the state's position is already in the baseline;
* a message the baseline counted has no entry until an event reveals what the baseline held: the first edit's `previous_mentions`, or the deletion's `had_mentions`;
* every event's `previous_mentions` / `had_mentions` is the state **before** it. That is what lets an edit that arrives as a tombstone (a deletion rewrites the earlier events of its message but keeps those fields, D12/D14) still catch the entry up, and the deletion then removes exactly what the client holds. The result is the same count live, by replay, with the cursor between the two, and after a restart (the entries are saved in the cache beside `as_of`: `counted`, `counted_mentions`);
* `UserStateChanged` replaces the whole state.

**Marking read.** Reading past counted messages takes them off. With every message after the read position loaded (a complete timeline) the unread and mention counts are rebuilt from the rows (each row says whether it mentions the person), and the entries are made to agree with the rows, so an edit event that arrives later for a row that is already ahead of it changes nothing. The count is then the rows': a message the baseline counted that has **no row** (it was deleted before the page was fetched) is no longer counted, and a note (`rebuilt_through`, saved in the cache) keeps its deletion from being subtracted a second time. Without a complete timeline the answer's own count is **not used**: it describes the server's log at the moment it answered, which can be ahead of the events applied here (a message deleted since is already left out, and its deletion event would be subtracted twice). What was read and is known to have been counted is taken off instead; anything else the request read is a message the baseline counted, which the `UserStateChanged` event the request produces accounts for. (Before this slice the answer's count, capped at what was held, was used; the simulation found the double subtraction.)

### User groups

The groups arrive in the bootstrap (per workspace), are saved in the cache, and follow `GroupChanged` (replaces or adds) and `GroupDeleted`; events for a workspace the person is not in are ignored. **Creating** carries an operation id and is reconciled like creating a channel: a lost answer is asked about (`GroupCommitted` finishes it at any stage, `not_found` resends the **same** request with the **same** id, at most three times), and starting the same create again continues the earlier operation. **Changing** sets the handle, name, and complete membership, and **deleting** is idempotent (`not_found` is deleting it, and a lost answer is asked again by the runtime), so those are plain requests with an `ActionKind`. The core checks the person's role, the handle (and that no person or other group has it), the name, and the sizes before asking.

### Who is in a conversation

A channel's list is requested when it is selected (not while a refused cursor waits for its bootstrap), once; a failed fetch is tried again when the person selects it again or the connection catches up, never in a loop. Each request has a generation, so the answer to one from before the lists were dropped is not taken for the current one. `MemberAdded` and `MemberRemoved` update a list; a change that arrives **while a fetch is in flight is applied to its answer**, because the snapshot may predate it. When the realtime connection catches up the lists are marked stale and the selected one is fetched again (the old list stays usable meanwhile; another channel's is fetched when it is next selected); a refused cursor drops all of them.

Runtime reports: `RepliesLoaded`, `ThreadFollowResult`, `ThreadReadResult`. **Effects**: `FetchReplies`, `SetThreadFollow`, `MarkThreadRead`, `PersistThreadDrafts`, and `SendMessage` gains `thread_root` and `also_in_channel`. **Changes**: `OpenThreadChanged`, `ThreadReset { root }`, `ThreadSplice { root, at, removed, inserted }` and `ThreadItemUpdated { root, index }` (indices into the replies), `ThreadRootChanged { root }`, `ThreadHistoryChanged { root }`, `ThreadStateChanged { root }`, `ThreadDraftChanged { root }`.

### Where a message lives

A message can be in up to three timelines: the conversation's, the pane's root (a one-row timeline), and the pane's replies. A top-level message is in the conversation's; a reply is in the pane's replies and, when it was sent also to the channel, in the conversation's too (the same message, not a copy); a root is in the conversation's and in the pane's root. Every event about a message (edit, deletion, reaction, thread summary, creation) goes through `homes_of`, so each copy stays current with the same version rules as before. Only the open thread's replies are held; they are not cached.

### The channel

* **Summaries.** A root's `ThreadSummary` has its own version, `as_of`; a row keeps the highest however it arrives (page, response, fetch, edit payload, `ThreadChanged`). "No replies" (`ThreadChanged` with `None`) has the version of its event, so an older page cannot bring the summary back. A change fires `TimelineItemUpdated` for the channel row.
* **Placeholders.** `MessageDeleted` for a root with a summary (the row's or the tombstone's, whichever is newer) leaves a row with `deleted = true`, the placeholder document and the summary; a root without one is removed as in D12. `ThreadChanged { None }` removes a placeholder, and the client forgets the thread's state (the server dropped everyone's). A root that arrives only as a deletion (its creation came as a replayed tombstone, or while the first page was loading) is added as a placeholder when the loaded range could hold it. Placeholders are never unread, not a "New messages" divider, and are cached.
* **Replies.** A reply only in its thread never appears in the channel and never counts in the channel's unread or mention counts; one also sent to the channel is an ordinary row there and counts as any message from someone else. **No reply ever moves the person's read position in the channel**, not even their own that was also sent there (the server's rule).
* **Late pages.** The "page in flight" memory covers summaries too: a thread change, or a deletion with the summary it carried, that arrives for a root that is not loaded yet is applied to a page that was read before it. The memory is cleared whenever a new request starts, because what arrived before it is already in its page.

### The pane

`OpenThread` seeds the root from the channel's row (or fetches it: `ThreadView::root` is `None` until `ThreadRootChanged`; a lost fetch is retried at the next catch-up) and requests the newest replies, paged like history; every request has a unique generation, so an answer for a pane that was closed is never taken for a later one. `RepliesLoaded` with `not_found` closes the pane with a notice; so do losing the conversation (`MemberRemoved`, which also forgets the thread's states, follows, and drafts), the first message of a thread without replies being deleted, and selecting another conversation. A root deleted while it still has replies keeps the pane open on the placeholder. A new snapshot clears the pane's confirmed rows and asks for the root and the newest replies again while an earlier answer may still be on the way; answers for the root are not ordered, so each one is merged (the newer summary wins) and only the last of the fetches in flight settles a failure (a failure after another answer has arrived changes nothing on screen).

### Replying

`SendReply` parses exactly like `SendMessage` (shortcodes, then mentions through `mention_directory`). A reply names its root (a reply to a reply is sent to the same root). It is an operation like a send: an optimistic row in the pane, a journal entry with `thread_root` and `also_in_channel` (serde-defaulted, so a journal written before threads still reads as sends to the channel), the same per-conversation send queue (so commit order is submission order across channel messages and replies), unknown outcomes reconciled through the operation status, a refusal kept as a failed row (`not_found` says the thread's first message was deleted). The row lives in the pane's replies; closing the pane **parks** rows still being sent or failed, and opening it again restores them. A confirmation finds its row either way. Replies whose outcome is unknown and whose thread is not open are asked about again at every catch-up (the person could not otherwise see the row, and the thread may be gone). An also-in-channel reply reaches the channel's timeline when the server confirms it (response or event), not before.

### Read state

The client holds a `ThreadUserState` for the threads the bootstrap lists and the events tell it about, with the tracking of the conversation counts: `thread_as_of` (events at or before it are already in the state), `thread_counted` (replies counted from live events, with whether each mentions the person), and `thread_rebuilt`; all three are cached. A reply from someone else after the read position counts; the person's own reply moves the read position to it and clears the counts, **without an event** (the server's rule; its `ThreadStateChanged` comes only when following starts); a replayed tombstone never counts; an edit moves the mention count by `previous_mentions`; a deletion subtracts only a counted reply (`had_mentions` for one the baseline counted). `ThreadStateChanged` replaces the state at its position. A thread the client holds no state for counts nothing.

**Marking read.** While the pane is open, the window is active, `ThreadAtBottom` is true, and the state shows unread replies, the newest loaded reply is sent (`MarkThreadRead`), one request at a time, forward only, a failure not repeated for the same position until something changes. As for conversations, the answer's counts are used only through the rows: with every reply after the new position loaded the unread and mention counts are rebuilt from the rows; otherwise what was read and known to be counted comes off and the rest waits for the server's state event. A server that clamps lower than asked (the newest reply was deleted) is taken as the position.

### Following

`SetThreadFollow` changes the display at once (a state is shown even for a thread the client holds none for: a *placeholder* with no position, which holds no counts, is never cached, and is dropped when the change settles on "not following") and sends one `PUT`; further changes only change what the person wants and the final wish is sent when the request returns. An unknown outcome repeats the request up to three times, then reverts with a notice. A refusal reverts; `not_found` forgets the thread. A state event that arrives meanwhile does not flip the display; the cache records the server's flag, never an unsaved one.

### Permalinks

A permalink to a reply (the fetched message names `thread_root`, or the loaded row does, even in the channel) selects its conversation, opens the pane, and pages the replies back up to `PERMALINK_MAX_PAGES` until the reply is found; the jump target has `thread: Some(root)`. Not found within the range, or too far back, is a notice. The channel behind keeps its reading position.

### Text that mentions someone

A send, reply or edit whose text contains `@` waits while the conversation's people are not known (a channel whose list has not arrived and whose fetch has not failed): the draft stays, a fetch is started if none is under way, and the text goes, in order, when the list arrives. If the fetch fails the text goes as it is (a name stays plain text). Without this a name typed right after switching channels silently lost its mention.

### Cache and upgrades

The cache carries each workspace's thread states with their tracking (`threads`, serde-defaulted), and the cached messages carry `thread`, `thread_root`, `in_channel` and `deleted` (placeholders). A cache written by protocol 5 is discarded silently (the stamp), and a cache message without the new fields reads as a plain message. The drafts file gains `thread_drafts` (additive; a file without it loads). The journal's new fields are skipped when empty, so entries written by sends to the channel are byte-identical to before.

### Decisions D15 did not settle

* Counting applies only to a thread the client holds a state for; the placeholder state of a pending follow holds none.
* Own reply: the thread read position moves with it, silently (confirmed by the server's `follow_for_reply`); no reply moves the channel's position.
* Only the open thread's replies are held; sends of a closed thread are parked rows.
* An also-in-channel reply is not shown in the channel before its confirmation.
* The thread's root is a separate one-row timeline, so it takes the same version rules as any message.
* Replies in closed threads, and a lost root fetch, are retried at catch-up rather than shown.
* Held text waits for the member list (above).

## Webhooks, bots, and selection restoration (slice 2E)

The contract is `llm-docs/DECISIONS.md` D16 and `PROTOCOL_VERSION` 7.

### Bots

`User::is_bot` marks the identity of a webhook (an app, not a person). `ClientCore::is_bot(user)` is for the "APP" badge; `member(id)` and `display_name(id)` still know bots, so their messages show a name. Bots are **never offered as people**: `members()` (the picker list), `mention_candidates` and `mention_directory` leave them out (a typed `@bot-…` stays plain text), and `OpenConversation`, `AddMembers`, `CreateGroup` and `UpdateGroup` refuse one with a readable action error. A bot's messages are ordinary: they count as unread, take reactions, and are deleted by admins as usual; nobody is their author, so `can_edit_message` is false.

### Webhooks

| Call | Meaning |
| --- | --- |
| `can_manage_webhooks(conversation)` | Admins and owners of the conversation's workspace. The server decides. |
| `webhooks(conversation)` → `&[Webhook]` | Oldest first, as last loaded and kept current by this client's own creations and deletions; empty for anyone who cannot manage them. Other admins' changes show when the list is loaded again, so load it when a dialog opens. |
| `created_webhook()` → `Option<&CreatedWebhook { webhook, url: SecretUrl }>` | The webhook just created, with its one-time address, until `DismissCreatedWebhook`. |

**Inputs**: `CreateWebhook { conversation, name }` (raw text, validated as a display name; a leading and trailing space is trimmed), `DeleteWebhook(id)`, `LoadWebhooks(conversation)`, `DismissCreatedWebhook`. **Action states**: `ActionKind::{CreateWebhook(conversation), DeleteWebhook(id), LoadWebhooks(conversation)}`. **Changes**: `CreatedWebhookChanged`, `WebhooksChanged { conversation }`. **Effects**: `CreateWebhook`, `DeleteWebhook`, `LoadWebhooks`.

* **Validation before asking**: the role, an archived conversation, the name (`Give the webhook a name.`, at most 64 characters, no control characters), and the limit of 10 per conversation when the list is loaded. A double click sends once.
* **The address.** The server keeps only a hash of the secret, so the address exists in the client only as the answer to the creating request. The runtime moves it into `SecretUrl` at once; `SecretUrl` prints as `SecretUrl(<redacted>)`, has no `Display` or `Serialize`, and is read with `as_str()`. It is therefore absent from every debug string (`Input`, `Output`, `Effect`, `ClientCore`), is never cached or saved, and lasts until it is dismissed, the webhook is deleted, the conversation is lost, or the person signs out.
* **Lost answers.** Creating carries no operation id and is a single attempt: a repeat could make a second webhook. When the answer is lost the action fails with words saying it is not known whether the webhook was created, and the list is loaded, where a webhook the person has no address for can be deleted. Deleting is idempotent and is repeated by the runtime; a webhook that is already gone counts as deleted. Loading is retried by the runtime. After a successful creation for a conversation whose list was never loaded, the list is loaded.
* **Refusals** have words: `forbidden` (admins and owners), `not_found`, `conflict` (an archived conversation), `limit_reached` (at most 10).

### Selection restoration

The app reopens on the conversation last open in the workspace if the person is still in it; otherwise the default as before. Every change of the open conversation is saved (`Effect::PersistView`), and the saved value is read at startup (`StartupState::view`). Leaving a conversation forgets it. Each draft keeps its caret: `Input::SetDraftSelection { conversation, anchor, head }` and `SetThreadDraftSelection { root, anchor, head }` report moves; `draft_selection(conversation)` and `thread_draft_selection(root)` give them back as `Option<TextSelection { anchor, head }>`. Offsets are UTF-8 bytes into the draft text.

* **Clamping.** The caret is held as reported and read back for the draft as it is now: an offset past the end becomes the end, and one inside a character or a grapheme cluster (an emoji with a skin tone, a letter with a combining accent, a family emoji) moves back to where that cluster starts. What is saved is clamped too, and a caret saved for text that has since changed is clamped again on load. So the composer never receives an offset that is not valid for its text, whatever order text and caret were reported in.
* **What is not kept**: a caret for a conversation with no draft text (clearing a draft drops it), and anything while signed out. Reply drafts keep theirs inside `ThreadDraft::selection`.
* **Persistence.** Everything goes into the existing drafts file through additive fields (`view`, `thread_drafts[].selection`), so a file written before loads unchanged; the saves share the debounce of the drafts.

### The limit on different reactions

A message holds at most 50 different emoji. Adding a new kind while the server's list is full used to race the withdrawal of another kind made a moment earlier: if the add reached the server first it was refused. Now an add that would exceed the limit **waits** while the person has asked to withdraw another kind that only they use (the withdrawal makes room), stays on display meanwhile, and is sent when the withdrawal returns (an answer, a refusal, or giving up after its repeats) or when an event shows the room is there. A repeat of an add after a lost answer waits the same way. With no withdrawal to wait for, the add is sent at once and the server decides.

### Cache and upgrades

Webhooks and the address are not cached. The cache is stamped with protocol 7, so a cache from protocol 6 is discarded silently. The saved view and carets are not part of the cache: they survive a discarded cache.

### Decisions D16 did not settle

* `members()` leaves bots out; `member(id)` does not.
* Adding a bot to a channel by `AddMembers` is refused (apps join through their webhook).
* The webhook list is not pushed by events; it is loaded on request and kept current by this client's own actions.
* The caret is stored in UTF-8 byte offsets and clamped to grapheme boundaries by the core.
* The last open conversation is saved on every change and restored only when the person is still a member; a conversation they were removed from falls back to the default.
* A withdrawal counts as making room only when nobody else uses that kind.

## Attachments (slice 3A)

The contract is `llm-docs/DECISIONS.md` D17 and `PROTOCOL_VERSION` 8. **File bytes never enter the core.** It handles descriptors, states, and effects; the runtime copies, uploads, downloads, and caches. The only bytes the core passes through are the ones the person pasted (`FileBytes`, at most 25 MiB, shared by `Arc` and never looked into) and the pictures the runtime hands back for the screen (`ImageData`, shared the same way).

### What the UI calls

| Call | Meaning |
| --- | --- |
| `Input::AttachFiles { target, files }` | Add files to a composer. `target` is `ComposerTarget::Conversation(id)` or `ComposerTarget::Thread(root)`. A `LocalFile` is a `FileSource::Path` (dialog, drop) or `FileSource::Bytes` (a pasted picture) and a name the core makes safe. |
| `Input::{RemoveAttachment, CancelAttachment, RetryAttachment}` | Remove a chip in any state; stop reading or uploading and keep a failed "Cancelled" chip; upload a failed chip again (only when `can_retry`). |
| `composer_attachments(target)` → `&[ComposerAttachment]` | `id`, `name`, `size`, `media_type_guess`, `state` (`Reading`, `Uploading { sent, total }`, `Uploaded`, `Failed { reason, can_retry }`), and `source` for previewing an image chip before it is uploaded. |
| `Input::SendMessage` / `SendReply` | Unchanged. Empty text is accepted when the composer has files (reading, uploading, or uploaded); a failed chip blocks the send with a notice. |
| `TimelineItem::attachments`, `TimelineItem::upload` | The files of a message (placeholders while it is being sent, the server's afterwards) and `Some(UploadProgress { files: Vec<PendingFile> })` while this client is sending it. |
| `Input::DiscardOperation { conversation, operation }` | Remove a failed row and delete its copies. |
| `Input::DownloadAttachment { attachment, destination }`, `CancelDownload(id)`, `DismissDownload(id)`; `download(id)` | `Downloading { received, total }`, `Done { path }`, `Failed { reason }`. |
| `Input::LoadThumbnail(id)`, `LoadFullImage(id)`, `ReleaseFullImage(id)`; `thumbnail(id)`, `full_image(id)` | `ImageState::{Loading, Ready(ImageData), Failed}`. |

**Changes**: `ComposerAttachmentsChanged { target }`, `DownloadChanged { attachment }`, `ImageChanged { attachment }`, and `TimelineItemUpdated` / `ThreadItemUpdated` for a sent message's progress. **Runtime reports** (the UI never sends these): `FileStaged`, `UploadProgress`, `UploadResult`, `DownloadProgress`, `DownloadResult`, `ImageLoaded`. **Effects**: `StageFile`, `UploadFile`, `CancelUpload`, `ReleaseFiles`, `DownloadAttachment`, `CancelDownload`, `FetchImage`, `ForgetAttachments`, and `attachments` on `SendMessage`.

### One file's life

The core gives each chosen file an `AttachmentId` (the id the upload and the sent message use, so a retried upload is the same upload). A file in a composer is one of `Reading` (`StageFile` asked the runtime to copy it into its encrypted outbox and check its size), `Stopped`, `Queued` (waiting for a slot), `Uploading`, `Uploaded`, or `Failed`; the chip shows the first four as `Reading`/`Uploading`. A file is uploaded as soon as its copy is in, so by the time the person sends, most are already `Uploaded`.

* **Limits.** Ten files to a composer (the rest are dropped with a notice), 25 MiB each. Pasted bytes over the limit become a failed chip at once; a path over the limit is reported by the runtime from the file's metadata before a byte is copied. Both read `<name> is 31.2 MiB; files can be at most 25 MiB.` and cannot be retried.
* **Upload manager.** At most three uploads run at once across the whole app; the rest wait in order. Progress only moves forward; a report for an older attempt is ignored (every attempt has a `generation`, as does every copy). An upload of unknown outcome is **repeated with the same id** up to three times, then the chip is `Failed { "Couldn't upload <name>. Check your connection.", can_retry: true }`. The core does this, not the runtime: the runtime makes one attempt per `UploadFile`. Refusals have words: `unsupported_media` (images must decode), `payload_too_large`, `limit_reached` (retryable), `forbidden`, `conflict`, `not_found`, `rate_limited`.
* **Cancel and remove.** `CancelUpload` stops the transfer; a late answer from it is ignored by its generation. `ReleaseFiles` stops anything still running for the file and deletes its copy.

### A message with files

`SendMessage` takes the files out of the composer into the message (`LocalOp`). The message is an ordinary operation with three more stages: `Staging` (a file is still being copied: the journal waits, so an entry never names a file that is not in the outbox), then `Persisting` (journal), then `Uploading` (some file is not on the server), then `Queued`/`Sending` as before. A message waiting on its files **blocks the messages behind it** in the conversation, as any message ahead in the queue does, so order is kept.

* **The row.** The pending row appears at once with placeholder attachments and `upload: Some(..)`; each file's state is `Reading`, `Uploading { sent, total }`, or `Uploaded` ("Uploading 2 of 3 files" is `uploaded_files()` of `total_files()`). `Delivery` stays `Pending`.
* **Failure.** A file that cannot go up fails the row (`RetryKind::NewOperation`, the journal entry is released because nothing was sent) with words that name the file. The copies are kept for **Retry**, which makes a new operation with the same files and uploads them all again (the server may have forgotten them; a copy it still holds is simply kept, since the id is the same), copying again any file whose copy had failed. **Discard** deletes the row and the copies. A reply to a thread that no longer exists releases its copies at once, since nothing can ever send it.
* **Unknown outcome.** The send is reconciled by `QueryOperationStatus` as before. If the server has no record, a message whose files are all `Uploaded` is simply sent again; one recovered after a restart (files not known to be on the server) uploads them first, then sends.
* **Restart.** The journal entry carries `attachments: [{ id, name, size }]` (additive: an entry written before loads as a send without files). The runtime keeps the copies the journal names and deletes the rest at start. The recovered row shows its files; if a copy is gone the row fails with `A file for this message is no longer available on this computer: <name>.`
* **Settling.** A confirmed message (by the answer, the status, or the event) releases its copies. Leaving a conversation, signing out, and a message deleted before it was heard back do too.

### Messages that are only files

`MessageDocument::empty()` is valid on the wire for a message with files. Everything that reads text copes: `plain_text()` and `to_markdown()` are empty (`edit_text` returns `""`), `message_excerpt` reads as the file's name (or `N files`), unread and mention counting never read the document. `EditMessage` with empty text is accepted when the message has files (the files stay; edits never change them), and refused with the old notice when it has none.

### Previews and downloads

The core holds at most 512 thumbnails and 32 MiB of them, and two whole images; the oldest go first and are asked for again when a row is drawn (a hit in the runtime's cache, so cheap). At most four fetches run at once and at most 64 wait. `LoadThumbnail` is idempotent and a `Failed` thumbnail stays failed until the connection catches up (rows ask on every draw); `LoadFullImage` on a `Failed` image asks again (the viewer's "Try again"). Deleting a message drops what is held for its files and tells the runtime (`ForgetAttachments`). A download is one at a time per file; its temporary file lives beside the destination and the result is checked against the SHA-256 before the rename.

### Runtime

* **Blobs.** The outbox and the image cache hold files of up to 25 MiB, so they are sealed in chunks, not in one piece: `LZBL`, format, kind, 16 random bytes, then 64 KiB chunks each sealed with XChaCha20-Poly1305 under a nonce of the random bytes and the chunk number, with the header and a "last chunk" flag authenticated. A chunk cannot be moved, dropped, repeated, or the end cut off without the read failing. The key is derived from the profile's state key for blobs only.
* **Outbox** (`<profile>/outbox/<id>.bin`). One thread copies files in order. A copy is written under `<id>.part` and renamed, so a crash leaves a whole copy or none. `ReleaseFiles` sets the cancel flag of a copy in progress and queues the deletion behind it, so cancelling and starting again (`Release`, `Stage`) ends with the new copy. With no secure storage there is no key and the runtime refuses to keep a copy: `Couldn't keep a copy of <name>: secure storage isn't available, so a safe copy can't be kept.`
* **Uploads.** `PUT` with the body streamed from the outbox (decrypted a chunk at a time by a thread, four chunks ahead), `Content-Length` and the percent-encoded name header, one attempt, a timeout of 30 s plus the size at 16 KiB/s, and progress reported at most every 150 ms. A copy that cannot be read ends the upload with `Unreadable` rather than as a network failure.
* **Downloads.** Streamed to `.lazy-<id>.part` beside the destination while the SHA-256 is computed, checked against the attachment's, then renamed over the destination; cancelling, a mismatch, or any failure deletes the temporary file. A failure to write is `Disk(reason)` ("No space left on device").
* **Images** (`<profile>/images/`). A memory layer of 8 MiB over an encrypted LRU of 64 MiB on disk; a file that cannot be read is deleted and fetched again without a word. Reads are retried like other reads.
* **Sign-out** deletes both directories and stops every transfer.

### Cache and upgrades

The cache is stamped with protocol 8, so a cache from protocol 7 is discarded silently; a cached message carries its files. A journal written before attachments loads unchanged.

### Decisions D17 did not settle

* **Composer files are not kept across a restart.** A chip does not survive quitting the app (the draft text does); only files of messages that were sent do. Files not named by the journal are deleted at start.
* Files are copied and uploaded **as soon as they are chosen**, not when the message is sent, so a person who removes a chip has already used an upload slot (and the server keeps an unattached upload for 24 hours).
* A failed chip blocks the send with a notice rather than sending the rest.
* A message waiting for its files **blocks later messages** in its conversation.
* Retrying a failed message uploads all its files again.
* A tombstone's own attachment list is ignored: a deleted message shows none.
* The journal is written when the copies are in, not at the moment of sending.
* Thumbnails of rows the core no longer holds are not found by a deletion (their cache entries age out of the 64 MiB LRU).

## Custom emoji (slice 3B)

The contract is `llm-docs/DECISIONS.md` D18 and `PROTOCOL_VERSION` 9. `ReactionEmoji` is an enum (`Unicode` or `Custom(EmojiId)`; `glyph()`, `unicode()`, `custom_id()`, and `to_string()` = `custom:{id}`), and a document can hold `Inline::Emoji { id, name, marks }`.

### What the UI calls

| Call | Meaning |
| --- | --- |
| `custom_emoji()` → `&[CustomEmoji]` | Every emoji of the workspace, live and deleted, ordered by name then id. Seeded by the bootstrap, kept current by `EmojiChanged` events (applied by id; a deleted emoji is never brought back by an older event), cached. |
| `custom_emoji_by_id(id)`, `live_custom_emoji()`, `custom_emoji_label(id)` | By identity; the usable ones; the name for display (`None` when the core has never heard of the emoji; a deleted one still has its name). |
| `custom_emoji_search(query, limit)` | For the picker: live emoji whose name starts with the query, then those that merely contain it, each group by name. Empty query: all. |
| `custom_emoji_suggestions(prefix, limit)` | For autocomplete after `:`: live names that start with the prefix; nothing for an empty prefix. |
| `can_manage_emoji()` | Admins and owners. |
| `Input::LoadEmojiImage(id)`; `emoji_image(id)` → `Option<&ImageState>` | The image, once asked for. Idempotent, deduped, 4 fetches at a time and at most 128 waiting; a `Failed` image stays failed until the connection catches up (then `Change::EmojiImageChanged` so it is asked for again). Not asked for a deleted or unknown emoji. The core holds at most 600 images / 12 MiB. |
| `Input::AddCustomEmoji { name, file }`, `RenameCustomEmoji { id, name }`, `DeleteCustomEmoji(id)` | Admin actions. Progress and readable errors are `action(ActionKind::AddCustomEmoji / RenameCustomEmoji(id) / DeleteCustomEmoji(id))`. |

**Changes**: `CustomEmojiChanged`, `EmojiImageChanged { emoji }`, and `EmojiPrefsChanged` when an emoji's liveness changes what the recent ones show. **Effects**: `UploadEmoji`, `RenameEmoji`, `DeleteEmoji`, `FetchEmojiImage`, `ForgetEmojiImages`. **Runtime reports** (the UI never sends them): `CustomEmojiUploaded { emoji, result }`, `EmojiImageLoaded { emoji, result }`; renames and deletes answer as `ActionResult` with `ActionOutcome::CustomEmoji` / `Done`.

### In messages

`mention_directory(conversation)` also holds the live emoji of the conversation's workspace (`MapDirectory::insert_emoji`), so `SendMessage`, `SendReply`, and `EditMessage` turn `:name:` into `Inline::Emoji` exactly when autocomplete would offer it; a name that is deleted, unknown, or escaped (`\:name:`) stays text. Standard shortcodes are replaced first, so `:tada:` is always the standard emoji (a custom name can never be one). `edit_text` writes an emoji back as `:name:` and a literal `\:name:` as `\:name:`, so editing never turns text into an emoji. Nothing waits for a list of people for `:` (that rule is for `@`). The plain-text projection (excerpts, copy) of an emoji is `:name:`.

### Reactions and recent emoji

`ToggleReaction` with `ReactionEmoji::Custom` is a standard reaction in every way: optimistic, the 50-kind limit, the rule that an add waits for the withdrawal that makes room. A **deleted or unknown** emoji cannot be newly added (a notice, nothing sent) but a reaction already made with it can be withdrawn; the summaries keep the id and the UI shows `:name:` muted. `RecordEmojiUse` accepts custom emoji. The preferences file stores them as `custom:{id}` (version still 1: additive, a file from before loads unchanged). **What `emoji_prefs().recent` shows leaves out custom emoji that are not live; what is saved keeps them** until newer ones push them out, so an emoji that is briefly unknown (a bootstrap not yet applied) is not forgotten.

### Admin actions

They are not messages: no journal, no outbox, no reconciliation by operation id.

* **Add.** The core chooses the `EmojiId`, checks the role, the name (`EmojiName::parse`, ':' around it and spaces forgiven), that no live emoji has the name, the limit of 500 live emoji, and a pasted image of at most 512 KiB; a path is checked by the runtime from its metadata before it is read. Then one `UploadEmoji` (`PUT` with `x-emoji-name`). **An upload of unknown outcome is repeated by the core with the same id up to three times** (the id makes it idempotent), then fails with `Couldn't reach the server…`. One add at a time; an answer for an add that was given up on is ignored. Success adds the emoji to the list from the answer (the event that follows changes nothing).
* **Rename** (`PATCH`, one attempt): refused locally for the same name, a clash with another live emoji, or a bad name. **Delete** (`DELETE`, repeated by the runtime after a lost answer): a `not_found` means it is gone, which is what was wanted. Both update the list from the answer, and the events do the same by id.
* **Refusals have words**: `name_taken`, `limit_reached`, `unsupported_media` ("Use a PNG, JPEG, GIF, or WebP picture."), `payload_too_large`, `forbidden`, `not_found`. A double submit sends once.

### Runtime

`UploadEmoji` reads the file (at most 512 KiB, refusing a larger one before reading it), picks `Content-Type` from the first bytes, and sends it whole. Images are fetched with `GET /v1/emoji/{id}` (retried like other reads), kept in `<profile>/emoji/` in the same encrypted chunked blobs as the image cache, 16 MiB at most, least recently used first, and tolerate damage silently (a file that cannot be read is dropped and fetched again). A rename keeps the cached image (it is named by identity); `ForgetEmojiImages` on a deletion drops it; sign-out removes the directory.

### Cache and upgrades

The cache is stamped with protocol 9, so a cache from protocol 8 is discarded silently; a cached workspace carries its emoji (a field that is absent reads as none). The preferences file and the journal are unchanged.

### Decisions D18 did not settle

* **The emoji list is one flat list across workspaces** (like user groups); `can_manage_emoji()` and the add use the primary workspace.
* **A reaction with an emoji the core does not know is refused like a deleted one**, since only live emoji are offered.
* **Recent emoji are hidden, not dropped,** while not live (see above).
* **A deleted emoji is final in the core**: an `EmojiChanged` that says live for an emoji already deleted is ignored (the server never undeletes, and the order of an event and an answer is not guaranteed).
* A rename event for an emoji replaces its name even if an older answer arrives later; the list converges when the stream is caught up.
* An upload is repeated three times for an unknown outcome, but a rename is not repeated (it could be refused for a name someone took meanwhile).
* Images of emoji the core does not hold (deleted while the app was away) age out of the 16 MiB cache.

## Search (slice 3C)

The contract is `llm-docs/DECISIONS.md` D19 and `PROTOCOL_VERSION` 10. The core parses the text with the server's own rules (`lazy_domain::search::SearchQuery::parse`), so a query that cannot be used is explained without a request.

### What the UI calls

| Call | Meaning |
| --- | --- |
| `search()` → `Option<&SearchView>` | `None` until `OpenSearch` (or the first `SetSearchQuery`). The view: `query` (the text typed), `parsed` (`Result<SearchQuery, SearchError>`; the filters as chips, or why it cannot be used), `sort`, `status` (`Idle`, `Loading`, `Ready`, `Failed { reason, can_retry }`), `hits`, `has_more`, `truncated`, `at_limit`, `generation`. |
| `Input::OpenSearch`, `CloseSearch` | Open the view; close it, forgetting the hits and stopping a request in flight (`Effect::CancelSearch`). The recent searches stay. |
| `Input::SetSearchQuery { text }` | Records and parses the text and **asks for nothing**: the screen waits for a pause (or Enter) and sends `RunSearch`. Opens the view if it is closed. |
| `Input::RunSearch` | Asks for the first page (20) of the typed text, trimmed. Ignored when the text does not parse. A newer request makes every older one irrelevant. |
| `Input::LoadMoreSearch` | The next page, from where the hits end, **of the run the hits answer** (its text and order, whatever has been typed since). Honoured only when `has_more && !at_limit` and nothing is loading; it also retries a failed next page. |
| `Input::SetSearchSort(sort)` | `Relevance` or `Recent`; runs again. |
| `Input::OpenSearchHit(index)` | Opens the hit through `open_permalink` (a loaded message is jumped to; a reply opens its thread; history is paged to an old one; a channel the person has not joined gives the join offer). The view stays open: the screen closes it when it has what it wanted. Records the run's text as a recent search. |
| `recent_searches()` → `&[String]` | The last 10 searches whose result was opened, most recent first, distinct ignoring case, trimmed, each at most 200 characters. |
| `search_hit_title(hit)`, `search_hit_joined(hit)` | `#design`, or the other people's names for a conversation (works for a conversation the core does not hold); whether the person is in it. |
| `opening_link()` | A permalink (and so a search hit) is still being looked for: fetched, or its history being paged. |

**Changes**: `SearchChanged` (the view), `RecentSearchesChanged`. **Effects**: `Search { workspace, generation, params }`, `CancelSearch`, `PersistRecentSearches(list)`. **Runtime report** (the UI never sends it): `SearchResult { generation, result }`.

### Requests and answers

Every request (a run, a next page, a re-run) takes the next number of a counter that only goes up and survives closing the view. `view.generation` is the latest; an answer is shown only if it answers that request, so an answer that arrives late (after a newer request, after the view was closed or reopened, after sign-out) changes nothing. A run **clears the hits** and sets `Loading`, so the hits on screen always answer the last run, even though `view.query` may be ahead of them while the person types; `Loading` with hits means the next page. Appended pages skip a hit already shown (same message and kind), since results shift when messages come and go; the page size is the core's (`SEARCH_PAGE`), and the server may return fewer. `at_limit` is `has_more` with 200 hits shown: the screen says to narrow the search.

**Failures** (`status`): `invalid_request` shows the server's reason and cannot be retried; `unavailable` ("took too long") becomes "That search took too long. Narrow it with in: or from:" (no final period: the screen adds its own) and can be retried; a lost connection is "Couldn't reach the server." and can be retried; `rate_limited` can be retried; `forbidden` and `not_found` mean the workspace can no longer be searched (a notice, no retry); `unauthenticated` expires the session like any other request and closes the search. A failed first page leaves no hits; a failed next page keeps them.

### While the hits are on screen

* A **deleted** message stops being a hit (events and the answer to the person's own delete), and one deleted while a request was out is removed from its answer before it is shown.
* An **edit** updates `hit.message` when its revision is newer (also for an edit that happened while the request was out) but **not `hit.snippet`**: that is the server's excerpt from when it searched, and stays until the next run.
* After a **resync** (a snapshot replaces the event log, so deletions and edits may have been missed) the core asks again for the first page of the run it shows or waits for.
* Someone **removed** from a private conversation keeps its hits until the next run; opening one gives the permalink's "can't be read" notice.

### Recent searches

Recorded only by `OpenSearchHit` (a search nobody opened from is not worth remembering), as the text of the run the hits answer. Saved by `Effect::PersistRecentSearches` after the runtime's usual pause; loaded into `StartupState::recent_searches` and repaired there (blanks, repeats, long entries, and the count). Sign-out clears them, in memory and on disk.

### Runtime

`Effect::Search` is one `GET /v1/workspaces/{id}/search` with the parameters in the query string, percent-encoded by `reqwest` (`q`, and `limit`, `offset`, `sort` only when set). It is a read: an unknown outcome is repeated with backoff like any read. **A `503` whose body is the server's `unavailable` is the one failure that is not unknown**: it is `Rejected`, because a search that timed out would only time out again (every other request treats `unavailable` as an unknown outcome). The runtime keeps **one** search: a new `Search`, `CancelSearch`, and sign-out hang up on the one waiting, and a hung-up request reports nothing. The recent searches are `<profile>/recent-searches.json`: plain JSON `{"version": 1, "queries": [...]}` written atomically beside `emoji-prefs.json` by the same saver (so the two never lose each other's write); a missing, damaged, or differently versioned file is no searches, silently; unknown fields are ignored; sign-out deletes it and drops a save in flight. Results are never saved.

### Cache and upgrades

Nothing in the content cache or the journal changed. The recent searches file is new and versioned from the start; protocol 10 invalidates a cache stamped 9 as every protocol bump does.

### Decisions D19 did not settle

* **A run clears the hits** (rather than keeping the old ones until the new answer) so that hits always answer the last run; the screen shows a spinner.
* **Hits answer the last run, the box may be ahead**: `LoadMoreSearch` and a resync use the run's text, `SetSearchSort` and `RunSearch` use the typed text.
* **The search is of the primary workspace** (like emoji and groups).
* **Recent searches are recorded by opening a hit,** not by running; case-insensitive dedupe; the newest spelling wins.
* **`view.generation` is 0** for a view that has asked for nothing, and numbers never repeat within a session (even across closing and reopening).
* **An edit does not touch the snippet** and a deletion removes the hit; nothing else changes a shown hit.
* **A resync re-runs** the shown search (the first page), because a skipped log can hide deletions and edits.
* **No cancellation reply:** the runtime says nothing for a request it hung up on; the core's generations make a reply that was already on its way harmless.
* **`unavailable` is a retryable failure** for search only.

## Notifications, status, and the thread inbox (slice 3D)

The contract is `llm-docs/DECISIONS.md` D20 and `PROTOCOL_VERSION` 11. The rules are one pure function, `lazy_domain::notification::decide`; the core supplies what it needs (the person's settings and preference for the conversation, whether they follow the thread, what the message is, and the time of the *event*) and decides what to show.

### What the UI calls

| Call | Meaning |
| --- | --- |
| `notification_settings()` → `&NotificationSettings` | What the person sees, including a change that is not saved yet. Seeded by the bootstrap, replaced by `NotificationSettingsChanged` events. |
| `conversation_notification_prefs(conv)` → `Option<&ConversationNotificationPrefs>`, `effective_level(conv)`, `is_muted(conv)` | The person's own preference (none when it is the default), the level that applies (its own, else the workspace's for its kind), and the mute. |
| `Input::SetNotificationSettings(settings)`, `SetConversationNotificationPrefs { conversation, level, muted }`, `PauseNotifications { until }` | Change them. Optimistic: the new value shows at once. `PauseNotifications` edits `dnd_until` (`None` resumes; quiet hours are untouched). Quiet hours that cannot work (`is_valid`) are refused with a notice and nothing changes. |
| `notifications_paused()` | A snooze or quiet hours at the core's clock; false until the clock is set. |
| `status_of(user)` → `Option<&UserStatus>`, `Input::SetStatus(Option<UserStatus>)`, `make_status(text, emoji, expires_at)` | A person's status unless it has ended at the core's clock (the person's own includes an unsaved change; it is also on `member(me).status`). `make_status` checks a status the person typed and says what is wrong in words; `SetStatus` refuses a status that has ended or names a custom emoji that is not live. |
| `Input::Clock(timestamp)` | The time, from the runtime (before the first realtime frames of a batch, and every 30 seconds). Statuses that end and a snooze that runs out are announced as changes. |
| `attention_count()` | The mentions in unmuted channels, plus the unread messages of unmuted direct and group conversations (a mention there is one of them), plus the unread replies of followed threads in unmuted conversations. |
| `Input::NotificationActivated { conversation, message }` | A notification was clicked: open the message as a permalink does (a reply opens its thread). The host raises the window. |
| `inbox()` → `Option<&InboxView>`, `inbox_entry_title(entry)`, `inbox_entry_joined(entry)`, `inbox_unread_total()` | The thread inbox (below). |

**Changes**: `NotificationsChanged` (settings, preferences, paused), `StatusChanged`, `InboxChanged`, `AttentionChanged`. **Effects**: `SetNotificationSettings`, `SetConversationNotificationPrefs`, `SetStatus`, `LoadInbox`, `CancelInbox`, `MarkInboxRead` (the runtime), and `Notify(DesktopNotification)`, `ClearNotifications { conversation }`, `RetractNotification { message }`, `SetBadge(count)` (the platform part of the host; the runtime ignores them). **Runtime reports** (the UI never sends them): `NotificationSettingsResult`, `ConversationPrefsResult { conversation }`, `StatusResult`, `InboxLoaded { generation }`, `InboxReadResult`.

### Saving settings, preferences, and status

Each is a whole value replaced with one idempotent `PUT`, so none of this is a journaled operation: repeating the same `PUT` is always safe. The person's change shows at once. Only one request per value is out at a time; a change made meanwhile waits for the answer and is then sent (the screen never flickers back to the value in flight). An **unknown outcome repeats the latest wish, up to three attempts in all**, then the value the server last said is shown again with a notice ("Couldn't save …: the server could not be reached"). A **refusal** shows the server's last value at once with a notice carrying its reason. The server's events (`NotificationSettingsChanged`, `ConversationNotificationPrefsChanged`, `UserStatusChanged`, also for the person's own saves) replace what the server last said; a change that is not saved yet stays on screen over them, so an older event never flips it. When nothing is pending the shown value is the last event or answer, which is the server's after the stream is delivered. Resetting a preference to the default removes it. The bootstrap seeds all three; sign-out forgets them. Nothing here is cached except that the users in the content cache carry their `status` (a cache written before has none).

### Desktop notifications

For every `MessageCreated` event the core builds an `IncomingMessage` (the conversation's kind, reply or not, also in the channel, whether it names the person in `mentions.users`, whether it used `@channel`) and calls `decide` with the *event's* `occurred_at`. It emits `Effect::Notify` only if **all** of these hold: the event arrived **live** (the workspace's connection had caught up: replays, the burst after a reconnect, and anything between a snapshot request and the next catch-up are not news); the message is not a tombstone; `decide` accepts it (never the person's own, never a muted conversation, never at level nothing, and only the reasons the settings allow) and says it is not paused; the settings have desktop notifications on; and the person is **not looking at it**: window active and the conversation selected and (the message is in the conversation's list, or it is a thread-only reply whose thread is the open pane). Edits never notify. Bots follow the same rules. A paused message still counts in the badge.

A notification says: title `#name` for a channel, the people's names for a group, the sender for a direct message; body `Sender: text` on one line, at most 140 characters (`[N files]` for a message that is only files, a custom emoji as `:name:`); with "show message text" off, `New message` for a direct message and `Sender: New message` elsewhere. `tag` is the conversation's id and `count` is how many notified messages of that conversation have not been seen: a newer notification replaces the earlier one and, from two on, says `3 new messages. Latest: Sender: text` (or only `3 new messages` with text hidden).

The core withdraws what is seen: `ClearNotifications { conversation }` when the notified messages of a conversation are read (its read position passes them, whether here or on another device, or the person is looking at it at the bottom with the window active; a thread-only reply when its thread is read or open at the bottom), at most once for a set; `RetractNotification { message }` when a notified message is deleted; and everything of a conversation the person leaves. It does not re-post the remaining ones.

### The badge

`SetBadge(count)` is emitted after any input that changes `attention_count()`, never otherwise (the first value, 0, is implicit), together with `Change::AttentionChanged`; sign-out announces 0. Muting a conversation takes it out of the count and dims nothing else: the unread and mention counts themselves never depend on a preference.

### The thread inbox

`inbox()` is `None` until `OpenInbox`. `InboxView { entries: Vec<InboxEntry>, unread_only, status: InboxStatus, has_more, marking_read, generation }`, where `InboxStatus` is `Idle`, `Loading` (with entries: the next page), `Ready`, or `Failed { reason, can_retry }`. `OpenInbox` opens it and asks for the first page (20); `LoadInbox { unread_only }` asks for the first page again with or without the filter (the entries clear while it loads); `LoadMoreInbox` asks for threads older than the oldest shown (it also retries a failed next page, which keeps the entries); `CloseInbox` stops a request in flight. Requests have generations that only go up, and an answer is shown only if it answers the last request (as for search). Opening an entry is the existing `Input::OpenThread`.

**Entries follow events.** The thread state of an entry is the core's own thread state (which counts new replies as they arrive, since the server announces a thread's state only when it is followed, unfollowed, or read). A `ThreadChanged` event updates the summary (by version) and moves the thread to its place, or removes it when no replies are left; a reply that arrives becomes the entry's newest reply; an edit updates the root and reply shown; a deleted root shows as deleted and a deleted newest reply is no longer shown; unfollowing removes the thread; leaving a conversation removes its threads. When an event says something an entry cannot absorb (a followed thread that is not listed becomes active or followed) the core **asks for the first page again, quietly** (status and entries stay as they are until it is answered, and the page is then the whole list: paging starts over). An event that arrives while a request is out asks again once it is answered, because the answer may predate the event.

`MarkInboxRead` shows every entry read at once and sends one `POST`; the server marks at most 500 threads (`INBOX_READ_CAP`), and the core asks again while it answers 500 (at most 20 times). A failure says so in a notice and asks for the list again. While it is out the entries are not overwritten by the core's thread states.

### Runtime

The three `PUT`s and the `POST` are single attempts (the core repeats the idempotent ones). The inbox `GET` is a read: retried on an unknown outcome, one at a time (a newer page or sign-out hangs up on the older, which reports nothing), through the same helper as search. The runtime sends `Input::Clock(now)` before the first frame of a batch of realtime frames whenever more than a second has passed since the last one on that connection, and every 30 seconds. Notifications, statuses, settings, and the inbox are never saved by the runtime.

### Cache and upgrades

`PROTOCOL_VERSION` 11 discards a cache stamped 10 silently, as every bump does. A cache message or member without `status` reads as none. Settings, preferences, and the inbox are not cached: the bootstrap supplies them.

### Decisions D20 did not settle

* **`mentions_me` is "the person is in `mentions.users`"**; `@channel` is `mentions_channel` (the shared `Mentions::includes` treats `@channel` as naming everyone, which would make every `@channel` a mention).
* **A mention inside a direct or group conversation is counted once** in `attention_count()` (as one of its unread messages), not twice.
* **Channel titles carry `#`** in notifications; a direct message is titled by the sender, a group by its people.
* **The hidden-text body is `New message`** in a direct message (the title says who) and `Sender: New message` elsewhere.
* **Notifications that are paused are not held** (nothing popped up, so there is nothing to clear or retract); the badge still counts them.
* **A snapshot request ends liveness** until the next catch-up, so nothing in between notifies.
* **Looking at a conversation** means the window is active and it is selected (not that the view is at the bottom); clearing needs the bottom.
* **Settings are of the primary workspace** (like emoji and groups).
* **Saving is "the latest wish, three attempts, then revert"**, not a journal: the `PUT`s are idempotent.
* **The inbox refreshes by asking for the first page again** rather than fetching the one thread an event names, and a refresh restarts paging.
* **A thread known only to the inbox** (followed but not in the bootstrap's newest 500) shows the state the server gave and is not counted further.

## Discovery (slice 3E)

The contract is `llm-docs/DECISIONS.md` D21 and `PROTOCOL_VERSION` 12. Four lists load a page at a time (the saved messages, the people directory, one person's profile, the channel directory) the way the thread inbox does, and the quick switcher is a pure function of what the core already holds.

### What the UI calls

| Call | Meaning |
| --- | --- |
| `is_saved(message)` | Whether a message is saved, including a change that is not saved yet. The bootstrap carries the newest 2,000 saved ids; `SavedChanged` events keep it current. |
| `Input::SetMessageSaved { message_id, saved }` | Optimistic: the marker flips at once. One idempotent `PUT` carries the latest wish; an unknown outcome repeats it up to three times, then the server's last value is shown again with a notice; a refusal does the same at once. Not journaled. |
| `saved()` → `&SavedView { open, items: Vec<SavedItem>, has_more, status: LoadStatus }`; `OpenSaved`, `CloseSaved`, `LoadMoreSaved` | The saved messages, newest saved first (20 a page, paged by the last item's `cursor`). Unsaving takes the item off the list at once. |
| `people()` → `&PeopleView { open, query, people: Vec<Person>, has_more, status }`; `OpenPeople`, `ClosePeople`, `SetPeopleQuery(text)`, `LoadMorePeople` | The people directory (50 a page). Each text asks for the first page; the newest wins. A text over 100 characters asks for nothing and says so. |
| `profile()` → `Option<&ProfileView { user_id, person: Option<Person>, status }>`; `OpenProfile { user_id }`, `CloseProfile` | One person. While `person` is `None` show `member(user_id)`; a person already in the directory is shown at once and refreshed. A person who is not in the workspace is `Failed { can_retry: false }`. |
| `browse()` → `&BrowseView { query, joined, sort, channels, has_more, status }`; `BrowseChannels`, `SetBrowseQuery`, `SetBrowseJoined`, `SetBrowseSort`, `LoadMoreBrowse`, `CloseBrowse` | The channel directory (50 a page). `BrowseChannels` opens it with the settings it already has. Changing any setting asks for the first page again. A join or leave updates `joined` in the loaded rows without a request (and a row joined while its page was on the way arrives joined). `ActionKind::Browse` and `browse_results()` are gone; the status is on the view. |
| `quick_switcher_results(text)` → `Vec<QuickSwitcherItem>`; `Input::ChooseQuickSwitcher(target)` | The switcher (below). |
| `recent_conversations()` → `&[ConversationId]` | The conversations visited, most recent first, at most 20. |

`LoadStatus` is `Idle`, `Loading` (with items: the next page), `Ready`, or `Failed { reason, can_retry }`; it is the inbox's `InboxStatus` (still available under that name). **Changes**: `SavedChanged`, `PeopleChanged`, `ProfileChanged`, `BrowseChanged`. **Effects**: `SetMessageSaved`, `LoadSaved`/`CancelSaved`, `LoadPeople`/`CancelPeople`, `LoadProfile`/`CancelProfile`, `LoadBrowse`/`CancelBrowse`, `PersistRecentConversations`. **Runtime reports** (the UI never sends them): `MessageSavedResult`, `SavedLoaded`, `PeopleLoaded`, `ProfileLoaded`, `BrowseLoaded`, each paged result carrying the generation of its request.

### Requests, answers, and events

Each list numbers its requests with a counter that only goes up (and survives closing it); an answer is shown only if it answers the request made last, so a late answer to a text the person has since changed, or to a list since closed, changes nothing. Failures say what happened and whether asking again can help; a failed next page keeps the rows. After a **snapshot resync** (the log was skipped) each list that has been loaded asks for its first page again, quietly: it keeps showing what it had until the answer comes, and the ids of saved messages come from the new bootstrap.

Events keep what is shown in step: a `SavedChanged` for a message not in an open list asks for the first page again (its place is the server's to say) when the server says it is saved, and takes it off the list when it says it is not; a deleted message leaves the saved list, an edited one shows its new revision, leaving a conversation takes its items away; a `UserStatusChanged` updates the copies of that person in the directory and the profile.

### Saving: what asks for the list again

Asking to save a message flips the marker and sends the `PUT`; the open list is **not** asked for until the server says so (the answer to that `PUT`, or the event), because the server has not heard yet. Undoing a failed removal puts the item back by asking for the list again. A removal waiting to be sent keeps its item off any page that lists it.

### The quick switcher

`quick_switcher_results(text)` gives at most 12 results (`QUICK_SWITCHER_LIMIT`).

* **No text**: the conversations visited most recently (the most recent is usually the one open), then those with unread messages that are not muted and not archived, ordered by mentions, then unread count, then name; archived conversations last.
* **Text**: the person's channels (matched on the name; a `#` in the title is not matched), direct and group conversations (the people's display names, or one of their usernames, which counts a little less), people with no direct conversation yet (display name or username; choosing one opens it; never yourself or an integration bot), and the places "Threads", "Saved", and "Search" when their words match. Score is `lazy_domain::fuzzy_match`'s plus a bonus for how recently the conversation was visited (3 for each place nearer the front of the list) and a small one for unread messages and mentions (none when muted). Live results come before archived ones, then by score, conversations before people before places, then by name. The last result is always "Browse channels matching …" (the 12th at most). With nothing to match and no one signed in, nothing.
* `matched` holds positions in the *title* (the `#` counts as a character), empty when the match was on a username, whose `@username` is then the subtitle. `unread`, `mentions`, `muted`, and `archived` come from the core's state for the row.
* **Choosing**: a conversation is selected (one the person is not in does nothing); a person opens or creates the direct conversation (`OpenConversation`); "Threads", "Saved", and "Search" open those views (search opens empty); "Browse channels" opens the directory with that text.

### Recently visited conversations

`change_selection` is the one place the selection changes, so any route (the sidebar, the switcher, a permalink, the default at start, a restored selection) counts. The list is per profile, most recent first, at most 20, repeats removed, and saved with `PersistRecentConversations` whenever it changes. A conversation the person is no longer in stays on the list (it may come back) and is left out of the switcher. The runtime keeps it in `<profile>/recent-conversations.json` (plain JSON, `{"version": 1, "conversations": [...]}`, written atomically by the same saver as the other preferences; a missing, damaged, or differently versioned file is nothing, silently; entries that are not ids are skipped), feeds it back in `StartupState::recent_conversations`, and deletes it at sign-out.

### Runtime

`PUT /v1/messages/{id}/saved` is one attempt (the core repeats the idempotent request). The four reads (`saved`, `people`, `people/{user}`, `channels/browse`) are retried like any read and run through the same one-at-a-time slot helper as search and the inbox: a newer request of a kind, `Cancel…`, and sign-out hang up on the one waiting, which reports nothing. Query strings are encoded by `reqwest`; fields that are not set are not sent.

### Cache and upgrades

Nothing in the cache or journal changed; `PROTOCOL_VERSION` 12 discards a cache stamped 11 silently. Saved ids, the lists, and the profile are never cached. The recent conversations file is new and versioned from the start.

### Decisions D21 did not settle

* **The most recent conversation comes first in the empty switcher, though it is the one open**; the screen may start on the second row.
* **A match on a username counts 10 less than the same match on a title**, so `zoe` finds the conversation with Zoe before a group that has someone with that username.
* **Recency bonus is 3 per place on the list (up to 60); unread is +10 and a mention another +10, none when muted.**
* **Muted conversations are listed by the empty switcher only when visited**, never for their unread messages.
* **`BrowseChannels` keeps the directory's settings** (text, filter, sort) between openings; `CloseBrowse` (added to the contract) forgets them.
* **Asking to save does not refresh the open list; the server's word does** (see above).
* **A text over 100 characters is not sent**; the view says so with `Failed { can_retry: false }`.
* **Statuses in directory rows are the server's at the time of the page, updated by events**, and not hidden by the clock: show them with the clock-aware `status_of`.
* **The profile has no `user` field**: the screen reads `member(user_id)`.

## Workspace administration (slice 3F)

The contract is `llm-docs/DECISIONS.md` D22 and `PROTOCOL_VERSION` 13. The workspace has a name and settings that admins and owners change, people have a role and can be deactivated, admins make invitation codes that let a stranger join, and a deactivated person loses the workspace. The server decides who may do what; the core only decides what to offer, and refuses what cannot work without asking (using `lazy_domain::workspace`).

### What the UI calls

| Call | Meaning |
| --- | --- |
| `workspace_settings()` → `WorkspaceSettings`, `my_role()` → `Option<WorkspaceRole>`, `can_manage_workspace()`, `can_create_channel()` | The settings of the person's workspace (the defaults before one is known); their role as it stands now; whether they may change the workspace, invite, and manage people (admins and owners); whether they may create a channel (their role and `ChannelCreationPolicy::allows`). `Input::CreateChannel` is refused without a request, as an action failure, when `can_create_channel()` is false. The name is `primary_workspace().workspace.name`. |
| `member(id).deactivated` | Set for a deactivated person. `member(id)` and `display_name(id)` still find them, so their old messages keep a name. |
| `Input::UpdateWorkspace { name: Option<String>, settings: Option<WorkspaceSettings> }` | Progress and failure are `action(ActionKind::UpdateWorkspace)`. The name is trimmed and checked (`WorkspaceName`: 1 to 64 characters); asking to change nothing does nothing. One idempotent `PATCH` (read again after a lost answer), not journaled; the answer replaces name and settings and is cached; a refusal keeps what was shown and says why (the server's own words when it gave any). |
| `Input::SetMemberRole { user_id, role }`, `Input::SetMemberDeactivated { user_id, deactivated }` | Actions are `ActionKind::SetMemberRole(user)` and `ActionKind::SetMemberDeactivated(user)`, one per person. ### The code is shown once

Creating an invitation is the one request here that is not repeated: it carries no operation id, so repeating it could make two. An unknown outcome (a lost answer) sets a notice, asks for the list again, and leaves the action failed; the person decides whether to make another, and an invitation whose code was lost stays on the list for them to revoke. The code (`InviteCode`, whose `Debug` prints `<redacted>`) lives in `invitations().created` only: until `DismissCreatedInvitation`, `CloseInvitations`, a role that is no longer a manager's, losing access, an expired session, or sign-out. It is never cached, journaled, or saved, and the runtime holds it only in the response it hands to the core. An answer that arrives after the view was closed is dropped with its code. A revoke whose answer is lost asks for the list again, since nothing else would tell the view.

### Roles, deactivation, and who is offered

`MemberRoleChanged` updates the person's own role (so `can_manage_workspace()` follows at once, the cache is rewritten, and a person who stopped being a manager has the invitations closed and the directory's deactivated people switched off) and the loaded directory and profile copies. `MemberDeactivated` updates `member(id).deactivated`, the loaded copies, and drops the person from a directory that leaves deactivated people out (a reactivation asks the directory again, since the person is missing from it). A role or settings change that arrives in a bootstrap rather than an event does the same. A deactivated person is left out of `members()` (pickers, the quick switcher's people, group and conversation pickers), `@` suggestions, and mention resolution (a typed `@name` stays text); `OpenConversation`, `AddMembers`, and adding to a group are refused with an action failure (a deactivated person already in a group may stay when the group is edited).

### Registering with a code

The code is trimmed; blank is none; a non-blank code that cannot be one (`invite_code_is_wellformed`: 20 to 64 letters, digits, `_`, `-`) is refused without a request, and no message ever repeats the code. A registration the server refuses has its own words in the existing sign-in error (`SessionPhase::SignedOut { last_error }`): `invitation_invalid` ("That invite code isn't valid…"), and `forbidden` ("This workspace is invite-only…"); a sign-in is never worded as a registration.

### Losing access

When a deactivation happens the server ends the person's subscription with a `ServerFrame::Error { code: forbidden }` (the session itself stays valid). The core treats that (and `not_found`) like a snapshot request: it distrusts what it holds, discards the cache, and asks for a bootstrap, which is the truth about access. A bootstrap without the workspace leaves the session `Ready` with no workspace, no conversations, and nothing selected; `access_lost()` names the workspace from what was held (or from the cache restored at start); the subscription is ended with `Effect::Unsubscribe`; the cache is discarded and not written again; the invitations, the notification settings and the changes waiting to be saved, and the lists are cleared (what the person visited is kept). A later bootstrap that lists the workspace again (`RetryLoad`, a new sign-in, a restart) subscribes again and clears `access_lost()`. The name is only known within a run or from a restored cache: after a restart with no cache the empty state is generic.

### Runtime

`PATCH /v1/workspaces/{id}`, `PUT …/people/{user}/role`, `PUT …/people/{user}/deactivated`, and `DELETE /v1/invitations/{id}` are idempotent and read again after a lost answer; `POST …/invitations` is one attempt; `GET …/invitations` runs in a one-at-a-time slot (a newer request, `CancelInvitations`, and sign-out hang up on the one waiting). The role and deactivation answers are built from the request (the body is not relied on). `Effect::Unsubscribe` ends the workspace's connection for good (a later `Subscribe` starts a new one).

### Cache and upgrades

`PROTOCOL_VERSION` 13 discards a cache stamped 12 silently (the previous shape lacked `settings` and `deactivated`; both have serde defaults). The cache now carries the workspace's settings, the person's role, and each person's deactivation. No invitation or code is ever in the cache.

### Decisions D22 did not settle

* **Access loss is read from a `forbidden`/`not_found` error frame** (the contract names the frame; what the core does with it is this section). It costs a full resync, because the frame cannot say which of "deactivated" and "reactivated at once" is true.
* **`RetryLoad` is "check again"** when the session is ready and has no workspace; the contract added no input for it.
* **`access_lost()` is not persisted.**
* **The answer to a role or deactivation change is built from the request**, so the stub and the real server may answer with whatever body.
* **Deactivated people who are already in a group stay**; only adding one is refused locally.
* **A revoke whose answer was lost asks for the list again**, like a create does.
* **`Input` is `Debug` with the register and sign-in fields as text** (as the password already was): nothing in the core or runtime logs an `Input`, and anything that does must redact `Register` and `SignIn`.

## Several workspaces, profile, avatars, appearance (slice 3G)

The contract is `llm-docs/DECISIONS.md` D23 and `PROTOCOL_VERSION` 14. A person may belong to any number of workspaces. The core keeps all of them current (one realtime connection each, which the runtime already had), shows one, and counts what needs the person's attention in each.

### What the UI calls

| Call | Meaning |
| --- | --- |
| `workspace_rail()` → `Vec<RailItem { id, name, initials, role, active, attention, unread, connection }>` | One entry per workspace, in the server's order. `attention` is the number `attention_count()` gives when that workspace is active; `unread` is a dot (unread messages in unmuted conversations, shown only when `attention` is 0); `connection` is that workspace's own realtime state (`connection()` stays the worst of all). `initials` are the first letters of the first two words of the name, or its first two letters. |
| `active_workspace()`, `primary_workspace()` | The workspace on screen, and its entry (`primary_workspace()` is now the active one). |
| `attention_count()`, `attention_total()` | The active workspace's, and the sum over all workspaces (the window title, the launcher; `Effect::SetBadge` carries the total). |
| `Input::SwitchWorkspace(id)` | Makes a workspace active. An unknown id, or the active one, does nothing. The workspace left has its inbox, search, saved list, people, profile, directory, invitations, thread pane, and jump target closed; the conversation open in the new one is the one open in it last (the default if it is gone). |
| `Input::CreateWorkspace { name }` | `action(ActionKind::CreateWorkspace)`. The name is checked with `WorkspaceName`; the core picks the id; one idempotent `PUT`, repeated with the same id up to three times after an unknown outcome. Success lists the workspace, subscribes after its `head`, and makes it active. |
| `Input::AcceptInvitation { code }` | `action(ActionKind::AcceptInvitation)`. The code is trimmed and checked for its shape (`invite_code_is_wellformed`) before any request; it is never echoed, saved, or logged. One attempt (a use is counted). Success joins and makes the workspace active; the code of a workspace already joined just shows it. Refusals have their own words (`invitation_invalid`, a deactivated membership). |
| `Input::UpdateProfile { display_name }`, `SetAvatar { source }`, `RemoveAvatar` | `action(ActionKind::UpdateProfile)` and `action(ActionKind::SetAvatar)` (removing shares it). A picture is a `FileSource` (a path or bytes) the runtime reads; one over `MAX_AVATAR_UPLOAD_BYTES` is refused before it is read. The answer is the person as others now see them, applied in every workspace. |
| `avatar(user)` → `Option<&ImageState>`; `Input::LoadAvatar(user)` | The picture (256 by 256 PNG bytes) of a person at their current version, once asked for; ask for people on screen only. `member(id).avatar_version` is 0 without one (nothing is fetched then). The version is found among the bootstrap's members of any workspace, the people directory page(s) held, and the loaded profile (`avatar_version(user)` gives it). A new version drops the old picture and fetches the new one; at most 200 pictures and 24 MiB are held (least recently used go first); a failed fetch is `Failed` until asked for again. |
| `appearance()`, `Input::SetAppearance(Appearance { theme, motion })` | Local to the device, applied at once (`Change::AppearanceChanged`), saved with `Effect::PersistAppearance`, and given back in `StartupState::appearance`. |

**Changes**: `RailChanged`, `ActiveWorkspaceChanged` (re-read everything workspace-scoped), `AppearanceChanged`, `AvatarChanged { user }`. **Effects**: `CreateWorkspace`, `AcceptInvitation`, `UpdateProfile`, `SetAvatar`, `RemoveAvatar`, `FetchAvatar`, `ForgetAvatars`, `PersistActiveWorkspace`, `PersistAppearance`. **Runtime reports** (the UI never sends them): `AvatarLoaded`, and `ActionOutcome::Joined` / `Profile` in the action results. `NotificationSettingsResult` and `StatusResult` now carry the `workspace` they were asked for (the runtime echoes it).

### Scopes

Everything that belongs to one workspace (its people and the person's status and deactivation among them, its conversations, groups, custom emoji, the person's notification settings, and the views of the inbox, search, saved list, directory, profile, and invitations) lives in the core's ordinary fields for the *loaded scope*; the other workspaces' copies are parked. The old code is unchanged: it reads and writes the loaded scope. An event of a workspace in the background, and the answer to a request made for one, are applied by loading that workspace's scope around the ordinary handler and loading the active one again afterwards (`route_scope`, `in_scope`); `handle` always ends with the loaded scope the active one. Each action in flight remembers the workspace it was started in, so a late answer lands there. Shared by all workspaces, and never exchanged: the person, timelines, read states and threads (keyed by id), drafts, the connections, the cache, the notice, preferences for conversations, saved marks, recent searches and visits, and the counters that number requests (so a late answer is never taken for another workspace's request). A conversation of a background workspace is never the selected one, and `select_conversation` or a permalink into another workspace switches to it first.

* **People**: a person known in several workspaces is the same person: a profile event in any log, or the answer to the person's own change, updates every workspace's copy; a bootstrap or a joined workspace is the newest the core has and is applied to the copies elsewhere. `member(id)` finds only people of the active workspace (someone of another workspace only is `None`, so a stranger never looks like a member), while `display_name(id)` names a person from any workspace, since a name is the person's own. Statuses and deactivation are each workspace's own.
* **Notifications** are made under the owning workspace's settings; the title starts with the workspace's name ("Beta · #general") when the person has more than one workspace and the event is not in the active one. `NotificationActivated` for a background message switches to its workspace and then opens it. A message is notified once, whichever workspaces exist. **Nothing is notified until a bootstrap has said what the person's settings are** (a start from the cache has none, since the cache does not hold them); the few messages that arrive live in that moment are counted but not shown.
* **A workspace that stops being listed** (a bootstrap without it) leaves the rail with a notice; its scope, cache entry, and subscription go (`Effect::Unsubscribe`); if it was active, the app's last-saved choice or the first remaining one becomes active; with none left the no-access screen shows (D22).
* **Active workspace** is saved with `Effect::PersistActiveWorkspace` (`active-workspace.json`, versioned like `recent-conversations.json`, deleted at sign-out) and restored from `StartupState::active_workspace`; the first workspace is used when it is gone.

### Runtime

`PUT /v1/workspaces/{id}` and `POST /v1/invitations/accept` are single attempts (the core repeats the first with the same id). `PATCH /v1/me` and `DELETE /v1/me/avatar` are idempotent and read again after a lost answer. `PUT /v1/me/avatar` sends the raw bytes with the sniffed type as a hint; a path is read off the core's thread, checking its size first. `GET /v1/users/{id}/avatar?v=` (at most 2 MiB) is cached on disk, encrypted, in `avatars/` (32 MiB, least recently used first) under a hash of the person and version, so no file says whose it is; `ForgetAvatars` drops what this run fetched for those people; sign-out empties the cache. `appearance.json` (`{"version": 1, "appearance": {"theme": …, "motion": …}}`) is written with the other small preferences; a value this build does not know costs only itself; **sign-out leaves it**, since it is the device's, not the account's.

### Cache and upgrades

`PROTOCOL_VERSION` 14 discards a cache stamped 13 silently (people gained `avatar_version`, with a serde default). The cache holds every workspace (their conversations, people, groups, emoji, cursors, timelines, and read states); the selection of each is in the view state and the drafts are keyed by conversation, so a restart restores all of them. It does not hold notification settings or statuses (they come from the bootstrap that follows every start).

### Decisions D23 did not settle

* **`primary_workspace()` is kept as the name of the active workspace's entry** rather than renamed.
* **Appearance survives sign-out**, as above.
* **`CreateWorkspace` and `AcceptInvitation` make the workspace active at once**, closing the views of the one left, as a switch does.
* **A profile event that arrives in one log before an older one in another** shows the older for a moment (the events carry no order across logs); the logs converge, and a version change always refetches the picture of the version shown.
* **Notifications wait for the first bootstrap of a run** (the decision above), the one behavior change to the older notification code.
* **The shared `Effect` and `Input` shapes changed in two places**: `NotificationSettingsResult` and `StatusResult` carry a `workspace`.
* **A person only the directory or a profile knows** has their picture fetched from the version on that page.
* **The simulation for several workspaces is a second suite** (`tests/multi_workspace_sim.rs`) with three workspaces of its own, not an extension of the single-log one (see the verification table).

## Logging and diagnostics (slice 3I)

The contract is `llm-docs/DECISIONS.md` D24 ("Logging") and a wire that does not change (`PROTOCOL_VERSION` 14). The client logs what happened and to what, never what was typed or read, and offers a report of its own health that is safe to copy into a bug report.

### Printing that cannot leak

`Input`, `Effect`, `JournalEntry`, `StartupState`, `ContentCache`, `LocalFile`, `FileSource`, and `DesktopNotification` have hand-written `Debug`. The text of an `Input` or an `Effect` is the variant, its identifiers, its numbers, and the *length* of any text (`SendMessage { conversation: ..., text: <redacted 12 chars> }`); a request error prints its code (`Rejected(Forbidden)`) or that its outcome is unknown, a transfer error the way it failed (never the system's reason, which can hold a path), a server frame its workspace, position, and kind.

`input_debug.rs` and `effect_debug.rs` are one exhaustive `match` each, so a new variant does not compile until its arm is written. A field prints as itself only when its type is on a short list (identifiers, numbers, booleans, enums of fixed words, the protocol's secret wrappers, which redact themselves); text prints as its length; everything else prints as `<TypeName>`. A new kind of content is therefore hidden until someone decides it may be shown.

What is *not* redacted: the read model (`TimelineItem`, `SearchView`, `ComposerAttachment`, and the like) is what the screen shows. Logging one is the caller's choice and should be made on purpose.

### What the runtime logs

All of it is `tracing`; the host picks the filter. No line holds a message, a name, a path, a query, a token, a code, or an address.

| Where | Level | Event (fields) |
| --- | --- | --- |
| every request (`api`) | DEBUG; WARN for a 5xx or no answer | `request answered` (`method`, `route`, `status`, `elapsed_ms`); `a request got no answer` (`reason`: `timed out`, `connection failed`, ...). The route is a pattern: the words of the path stay, every identifier becomes `:id` (`/v1/conversations/:id/messages`), the query is never logged |
| retries of reads (`retry_read`) | DEBUG | `repeating a read after an unknown outcome` (`attempt`, `attempts`) |
| realtime | DEBUG / INFO / WARN | `opening the realtime connection` (`workspace`, `attempt`); `realtime connection open` (`cursor`); `caught up with the server` (`seq`); `the server needs a fresh snapshot`; `the server no longer accepts the session`; `realtime connection ended` (`reason`); `ignoring a realtime frame that could not be parsed` (`reason` is the kind and place of the JSON error, `bytes` its size) |
| uploads | WARN | `an attachment upload failed` (`reason`: `TransferError::code()`) |
| cache | INFO / WARN | `discarding the saved message cache` (the core asked); `... from an older protocol`; `... its contents are invalid` (the place of the JSON error) |
| sign-in | INFO | `signed in` (`user`: the id); `sign-in failed` (`reason`: the error code) |
| every effect the runtime executes | TRACE | `executing an effect` (`effect`: the redacted `Debug`) |

Errors that reach a notice or the diagnostics carry a code or fixed words, not a body. `describe` turns a `reqwest::Error` into `timed out`, `connection failed`, `too many redirects`, `the response could not be decoded`, and so on, because `reqwest`'s own text ends with the request's URL and its query (a search). `describe_json` turns a `serde_json::Error` into its kind and its line and column, because `serde_json` quotes the value that was the wrong shape (`invalid type: string "..."`). A panicked or cancelled task is logged as `panicked` or `cancelled`, because `tokio`'s `JoinError` repeats the panic message.

Libraries underneath log too: at TRACE and DEBUG `hyper_util` names the server's host and port (the capture test found it). That is no secret and no content, but a host that turns the filter up should leave dependencies at WARN. Records from the `log` crate (`tungstenite` uses it) are not `tracing` events and are not looked at by the capture test.

### The diagnostics report

`ClientCore::diagnostics() -> Diagnostics` is plain data for the Help, Diagnostics dialog (the UI adds the application version, the operating system, the server address, and the folders, which only it knows):

| Field | Meaning |
| --- | --- |
| `protocol_version` | `PROTOCOL_VERSION` of this build |
| `phase`, `connection` | `loading`, `signed_out`, `signing_in`, `unreachable`, or `ready`; and the aggregate connection (`live`, `catching_up`, `connecting`, `reconnecting (attempt N)`, `offline`) |
| `workspaces` | One `WorkspaceDiagnostics { id, active, connection, applied }` per workspace: the identifier, never the name |
| `conversations`, `unsettled_operations`, `uploads_in_flight`, `cached_messages` | Counts. An unsettled operation is a send or an edit not yet confirmed (failed ones included) |
| `recent_errors` | The last `MAX_DIAGNOSTIC_EVENTS` (10) errors, oldest first, each `{ at: Option<Timestamp>, category, code }` |

`report()` renders it as one fact to a line. `at` is the time the core was last told (it has no clock of its own). Recorded: `auth`, `bootstrap`, `history`, `send`, `action`, `upload` (each with `RequestError::code()` or `TransferError::code()`: the server's error code as a snake_case word, `unknown_outcome`, `too_large`, `unreadable`, `missing`, `disk`, `checksum_mismatch`, `cancelled`), `realtime` (the code of an error frame), `socket` (`closed`), `snapshot` (`required`), `session` (`expired`), `storage` (`problem`, `startup_problem`), and `cache` (`discarded_other_account`, `discarded_snapshot_required`, `discarded_workspace_lost`). A message shown to the person is not an error of the program and is not recorded.

## Runtime

```rust
let (runtime, inputs) = Runtime::start(RuntimeConfig::from_env())?;  // inputs: async_channel::Receiver<Input>
runtime.execute(output.effects);                                      // never blocks
runtime.shutdown();                                                   // call outside any async context
```

`RuntimeConfig` fields: `server_url` (default from `LAZY_SERVER_URL`, fallback `http://127.0.0.1:8080`), `profile_dir` (`None` → `LAZY_PROFILE_DIR` → the platform data directory), `secure_storage`, `request_timeout`, `read_attempts`, `reconnect` (`BackoffPolicy`), `idle_timeout`, `save_debounce`.

### Ownership

`Runtime` owns a two-thread Tokio runtime and everything spawned on it. HTTP tasks live in a `JoinSet` and stop when the cancellation token fires; each realtime subscription has a child token and a command channel and ends on sign-out, expiry, or shutdown; the journal actor applies journal commands in order (including discarding the cache) and the saver coalesces drafts and the cache. `shutdown()` cancels, lets the journal actor finish queued commands, flushes pending saves, awaits all tasks (aborting after 5 seconds), and stops the runtime. Task panics are logged when tasks are reaped. A mutation interrupted by shutdown stays in the journal.

The input channel is bounded (4096). A host that stops draining it slows the realtime reader rather than growing memory.

### Failure classification

Reads that are safe to repeat (bootstrap, history, operation status, fetching a message) are retried up to `read_attempts` with backoff, then reported as `Unknown`. Deleting a message is idempotent on the server and is retried the same way. Mutations (register, login, send, **edit**, **react**) are attempted exactly once; a reaction's unknown outcome is repeated by the core, not the runtime, because only the core knows the person's latest wish. Creating a group is attempted once (the core reconciles it); changing one is a single attempt; deleting one and fetching a conversation's people are idempotent reads and are retried. A 4xx with an `ApiError` body whose code is a definitive refusal is `Rejected`; a timeout, dropped connection, 5xx, or unparseable body is `Unknown`. A 401 on the WebSocket upgrade becomes `Input::SessionExpired`.

### Conversation requests

Created and opened conversations use `POST` once, never repeated by the runtime (the core reconciles). Browsing is a safe read and is retried. The other management calls are single attempts: join, archive, unarchive (`POST`, no body, answered with the conversation), leave (`POST`) and remove member (`DELETE`) where any 2xx status counts and the body is ignored (the contract does not say what they return), add members (`POST` with `user_ids`), update (`PATCH`, absent fields unchanged), favorite (`PUT`), and mark read (`POST` with `up_to`). All use `lazy_protocol::paths` and the same failure classification: a 4xx `ApiError` with a definitive code is a refusal, anything else is an unknown outcome.

### Secrets

The session token and the 256-bit key protecting local files live in `SecureStorage`. Entries are namespaced by SHA-256 of (canonical profile directory, normalized server URL), under keys `session-token:<namespace>` and `state-key:<namespace>`, so two clients on one machine (`LAZY_PROFILE_DIR=a`, `LAZY_PROFILE_DIR=b`) never share, overwrite, or delete each other's secrets, and a token is never offered to a different server. Sign-out deletes only its own namespace.

* `KeyringStorage` uses the OS credential store (Secret Service on Linux; verified working here).
* `InsecureFileStorage` stores plain files in `<profile>/insecure-secrets/` and is used only with `SecureStorageChoice::InsecureFile` (`LAZY_INSECURE_STORAGE=1`). It is never chosen automatically. If the credential store is unavailable the runtime reports it in `Started.problems`, and refuses to journal (so sends fail with an explanation) rather than writing anything unprotected.

### Local files

`<profile>/outbox/` (encrypted copies of files waiting to be uploaded), `<profile>/images/` (the encrypted image cache), and `<profile>/emoji/` (the images of custom emoji, 16 MiB) hold chunked blobs, not state files: see [Attachments](#attachments-slice-3a). `<profile>/emoji-prefs.json` is a plain file: see [Emoji preferences](#emoji-preferences). The others are `<profile>/journal.enc`, `drafts.enc`, `cache.enc`: `LZST` magic, format version, kind, 24-byte nonce, XChaCha20-Poly1305 ciphertext of JSON, with the header authenticated. Writes go to `<name>.tmp`, are fsynced, renamed over the target, and the directory is fsynced; the acknowledgment (`SubmissionPersisted`) is sent only after that. Limits: journal 256 entries / 16 MiB, drafts 200 / 64 KiB each / 8 MiB, cache 200 messages per conversation / 50 conversations / 4 MiB (evicted by whole timelines when over). An unreadable file is renamed to `<name>.corrupt-<timestamp>` (at most three kept), reported through `Started.problems`, and never silently dropped; a file with a newer format is left untouched and its kind is locked against writes. Files are mode 0600 and the profile directory 0700.

## Wiring it into GPUI

Sketch checked against the pinned revision's `Context::spawn` (`AsyncFnOnce(WeakEntity<T>, &mut AsyncApp)`); adjust names to the actual code.

```rust
struct AppModel {
    core: ClientCore,
    runtime: Runtime,
    // list states, views, ... keyed by conversation
}

impl AppModel {
    fn new(cx: &mut Context<Self>) -> anyhow::Result<Self> {
        let (runtime, inputs) = Runtime::start(RuntimeConfig::from_env())?;
        // Drain runtime reports on GPUI's foreground executor. The task is retained in a field
        // (or detached on purpose) so it lives as long as the model.
        cx.spawn(async move |this, cx| {
            while let Ok(input) = inputs.recv().await {
                if this.update(cx, |model, cx| model.apply(input, cx)).is_err() {
                    break; // the model was dropped
                }
            }
        })
        .detach();
        Ok(Self { core: ClientCore::new(), runtime })
    }

    /// The single entry point for person actions and runtime reports.
    fn apply(&mut self, input: Input, cx: &mut Context<Self>) {
        let output = self.core.handle(input);
        self.runtime.execute(output.effects);
        for change in output.changes {
            self.update_list_state(change); // splice / remeasure / reset, in order
        }
        cx.notify();
    }
}

// From a view: composer submit, sidebar click, ...
model.update(cx, |m, cx| m.apply(Input::SendMessage { conversation, text }, cx));
```

On window close or app quit, call `runtime.shutdown()` from a non-async context so the pending drafts and cache are flushed and connections close cleanly.
